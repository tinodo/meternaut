# Bootstrap: the one step that is not a workflow

Every change to Azure goes through the workflow [`deploy-hub.yml`](../.github/workflows/deploy-hub.yml) ([AGENTS.md](../AGENTS.md) rule 18). The workflow signs in to Azure as an identity, and an identity cannot create itself, so a person creates it once. That is this page. It is the only manual step, and nothing here runs until the owner has said yes in plain words in the conversation.

> **Since 2026-11-10 this repository is public ([rule 37](../AGENTS.md)), and since 2026-11-11 the Hub runs in it, directly ([rule 18](../AGENTS.md)).** This page is the record of how the first environment was made, and steps 3 and 5 below are written for the repository as it is now. The logs of a public repository are readable by anyone, so: the job of the Hub is bound to the GitHub environment `hub`, which accepts a deployment from `main` alone; the federated credential of step 3 trusts the subject of that environment and no branch and no pull request; every identifier of the estate is a secret of that environment (step 5), which GitHub masks in the log and in the summary, and only plain configuration is a variable of it; and the repository's own settings hold no secret and no variable. A plan of the same day, in which a small private repository would call the Hub, was dropped: a private repository costs Actions minutes again. The owner says yes to steps 3 and 5 first, in plain words ([rule 18](../AGENTS.md)).

**In GitHub**, on this repository: one environment, `hub`, and its settings. The environment accepts a deployment from the branch `main` alone (a deployment branch rule), and the federated credential of step 3 trusts only it. Its **secrets** are the identifiers of the estate, which the workflow reads and GitHub masks in the public log (none is a password or a key): `AZURE_CLIENT_ID` (the identity's client id), `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID`; `ENV_VNET_PREFIX` and `ENV_PE_SUBNET_PREFIX` (two address ranges) and `ENV_DNS_SERVERS` (the DNS server); `ENV_OWNER` and `ENV_ALERT_EMAILS` (the owner's address twice); `CONSOLE_APP_CLIENT_ID`, `CONSOLE_PEOPLE` and `MAIL_SENDER` (the function app, below); and, optional, `CONSOLE_HOST_NAME` (below) and `DRIFT_ACCEPTED_EXEMPTIONS` and `DRIFT_ACCEPTED_DENY` (the drift check, below), and `TEAMS_BOT_APP_ID` (the Teams bot, below; replaced by the owner's ruling of 2026-11-13, pending his plain yes): an unset secret reads as an empty text, which the tools take as unset. Its **variables** are plain configuration, which the page of a run may show: `ENV_RESOURCE_GROUP` (the project's resource group), `ENV_LOCATION` (the region) and `ENV_BUDGET_AMOUNT`, and, optional, `TEAMS_DELIVERY` (queue or bot: the Teams bot, below; replaced by the owner's ruling of 2026-11-13, pending his plain yes). The repository's list of allowed actions holds `azure/login`, at the full commit that the workflow names, besides GitHub's own actions. No secret and no variable is set at repository level (`drift.yml`, which stays disabled, would read one repository variable, `DRIFT_CLIENT_ID`, once an identity of its own exists for it: none is set): until 2026-11-11 the first three secrets and eight variables were, and the function app's and the drift check's values were repository variables, so the owner moves them into the environment (step 5) and deletes the repository-level ones. Two older secrets and one older variable were set when the environment was first made, and no workflow step reads any of them since 2026-11-07, so the owner deletes them: the secrets `GATEWAY_RESOURCE_ID` (the resource id of the API Management instance) and `GATEWAY_APPINSIGHTS_ID` (the resource id of the Application Insights component that the usage recording read), and the variable `RECORDING_READER_IDS` (the people who could read the usage store) ([the section](#changed-on-2026-11-07-the-usage-recording-and-the-old-model-account-are-removed)).

## Running the Hub

The Hub is the workflow [`deploy-hub.yml`](../.github/workflows/deploy-hub.yml): it starts by hand only (`workflow_dispatch`), as the owner's account on `main`, and an agent starts it only on the owner's plain words ([rule 18](../AGENTS.md)). The actions that only read (`what-if`, `drift-check`, `agents-drift`, `agent365-check`, and `foundry-evals` with `probe` or `rule`) need no yes. `agents-drift`, `foundry-evals` and `foundry-redteam` read nothing (403 and 401) until the Operator's identity holds Foundry User on the project, which the action `foundry` gives it once `operator` has made the identity. It runs in this repository, in the environment `hub` (below).

**In this repository, in the environment `hub` (built on 2026-11-11, not yet run).** The job of the Hub is bound to the environment `hub`, which accepts a deployment from `main` alone, and it signs in with OpenID Connect and the action `azure/login` (pinned to a full commit, and on the repository's list of allowed actions): no credential is stored, and the federated credential of the identity (step 3) trusts the subject of the environment and nothing else. The log, the summary and the annotations of a run are public, so every identifier of the estate is a secret of the environment (the list is under *In GitHub* above), GitHub masks it from the first line of the log, the workflow publishes no output of the job, and each step masks what it reads from Azure before it prints anything. The first thing a run does is to ask GitHub whether CI passed for the commit that the run is on. What the owner says yes to is the environment and its branch rule, the credential for its subject, its secrets and variables, the allowed action, and a first run of `what-if`. A plan of 2026-11-11, in which a small private repository would call the Hub (and pin one commit of this one), was dropped the same day, because a private repository costs Actions minutes again and a public one does not. `drift.yml`, whose identity does not exist yet, stays disabled in the Actions settings.

## What the identity can and cannot do

Since 2026-11-07 it does nothing on the owner's API Management instance: the workflow has no action, and the repository no template or tool, that can create, change or read an object of it ([rule 15 (c)](../AGENTS.md)). On the real estate the identity still holds the custom role *Meternaut gateway deployer* in the instance's resource group, which could add and change objects in the instance and change its service-level settings (Azure's roles cannot narrow a role to some objects of an instance, so what held it to the Citadel module's objects was the workflow, which is gone). Nothing uses the role now, so a person removes it ([the section](#the-custom-role-no-longer-used)). It never had a right to delete in the instance or in the gateway's group.

It can delete the project's resource group with everything in it, because *Contributor* covers that; the workflow never does, and a budget alert is the only warning. It cannot create other resource groups, change anything else in either subscription, register a resource provider, purge a soft-deleted account (the action `retire-old` tries it once, for the old model account, and says so when Azure refuses: [the section](#changed-on-2026-11-07-the-usage-recording-and-the-old-model-account-are-removed)), give any role except the nine above (and the tenth, [for the AI Gateway](#added-on-2026-11-07-for-the-ai-gateway), whose hand step was done on 2026-11-07) to a service principal in the project's group, or touch the network, the firewall or the DNS of the landing zone.

Who can use the credential: a run of the Hub in the environment `hub`, and nothing else. The credential trusts the subject of the environment and not a branch, a tag or a pull request, so a pull request, a fork, a branch and every other workflow of the repository get no token that Azure accepts. The environment accepts a deployment from `main` alone, the job starts only by hand and only as the owner's account (its guard), and `main` is protected by the owner's ruleset (a pull request and the check `checks`, no force push, no deletion, no bypass), so a commit that runs with the identity passed `checks` and was read in full ([rule 37 (e)](../AGENTS.md)). [`tools/workflow-lint.py`](../tools/workflow-lint.py) fails a change that would make the Hub start any other way, take the environment away or read a secret that is not on the list. The credential `github-main`, which was made for the earlier, private repository and trusted that repository's immutable ids and not this one's, was deleted on 2026-11-11, after the first runs of the Hub in the environment had signed in with the credential of the environment: the deploy identity has the one federated credential `github-hub-env` and no other. A required reviewer can be added to the environment (a public repository can have one); until the owner adds it, the approval is a rule of process: the owner says it in plain words in the conversation. An agent starts `what-if`, which reads and changes nothing, on its own; every action that deploys or changes something needs his words (one yes to the whole list is enough), and `aigateway` also needs the input `public_ai_gateway_requested`, which only his written request for a public AI Gateway allows ([the record](../docs/proposals/08-ai-gateway.md#the-guard-against-a-public-front-door-by-accident)).

## The custom role (no longer used)

When the environment was first made, the owner gave the deploy identity a custom role, *Meternaut gateway deployer*, in the resource group of his API Management instance, so that the workflow could add Citadel's objects to the instance and make the access product of the first cases on it. On 2026-11-07 he ordered the undo of everything that Meternaut added there, and since then no Hub action, template or tool of the repository reads or writes anything outside the project's own resource group (a test pins that), so nothing uses the role any more. The role is retired: it is the item W8 of [`access-requirements.json`](access-requirements.json), and its definition is not kept on this page (the history of the repository has it): nobody is to make it again.

A person removes it, on the owner's word, signed in as himself, with the same tool that retires the key reader (W7): `python tools/access-requirements.py retire --only W8 --gateway <resource id of the API Management instance>`, a dry run first, and then the same with `--apply`. It removes every assignment of the role in the instance's resource group and below it, whoever holds it (the deploy identity's among them), and then the role. It deletes no identity: the deploy identity stays, because it deploys the project's own resource group. No action does this, and none may: the workflow's identity must not hold the right to assign roles there. On this page the role is the only right of the deploy identity outside the project's group, so afterwards it holds none, and the other roles of this page do not touch the instance.

## The commands

Run once, by the person who approved it, signed in to Azure and to GitHub as himself. Nothing here is written into the repository: fill in the values at the top. The Azure CLI is called through its own Python because the `az.cmd` wrapper on Windows mangles the parentheses of the condition.

```powershell
$devSub    = '<id of the subscription that holds the project''s resources>'
$insights  = '<resource id of the old gateway''s Application Insights component: only to retire W9 and W10, see the section of 2026-11-07 that removes the usage recording>'
$owner     = '<the owner''s mail address>'
$vnet      = '<a free /24 inside 10.0.0.0/8 for the network>'
$subnet    = '<the first /27 of it, for the endpoint>'
$dns       = '<the landing zone''s DNS server>'
$region    = 'swedencentral'
$repo      = 'tinodo/meternaut'
$idGroup   = 'meternaut-bootstrap-sc-rg'
$hubGroup  = 'meternaut-sc-rg'
$uami      = 'meternaut-deploy-sc-uami'
function az { & 'C:\Program Files\Microsoft SDKs\Azure\CLI2\python.exe' -IBm azure.cli @args }

# 1. The two resource groups
az group create --subscription $devSub --name $idGroup  --location $region --tags workload=meternaut component=identity owner=$owner
az group create --subscription $devSub --name $hubGroup --location $region --tags workload=meternaut component=project owner=$owner

# 2. The identity
az identity create --subscription $devSub --resource-group $idGroup --name $uami --location $region --tags workload=meternaut
$principal = az identity show --subscription $devSub --resource-group $idGroup --name $uami --query principalId --output tsv
$client    = az identity show --subscription $devSub --resource-group $idGroup --name $uami --query clientId --output tsv

# 3. The credential: a run of the Hub, which is bound to the GitHub environment "hub" of this repository (step 5 makes the
#    environment). GitHub names the repository in the subject by its owner's and its own numeric id too
#    (repo:<owner>@<id>/<repository>@<id>); the repository's own setting gives that prefix. The plain form
#    repo:<owner>/<repository> does not match: Azure answers AADSTS700213. No branch, tag or pull request subject is made:
#    only a job that is bound to the environment gets a token that Azure accepts.
$prefix = (gh api "repos/$repo/actions/oidc/customization/sub" | ConvertFrom-Json).sub_claim_prefix
az identity federated-credential create --subscription $devSub --resource-group $idGroup --identity-name $uami --name github-hub `
  --issuer https://token.actions.githubusercontent.com --subject "${prefix}:environment:hub" --audiences api://AzureADTokenExchange

# 4. The rights on the project's group
$scope = "/subscriptions/$devSub/resourceGroups/$hubGroup"
az role assignment create --assignee-object-id $principal --assignee-principal-type ServicePrincipal --role 'Contributor' --scope $scope
$condition = @'
((!(ActionMatches{'Microsoft.Authorization/roleAssignments/write'})) OR (@Request[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {5e0bd9bd-7b93-4f28-af87-19fc36ad61bd} AND @Request[Microsoft.Authorization/roleAssignments:PrincipalType] ForAnyOfAnyValues:StringEqualsIgnoreCase {'ServicePrincipal'})) AND ((!(ActionMatches{'Microsoft.Authorization/roleAssignments/delete'})) OR (@Resource[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {5e0bd9bd-7b93-4f28-af87-19fc36ad61bd} AND @Resource[Microsoft.Authorization/roleAssignments:PrincipalType] ForAnyOfAnyValues:StringEqualsIgnoreCase {'ServicePrincipal'}))
'@
az role assignment create --assignee-object-id $principal --assignee-principal-type ServicePrincipal --role 'Role Based Access Control Administrator' --scope $scope --condition $condition --condition-version 2.0

# 5. The environment "hub" and its settings. The environment accepts a deployment from main alone, and every identifier of
#    the estate is a secret of it: the log of a public repository is public, GitHub masks a secret and does not mask a
#    variable. Nothing is set at repository level.
gh api -X PUT "repos/$repo/environments/hub" -F "deployment_branch_policy[protected_branches]=false" -F "deployment_branch_policy[custom_branch_policies]=true"
gh api -X POST "repos/$repo/environments/hub/deployment-branch-policies" -f name=main -f type=branch
$tenant = az account show --subscription $devSub --query tenantId --output tsv
gh secret set AZURE_CLIENT_ID          --env hub --repo $repo --body $client
gh secret set AZURE_TENANT_ID          --env hub --repo $repo --body $tenant
gh secret set AZURE_SUBSCRIPTION_ID    --env hub --repo $repo --body $devSub
gh secret set ENV_VNET_PREFIX          --env hub --repo $repo --body $vnet
gh secret set ENV_PE_SUBNET_PREFIX     --env hub --repo $repo --body $subnet
gh secret set ENV_DNS_SERVERS          --env hub --repo $repo --body $dns
gh secret set ENV_OWNER                --env hub --repo $repo --body $owner
gh secret set ENV_ALERT_EMAILS         --env hub --repo $repo --body $owner
# (the secrets CONSOLE_APP_CLIENT_ID, CONSOLE_PEOPLE and MAIL_SENDER, and the optional CONSOLE_HOST_NAME,
#  DRIFT_ACCEPTED_EXEMPTIONS and DRIFT_ACCEPTED_DENY, are set where the sections below introduce them)
# (no secret for the old gateway's Application Insights any more: since 2026-11-07 nothing reads it)
gh variable set ENV_RESOURCE_GROUP     --env hub --repo $repo --body $hubGroup
gh variable set ENV_LOCATION           --env hub --repo $repo --body $region
gh variable set ENV_BUDGET_AMOUNT      --env hub --repo $repo --body 25
# The one action outside GitHub's own that the Hub uses, at the commit that the workflow names, goes on the repository's
# list of allowed actions
$login   = (Select-String -Path .github/workflows/deploy-hub.yml -Pattern 'uses: (azure/login@[0-9a-f]{40})' | Select-Object -First 1).Matches[0].Groups[1].Value
$allowed = gh api "repos/$repo/actions/permissions/selected-actions" | ConvertFrom-Json
$allowed.patterns_allowed = @($allowed.patterns_allowed) + $login
$allowed | ConvertTo-Json | gh api -X PUT "repos/$repo/actions/permissions/selected-actions" --input -
```

Read the result back before the first run: `az role assignment list --assignee $principal --all --output table` shows two assignments (an estate that was made before 2026-11-07 shows a third, the custom role of [the section above](#the-custom-role-no-longer-used), which a person removes), `gh api repos/$repo/environments/hub/deployment-branch-policies` shows the one policy `main`, `gh secret list --env hub --repo $repo` shows the eight secrets of step 5 (and later the ones that the sections below add) and `gh variable list --env hub --repo $repo` the three variables. `gh secret list --repo $repo` and `gh variable list --repo $repo` show none: an estate that was made before 2026-11-11 set three secrets and eight variables there (an older one has two more secrets, `GATEWAY_RESOURCE_ID` and `GATEWAY_APPINSIGHTS_ID`, which nothing reads), and the owner deletes them once the environment holds the values. The budget's start date is not a setting: the workflow reads it from the budget once it exists.

**The one hand step: one more role in the condition.** The condition of the deploy identity's *Role Based Access Control Administrator* assignment lists the roles that it may give to a service principal ([above](#added-on-2026-11-04-for-the-usage-recording)). The template gives the cases app *Azure AI User*, which is not in the list, so the action would be refused. *Monitoring Metrics Publisher*, the other role that the template gives, is in the list already. A person who may assign roles in the project's group adds the one id, with their own sign-in, on the owner's written word, and reports it at once.

The condition is changed **in place, with one write**: `az role assignment update` takes the assignment as JSON, changes its condition, and the assignment keeps its id. There is no moment in which the deploy identity has no assignment, so nothing has to be restored when the write fails. The commands read first (there must be exactly one assignment, and its condition must have the shape that the templates write), change nothing but the list of ids, show what changes, and ask before they write. They test the exit code of the update: when it fails, nothing else happens and the assignment is unchanged. After a good update they read the assignment back and fail unless there is exactly one, with the same id, whose two lists of role ids both hold the old ids and the Foundry User role. Nothing is written until the person types `yes`; any other answer is a dry run that changes nothing. They run in PowerShell 7 and in Windows PowerShell 5.1. Paste them as one block, or save them as a `.ps1` file, so that an error stops the rest. They use `$devSub`, `$hubGroup` and `$principal` of the commands at the top of this page:

```powershell
function az { $PSNativeCommandArgumentPassing = 'Legacy'; & 'C:\Program Files\Microsoft SDKs\Azure\CLI2\python.exe' -IBm azure.cli @args }
$scope = "/subscriptions/$devSub/resourceGroups/$hubGroup"
$foundryUser = '53ca6127-db72-4b80-b1b0-d745d6d5456d'
$read = "az role assignment list --subscription $devSub --assignee-object-id $principal --scope $scope --role 'Role Based Access Control Administrator' --output json"
function Get-Assignments { param($Query) az role assignment list --subscription $devSub --assignee-object-id $principal --scope $scope --role 'Role Based Access Control Administrator' --query $Query --output json }
# 1. Read the assignment (there must be exactly one) and the role ids that its condition lists (the list for a write and the list for a delete must be the same)
$count = Get-Assignments 'length(@)'
if ($LASTEXITCODE -ne 0) { throw "The assignments could not be read (exit code $LASTEXITCODE). Nothing was changed. Read them: $read" }
if ("$count".Trim() -ne '1') { throw "The deploy identity must have exactly one Role Based Access Control Administrator assignment on the project group, and the list says '$count'. Nothing was changed. Read them: $read" }
$text = Get-Assignments '[0]'
if ($LASTEXITCODE -ne 0) { throw "The assignment could not be read (exit code $LASTEXITCODE). Nothing was changed. Read it: $read" }
$old = $text | ConvertFrom-Json
$lists = @([regex]::Matches($old.condition, 'GuidEquals\s*\{([^}]*)\}') | ForEach-Object { ($_.Groups[1].Value -split ',\s*' | Sort-Object) -join ',' })
if ($lists.Count -ne 2 -or ($lists | Select-Object -Unique).Count -ne 1) { throw 'The condition is not the one that the templates expect (two lists of the same role ids). Stop and read it.' }
$current = $lists[0] -split ','
if ($current -contains $foundryUser) { throw 'The condition lists the Foundry User role already: nothing to do.' }
# 2. Add the one id, and change nothing else of the condition
$roles = (@($current) + $foundryUser) -join ', '
$condition = "((!(ActionMatches{'Microsoft.Authorization/roleAssignments/write'})) OR (@Request[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {$roles} AND @Request[Microsoft.Authorization/roleAssignments:PrincipalType] ForAnyOfAnyValues:StringEqualsIgnoreCase {'ServicePrincipal'})) AND ((!(ActionMatches{'Microsoft.Authorization/roleAssignments/delete'})) OR (@Resource[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {$roles} AND @Resource[Microsoft.Authorization/roleAssignments:PrincipalType] ForAnyOfAnyValues:StringEqualsIgnoreCase {'ServicePrincipal'}))"
$shape = { param($c) $c -replace 'GuidEquals\s*\{[^}]*\}', 'GuidEquals {ids}' -replace '\s+', ' ' }
if ((& $shape $old.condition) -ne (& $shape $condition)) { throw 'The condition differs from the templates in more than the role ids. Stop and read it.' }
# 3. Show the difference, then change the condition in place: one write, and the assignment keeps its id
Write-Host "Role ids now:        $($current -join ', ')"
Write-Host "Role ids afterwards: $roles"
Write-Host "Added:               $foundryUser (Azure AI User, named Foundry User since the rename)"
if ((Read-Host 'Change the condition as shown? Type yes') -ne 'yes') { throw 'Stopped. Nothing was changed.' }
$old.condition = $condition
$json = $old | ConvertTo-Json -Depth 20 -Compress
# The JSON is an argument of the CLI: every quote of it is doubled, which reaches the CLI unchanged in Windows PowerShell 5.1 and in PowerShell 7 (the Legacy setting in az makes 7.3 and later pass it the same way)
az role assignment update --subscription $devSub --role-assignment ($json -replace '"', '""') --output none
if ($LASTEXITCODE -ne 0) { throw "The update failed (exit code $LASTEXITCODE). It is one write and nothing else was done, so the assignment is unchanged. Read it: $read" }
# 4. Read it back: exactly one assignment, the same one, and both lists hold the old role ids and the Foundry User role
$count = Get-Assignments 'length(@)'
if ($LASTEXITCODE -ne 0) { throw "Read back: the assignments could not be read (exit code $LASTEXITCODE). The update was made; read them: $read" }
if ("$count".Trim() -ne '1') { throw "Read back: the list says '$count' assignments, not one. The update was made; read them: $read" }
$text = Get-Assignments '[0]'
if ($LASTEXITCODE -ne 0) { throw "Read back: the assignment could not be read (exit code $LASTEXITCODE). The update was made; read it: $read" }
$new = $text | ConvertFrom-Json
$after = @([regex]::Matches($new.condition, 'GuidEquals\s*\{([^}]*)\}') | ForEach-Object { ($_.Groups[1].Value -split ',\s*' | Sort-Object) -join ',' })
$meant = ($roles -split ',\s*' | Sort-Object) -join ','
if ($new.id -ne $old.id -or $after.Count -ne 2 -or $after[0] -ne $meant -or $after[1] -ne $meant) { throw "Read back: the assignment is not as meant (the same id, and both lists of role ids hold the old ids and $foundryUser). Its lists are: $($after -join ' | '). Read it: $read" }
Write-Host "Read back: one assignment, with the same id, and both lists hold the old role ids and $foundryUser (Foundry User)."
```

**The order.** (1) The hand step above. (2) The action `what-if` (it now shows the Foundry resource too, once the usage recording has made the Application Insights component), and then the action `foundry`. (3) The action `cases`: it passes the project's address to the app only when the project is in Azure, so the app's settings `FOUNDRY_PROJECT_ENDPOINT` and `INVESTIGATE` (on when there is an address, off otherwise) change at that run and not before. On an estate where `cases` has never run, the order is `recording`, `cases`, then the hand step, `foundry` and `cases` again: the role goes to the cases app's own system-assigned identity, which the first run of `cases` makes with the app, and `foundry` refuses to run without it.

**What the action checks, and what it needs.** Before it deploys, `foundry` requires the Application Insights component of the usage recording and the cases app with its own system-assigned identity (the workflow reads the object id from the app), and that its parameter file carries that identity's object id: no role is ever given to a placeholder. It then reads the resource back from Azure with GET requests only, and fails the run unless public network access is Disabled, local authentication is off, project management is on, the resource and the project have identities, the project reports an endpoint and it is the address that the cases app is given, the private endpoint is approved, every model of `models.json` is deployed as it says with the guardrail (a list is read to its last page), the guardrail holds each of its sixteen filters, on and blocking (hate, sexual, violence and self-harm from the severity Medium, profanity, protected material, and the Prompt Shields: Jailbreak and Indirect Attack on the user input, Indirect Attack on tool results), and the project's connection to Application Insights is made with an identity. **Costs.** The Foundry resource and the project cost nothing while no agent runs. The private endpoint costs a few euros a month, like the others. No new resource provider is needed.

## Changed on 2026-11-06: the function apps move to system-assigned identities, step one

The owner prefers system-assigned managed identities. The two function apps, the cases app (`func-meternaut-cases-<digest>`) and the usage app (`func-meternaut-usage-<digest>`), therefore move from the user-assigned identities `id-meternaut-cases` and `id-meternaut-usage` to an identity of their own each. One user-assigned identity stays: `id-meternaut-console-auth`, which the function app's sign-in presents to Microsoft Entra in place of a client secret. Microsoft documents that secretless sign-in of an App Service app only with a user-assigned identity ([Configure Microsoft Entra authentication](https://learn.microsoft.com/azure/app-service/configure-authentication-provider-aad#use-a-managed-identity-instead-of-a-secret)). It holds no role, and that does not change.

An app that loses an identity before the new one has its rights stops working, so the move takes two steps. This section is step one, which is additive. Step two is a separate change: it moves the settings to the new identities and takes the old ones off the apps, and it is made only after the steps below are done and read back. The old identities themselves are removed later, by a person, and not by the workflow: `tools/access-requirements.py retire` finds the grants of an identity by its object id, so it has to run while the identity still exists, and the workflow's identity cannot see the grants outside the project's group that `retire` removes. The order is written down with step two.

**What step one changes.** The actions `recording` and `cases` do it with the deployment identity's existing rights, so nothing new is needed in Azure:

- Each function app gets a system-assigned identity next to its user-assigned ones.
- The cases app's system-assigned identity gets every role that `id-meternaut-cases` holds inside the project's resource group: *Azure Event Hubs Data Receiver* on the control hub, *Storage Blob Data Owner* on the three containers that the Functions hosts of the account share, *Storage Queue Data Contributor* and *Storage Table Data Contributor* on the storage account, and *Monitoring Metrics Publisher* on Application Insights. The usage app's gets what `id-meternaut-usage` holds: *Azure Event Hubs Data Receiver* on the three hubs, *Storage Blob Data Owner*, *Storage Queue Data Contributor* and *Storage Table Data Contributor* on the account, *Monitoring Metrics Publisher*, and the data role *Data Contributor* of the Cosmos DB account. They are the same roles on the same resources, so the condition of the deployment identity's role-assignment right ([above](#added-on-2026-11-04-for-the-usage-recording)) needs no change.
- The action `foundry` gives the cases app's system-assigned identity *Foundry User* on the project as well, once the app has one. The workflow reads its object id from the app (an app that has none yet is "none yet", and no role is given), so the order is `cases`, then `foundry`.
- No setting changes. Both apps keep running on their user-assigned identities: their settings, the deployment storage of the usage app and the function app's sign-in are as they were. The summaries of `recording` and `cases` print the object id of each system-assigned identity, and the templates return it (`usageSystemPrincipalId`, `casesSystemPrincipalId`).

A role assignment of a system-assigned identity is named after the app's resource id, because Bicep needs the name when the deployment starts and the identity's object id does not exist until the app does. An app that is deleted and made again gets a new object id, and its old assignments (they show as "Identity not found") have to be removed before the template makes new ones.

**What a person does between the steps** (the owner's session; each is outside the project's resource group or outside Azure, so the workflow's identity has no right to it and must not get one, [rules 18 and 24](../AGENTS.md)):

1. **The same reads outside the group, for the two system-assigned identities.** For the cases app: *Reader* and *Cost Management Reader* on each subscription that the Watch reads, or once at the tenant root management group above them, which makes the Watch read every subscription its identity can read ([below](#changed-on-2026-11-07-the-watch-reads-every-subscription-that-its-identity-can-read)) (R1 and R2; the key reader that this step once added is retired, W7). For the usage app: *Monitoring Reader* on the gateway's Application Insights and the custom role *Meternaut usage reader* on the central workspace (R4 and R5). [`tools/access-requirements.py`](../tools/access-requirements.py) reads each app from the project's group (`--cases-site` and `--usage-site` name them), takes its system-assigned identity, and checks and grants every line for it, next to the user-assigned identity while the app still runs as one. `check` reads what is there, `grant` is a dry run that prints the exact commands, and `grant --apply` makes them with that person's own sign-in:

   ```powershell

   python tools/access-requirements.py grant --project-subscription $devSub --project-group $hubGroup --cases-site $casesApp --usage-site $usageApp --gateway $gateway --gateway-insights $insights
   python tools/access-requirements.py grant --project-subscription $devSub --project-group $hubGroup --cases-site $casesApp --usage-site $usageApp --gateway $gateway --gateway-insights $insights --apply
   ```

   `$casesApp` and `$usageApp` are the names of the two apps in the project's group (`func-meternaut-cases-<digest>` and `func-meternaut-usage-<digest>`), `$gateway` and `$insights` the resource ids of the API Management instance and of its Application Insights component. `--estate` (once for each subscription or management group that the Watch reads; the project's subscription when it is left out), `--workspace` and `--only` are as they were. An app that has no system-assigned identity yet is reported as "cannot yet": run `cases` or `recording` first.
2. **The right to send letters, for the cases app's system-assigned identity.** [`tools/exchange-setup.py`](../tools/exchange-setup.py) makes the role *Application Mail.Send* for it, limited to the one shared mailbox, and proves that it may not send as another mailbox ([step 3 of the function app and approval loop section](#added-on-2026-11-05-for-the-function-app-and-the-approval-loop)). It needs two ids of the identity's service principal. The object id (`--identity-principal-id`) is `identity.principalId` of the app: the summary of the action `cases` prints it, and `az rest --method get --url "https://management.azure.com<resource id of the app>?api-version=2024-04-01" --query identity.principalId --output tsv` reads it. The application (client) id (`--identity-client-id`) is not on the app, and the deployment identity may not read the directory, so the owner's session reads it from Microsoft Entra: `az ad sp show --id <object id> --query appId --output tsv`.


## Changed on 2026-11-06: the Operator

Once the services of the project are private, the workflow can no longer publish code, start a run, read the telemetry or knock at the function app's front door from outside the network ([the decision record](../docs/proposals/07-private-by-default.md)). The Operator does those things from inside: a container group of Azure Container Instances that the workflow makes in a subnet of the project's network, with an identity of its own, lets run one script, reads the log of and deletes. Two new actions: `operator` deploys [`environment/operator/main.bicep`](operator/main.bicep) into the project's resource group, and `operator-probe` runs [`operator/probe.sh`](../operator/probe.sh) once in the Operator and prints what it finds. Two existing actions now use it: `recording-check` and `cases-run` run their check tool ([`tools/recording-check.py`](../tools/recording-check.py), [`tools/cases-check.py`](../tools/cases-check.py)) in the Operator with the generic script [`operator/run-tool.sh`](../operator/run-tool.sh), so that the control event is sent, and the telemetry is read, from inside the network. What `operator` makes, and nothing else:

- **The identity** `id-meternaut-operator`, user-assigned, attached to no app.
- **The subnet** `snet-ops`, delegated to `Microsoft.ContainerInstance/containerGroups`, with the network security group `nsg-meternaut-ops`. It is made once and then left alone ([rule 27](../AGENTS.md)): the landing zone's network manager puts a route table on it some minutes after, a container group gets its way out through that table, and the action waits for it (20 minutes at most; it waits for nothing when the endpoint subnet has no table either).

**What the deploy identity's rights already cover.** *Contributor* on the project's group is `*` less a short list of `Microsoft.Authorization` writes and a few other actions ([Learn](https://learn.microsoft.com/azure/role-based-access-control/built-in-roles/privileged#contributor), read on 2026-11-06), so it covers `Microsoft.ContainerInstance/containerGroups/*`, the right to join a subnet (`Microsoft.Network/virtualNetworks/subnets/join/action` on `snet-ops`) and the right to assign the identity to a group (`Microsoft.ManagedIdentity/userAssignedIdentities/assign/action` on `id-meternaut-operator`): the network and the identity are both in the project's group. function Get-Assignments { param($Query) az role assignment list --subscription $devSub --assignee-object-id $principal --scope $scope --role 'Role Based Access Control Administrator' --query $Query --output json }
```powershell
# 1. Read the assignment (there must be exactly one) and the role ids that its condition lists (the list for a write and the list for a delete must be the same)

if ($LASTEXITCODE -ne 0) { throw "The assignments could not be read (exit code $LASTEXITCODE). Nothing was changed. Read them: $read" }

$text = Get-Assignments '[0]'
if ($LASTEXITCODE -ne 0) { throw "The assignment could not be read (exit code $LASTEXITCODE). Nothing was changed. Read it: $read" }

$lists = @([regex]::Matches($old.condition, 'GuidEquals\s*\{([^}]*)\}') | ForEach-Object { ($_.Groups[1].Value -split ',\s*' | Sort-Object) -join ',' })
if ($lists.Count -ne 2 -or ($lists | Select-Object -Unique).Count -ne 1) { throw 'The condition is not the one that the templates expect (two lists of the same role ids). Stop and read it.' }
$current = $lists[0] -split ','
if ($current -contains $reader) { throw 'The condition lists the Reader role already: nothing to do.' }
# 2. Add the one id, and change nothing else of the condition

$condition = "((!(ActionMatches{'Microsoft.Authorization/roleAssignments/write'})) OR (@Request[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {$roles} AND @Request[Microsoft.Authorization/roleAssignments:PrincipalType] ForAnyOfAnyValues:StringEqualsIgnoreCase {'ServicePrincipal'})) AND ((!(ActionMatches{'Microsoft.Authorization/roleAssignments/delete'})) OR (@Resource[Microsoft.Authorization/roleAssignments:RoleDefinitionId] ForAnyOfAnyValues:GuidEquals {$roles} AND @Resource[Microsoft.Authorization/roleAssignments:PrincipalType] ForAnyOfAnyValues:StringEqualsIgnoreCase {'ServicePrincipal'}))"
$shape = { param($c) $c -replace 'GuidEquals\s*\{[^}]*\}', 'GuidEquals {ids}' -replace '\s+', ' ' }
if ((& $shape $old.condition) -ne (& $shape $condition)) { throw 'The condition differs from the templates in more than the role ids. Stop and read it.' }
# 3. Show the difference, then change the condition in place: one write, and the assignment keeps its id
Write-Host "Role ids now:        $($current -join ', ')"
Write-Host "Role ids afterwards: $roles"
Write-Host "Added:               $reader (Reader)"
if ((Read-Host 'Change the condition as shown? Type yes') -ne 'yes') { throw 'Stopped. Nothing was changed.' }
$old.condition = $condition
$json = $old | ConvertTo-Json -Depth 20 -Compress

if ($LASTEXITCODE -ne 0) { throw "The update failed (exit code $LASTEXITCODE). It is one write and nothing else was done, so the assignment is unchanged. Read it: $read" }
# 4. Read it back: exactly one assignment, the same one, and both lists hold the old role ids and the Reader role
$count = Get-Assignments 'length(@)'
if ($LASTEXITCODE -ne 0) { throw "Read back: the assignments could not be read (exit code $LASTEXITCODE). The update was made; read them: $read" }
if ("$count".Trim() -ne '1') { throw "Read back: the list says '$count' assignments, not one. The update was made; read them: $read" }
$text = Get-Assignments '[0]'
if ($LASTEXITCODE -ne 0) { throw "Read back: the assignment could not be read (exit code $LASTEXITCODE). The update was made; read it: $read" }
$new = $text | ConvertFrom-Json
$after = @([regex]::Matches($new.condition, 'GuidEquals\s*\{([^}]*)\}') | ForEach-Object { ($_.Groups[1].Value -split ',\s*' | Sort-Object) -join ',' })

Write-Host "Read back: one assignment, with the same id, and both lists hold the old role ids and $reader (Reader)."
```

## Changed on 2026-11-08: the control message goes through a Storage queue (built, not deployed)

The owner ordered it on 2026-11-08, about a cost tool that pays for a channel it hardly uses ("Old crap needs to be removed. Why ask? Of course."). The biggest idle cost line of Meternaut was one Event Hubs namespace that served one hub, `cases-control`. That hub carried one small JSON message now and then, to start one Watch. The meters:

| Meter | US dollars | A month of 730 hours |
|---|---|---|
| Event Hubs Standard, one throughput unit (Sweden Central) | 0.03 an hour | 21.9 |
| The namespace's private endpoint | 0.01 an hour | 7.3 |
| **Together** | | **29.2** |

Both prices were read on 2026-11-08 from the Azure retail price list (`https://prices.azure.com/api/retail/prices`): the meter "Standard Throughput Unit" of Event Hubs Standard in `swedencentral`, and the meter "Standard Private Endpoint" of Virtual Network Private Link (region Global). The message now goes through a queue in the storage account that exists already, and that already has its private endpoint for queues. A Storage queue has no hourly charge: it is billed for what it stores and for each operation. The amount was not read from the price list. One message a day and about one read a minute of an idle trigger are small, and the account exists whatever the queue does.

**What changed.**

- **The app.** The cases app has a Storage queue trigger on the queue `cases-control` instead of the Event Hubs trigger ([`function_app.py`](../src/case-functions/function_app.py)). It uses the host storage account of the app (the connection `AzureWebJobsStorage`), whose settings are identity-based in this app: `AzureWebJobsStorage__credential`, `__blobServiceUri`, `__queueServiceUri` and `__tableServiceUri`. No connection string, no key, no SAS. The setting `CASES_CONTROL_QUEUE_NAME` (it was `EVENTHUB_CASES_CONTROL_NAME`) holds the queue's name, and the app still refuses to start the loop without it. The checks of the message are the same: a known job, a valid request id, and not older than 15 minutes, which is now measured from the time that the queue says that the message was inserted. `host.json` takes one message at a time (as the one partition of the hub did) and says five tries.
- **The cases template** ([`cases/main.bicep`](cases/main.bicep)) makes the queue in the existing account. It no longer makes the hub, its consumer group, the *Azure Event Hubs Data Receiver* role or any `EventHubConnection__*` setting. The cases app already holds *Storage Queue Data Contributor* on the whole account, because its host needs it, and that covers the trigger and the poison queue: no role is added for it.
- **The Operator** ([`operator/main.bicep`](operator/main.bicep)) is given *Storage Queue Data Contributor* on the one queue (the scope of the assignment is the queue and nothing else), in place of *Azure Event Hubs Data Sender* on the hub. That is wider than a sender needs: it can also read, delete and clear messages. The narrower *Storage Queue Data Message Sender* is not among the roles in the condition of the deploy identity's role-assignment right, and adding it would be one more hand step for the owner. The queue holds only job names and request ids.
- **The sender.** [`tools/cases-check.py`](../tools/cases-check.py) puts one message in the queue with the Operator's identity: a POST to `https://<storage account>.queue.core.windows.net/cases-control/messages` with a bearer token for `https://storage.azure.com/`, the header `x-ms-version` (2026-04-06) and a body `<QueueMessage><MessageText>…</MessageText></QueueMessage>` in which the text is the base64 of the JSON, because the host decodes base64. It expects 201. It runs inside the network, through the private endpoint for queues that exists already, and the action `cases-run` passes the storage account's name (`--storage-account`) in place of the namespace. The sender sets a time to live of one hour: the app refuses a message older than 15 minutes anyway, and the queue's own default would be seven days. Every refusal that the tool had is kept, among them that it runs only in a GitHub Actions run.
- **The base** ([`base/main.bicep`](base/main.bicep)) no longer declares the Event Hubs namespace, its private endpoint or the container `azure-webjobs-eventhub`, and the parameter builder, the workflow and the tests no longer name the namespace, except to delete it (below). A template that stops declaring a resource does not delete it, so the new action `retire-event-hubs` does.

**What the queue is.** The trigger polls. When the queue is empty the host waits longer between two reads, up to one minute by default, so a message can wait about a minute before a Watch starts. Delivery is at least once: the same message can reach the app twice. The Watch is read only and capped, and the check of the message's age keeps an old message from starting one late. When a try fails, the host tries again, and after five tries in all (the first included) it moves the message to the queue `cases-control-poison` of the same account, where a person can read it. A refusal of the app (an unknown job, a bad request id, a message that is too old) is an answer: the message is consumed and the History says why. No key is involved at any point. Sources: [Azure Queue storage trigger for Azure Functions](https://learn.microsoft.com/azure/azure-functions/functions-bindings-storage-queue-trigger), [Put Message](https://learn.microsoft.com/rest/api/storageservices/put-message) and [Authorize with Microsoft Entra ID](https://learn.microsoft.com/rest/api/storageservices/authorize-with-azure-active-directory).

**The new action `retire-event-hubs`** needs no input. It may run only after `cases-run` has passed, because it removes the old channel, and it refuses to delete anything while the queue `cases-control` is not there. It refuses to run unless the resource group is the workflow's `ENV_RESOURCE_GROUP` and the subscription is its `ENV_SUBSCRIPTION_ID`. It deletes nothing but this list, each by its exact name (built from the digest of the subscription and the group), in this order. For each one it reads the resource, deletes it when it is there, reads again until it is gone, and prints one line: deleted, or was not there. A second run is safe, and an estate that never had a namespace passes with "was not there" three times. The code is [`tools/retire-old.py`](../tools/retire-old.py) with its list `event-hubs`: the action `retire-old` is the same tool with its other list.

1. the namespace's private endpoint `pe-evhns-meternaut-<digest>`
2. the Event Hubs namespace `evhns-meternaut-<digest>`, which takes its hub `cases-control`, that hub's consumer group `casesControl` and whatever else is in it with it (no purge is needed for Event Hubs)
3. the container `azure-webjobs-eventhub` in the storage account, where the Functions host kept the checkpoints of the Event Hubs trigger

The role assignments that were scoped to the hub alone (the cases app's *Azure Event Hubs Data Receiver*, the Operator's *Azure Event Hubs Data Sender*) are not deleted by the action. They apply to nothing once the hub is gone. Whether Azure also removes their records was not checked.

**What a person does, in order.** Each Hub action is on the owner's word (one yes to the whole list is enough).

1. Merge. Nothing changes in Azure by the merge.
2. The Hub action `cases`: makes the queue, deploys the new trigger and the settings. The app then no longer reads the namespace: the template does not write the old Event Hubs settings any more.

5. Only then the Hub action `retire-event-hubs`.

`what-if` shows what `retire-event-hubs` would delete, by reading the three items by name, and says that each is not there once they are gone, or on an estate that never had them. No other step of any action reads the namespace, so `what-if` and the checks before each deploy pass before the namespace is gone, after it, and on an estate that never had one. The action `base` does not have to run for this change.

**Not checked.** Nothing of this ran in Azure when it was written.

The documentation says that identity-based connections are supported for this trigger. It was not tried. If `cases-run` shows no Watch, that is the first thing to look at.

CI runs for the head of a push unless its message says `[skip ci]`, which [rule 35](../AGENTS.md) asks for on a commit that is pushed before its branch is finished: a head with that marker has no run to find, and the Hub refuses it until a commit without the marker is on top of it and has passed. For that step the workflow has one more permission, `actions: read` (the list of the runs of one workflow, read with the run's own token), and nothing else of it changes: it starts only by hand, only for the owner, only on `main`, as one job, with OpenID Connect and no secret (the lint and the guard in CI pin all of that). Also left to CI, because it ran for the same commit: the workflow lint, the Bicep lint and the selftest of the drift tool. The Hub still compiles each template to a file, because the builder of the parameter files checks every file against the template that it is for. What a person does: push, let CI finish (about two minutes), then run the Hub. The way back is to put the two test commands back as the first steps of the job, which needs the owner's word.

**The order.** (1) Push once and merge; the CI run of the merge commit on `main` has to pass, because every Hub run asks for it. Nothing changes in Azure. (2) G1 and G2, on the owner's yes. (3) `base`, which turns the OpenTelemetry ingestion on; the platform reports the endpoints about ten minutes later. Taking the model side away is meant to be a workflow's job (an action `remove`). It is not built: this page said that `remove` would exist before the first `model-side` run, and it did not, so it is the next change, and the changelog records that the promise was not kept. Nothing of Meternaut is on the owner's API Management instance any more, and no action can put it there; what was added is removed by a person ([part 2](#changed-on-2026-11-07-the-undo-of-what-meternaut-added-to-the-owners-api-management-instance-part-2-the-hub-no-longer-touches-it)). Taking the identity and the settings away is the other half of the bootstrap, so it is a manual step of the same kind, and it needs the owner's own plain-word yes, given separately from the one that created the identity: delete the role assignments (`az role assignment delete --assignee $principal --scope <each scope>`), the two resource groups (with the second, the identity and its credential), and the secrets and variables (`gh secret delete`, `gh variable delete`).

A model account that was deleted is soft-deleted and keeps its name for a while. The workflow restores it by itself on the next `model-side`, so nothing has to be purged.
