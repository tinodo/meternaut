# The deploy repository

The Hub, [`deploy-hub.yml`](../../.github/workflows/deploy-hub.yml), prints names and ids of the owner's estate, and a public repository's logs are public ([rule 37](../../AGENTS.md)). So a small **private** repository of the owner, the deploy repository, calls the Hub as a reusable workflow. Its logs, its variables, its three secrets, the OpenID Connect credential that trusts it and the minutes of its runs are the private repository's. The public repository still holds no secret, no variable and no credential, and no credential trusts it.

The deploy repository holds one workflow, [`hub.yml.template`](hub.yml.template), and settings. It pins the Hub to one full commit of the public repository, so changing the code that deploys is a commit of the owner in the private repository. Nothing in this folder has run: no repository, secret, variable or credential exists yet, and nobody has called the Hub this way. A part is done when it has run ([rule 32](../../AGENTS.md)).

**Not verified, and why it costs nothing.**

- *Can a workflow that is disabled in its own repository be called from another?* The page on disabling says only that it is not triggered there. A user report (community discussion 60389, 2023, unanswered by GitHub) says the call still runs. If the first call is refused for this, nothing was changed; only the owner may then enable `deploy-hub.yml` in the public repository ([rule 37](../../AGENTS.md)). That is harmless while no credential trusts the public repository and `azure/login` is not an allowed action there.
- *Can the token of a private repository read the list of runs of a public one?* The list of a public repository needs no permission, but it was not tried. The Hub's check of CI stops the run with GitHub's own message when it cannot read, and nothing is changed.
- *Does the first step of a run print its `env:` before it can mask?* The runner prints each step's `env:` block, and the first step's head comes before any mask. This is how the runner behaves, not a documented promise; the log is private either way.

## What is done once, in order

Nothing below is done by an agent on its own. Each step that creates a repository, a secret, a variable or a credential needs the owner's plain yes ([rules 18 and 37](../../AGENTS.md)).

| # | Step | Who | What it needs from the owner |
|---|---|---|---|
| 1 | Create a **private** repository, with `main` as its default branch, and no other writer than the owner. | The owner | The name. Nothing from the old estate is copied into it but what steps 4 and 5 name. |
| 2 | In *Settings, Actions, General*: **Allow the owner, and select non-owner, actions and reusable workflows**, with *Allow actions created by GitHub* and one specified action, `azure/login@a641126d1b8aa4d1fa005f4f92df94a3a4c4c906`; turn on *Require actions to be pinned to a full-length commit SHA*; the token's default permission is read; a workflow may not approve pull requests. | The owner | A yes. The Hub's own steps use `actions/checkout`, `actions/setup-python` and `azure/login` and no other action. |
| 3 | Copy `hub.yml.template` to `.github/workflows/hub.yml`, replace the placeholder after the `@` with the full commit of `main` in the public repository that is to deploy, and commit it to `main`. Take a commit whose `checks` run passed: the Hub asks GitHub and refuses any other. | The owner or an agent he names | The commit, which he reads in the public repository. |
| 4 | Set the three secrets `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID` and the variables `ENV_RESOURCE_GROUP`, `ENV_LOCATION`, `ENV_VNET_PREFIX`, `ENV_PE_SUBNET_PREFIX`, `ENV_DNS_SERVERS`, `ENV_OWNER`, `ENV_ALERT_EMAILS` and `ENV_BUDGET_AMOUNT`, as in [BOOTSTRAP](../BOOTSTRAP.md) step 5, but in **this** repository (`--repo <owner>/<deploy-repository>`). The workflow also reads `CONSOLE_APP_CLIENT_ID`, `CONSOLE_PEOPLE`, `CONSOLE_HOST_NAME`, `MAIL_SENDER`, `DRIFT_ACCEPTED_EXEMPTIONS`, `DRIFT_ACCEPTED_DENY` and `TEAMS_BOT_ENABLED`; set the ones that the parts he wants to run need, as their sections in BOOTSTRAP say. | The owner | The values, from the old repository's settings or from Azure. A value is never typed into a chat, a commit or a pull request. |
| 5 | Make the federated credential for this repository's subject on the existing deploy identity (below). The identity and its roles stay as they are. | A person with the right on the identity | A yes. The old credential `github-main`, for the earlier repository, is removed by a person when he says. |
| 6 | The first run is the action `what-if`, started by the owner from *Actions, Hub, Run workflow*. It reads and changes nothing. Check that it started (it was not refused for a disabled workflow or a policy), that every step up to the sign-in passed, that the sign-in worked and that the log shows `***` where an id or a name of the estate would be. | The owner | His read of the log. |
| 7 | Every later run follows [rule 18](../../AGENTS.md): the agent says what it changes, what it costs a month and how long it takes, and the owner says yes in words. A newer Hub is a new commit after the `@` in `hub.yml`. | The owner | His yes for each run that changes something. |

The credential, with the same `$devSub`, `$idGroup` and `$uami` as the commands of BOOTSTRAP:

```powershell
$deployRepo = '<owner>/<deploy-repository>'
$prefix = (gh api "repos/$deployRepo/actions/oidc/customization/sub" | ConvertFrom-Json).sub_claim_prefix
az identity federated-credential create --subscription $devSub --resource-group $idGroup --identity-name $uami --name github-deploy-repository-main `
  --issuer https://token.actions.githubusercontent.com --subject "${prefix}:ref:refs/heads/main" --audiences api://AzureADTokenExchange
```

Read the prefix back before the first run: it has to name the owner's and the repository's numeric ids (`repo:<owner>@<id>/<repository>@<id>`), or Azure answers AADSTS700213.

## What it costs, and what it does not stop

- **Minutes.** A run of the deploy repository draws on the owner's private-repository allowance, which is a money amount (GitHub Free $12, Pro $18 a month, about 2,000 or 3,000 Linux minutes). The Hub no longer runs the unit tests ([rule 35](../../AGENTS.md)), and those were about five of its eight average minutes; `cases` takes 10 to 40. The checks of the public repository stay free.
- **The credential trusts a repository, not a workflow.** It lets any run of the deploy repository on `main` sign in as the deploy identity, whatever it runs. The lock is that the repository has one workflow, one writer and a pinned commit. A second workflow or a second writer would widen it.
- **The approval is a rule of process.** A required reviewer would be its technical form, and a private repository on Free, Pro or Team cannot have one. The guard `github.actor == 'tinodo'` cannot tell the owner's click from a run that an agent starts with his token.
- **A masked log is the second line.** The Hub asks the runner to mask the subscription, tenant and client ids, the resource group, the address ranges, the owner's addresses and the console's host name, as they are and in lower and upper case. It cannot mask what it has no value for: the names that tools print (a storage account, an app, a gateway), the object ids of identities and the text of Azure's own answers. Those are in a private log, which is the first line.
- **`drift.yml` is not called.** It stays disabled in the public repository; the Hub's own action `drift-check` reads the same things with the deploy identity.
- **Run numbers start again at 1.** The action `plant` names its waste after the run number (`r<number>`), so a name can meet a planting of the earlier repository. Before planting, look at what already carries that name.

## The way back

Delete the credential `github-deploy-repository-main` and the deploy repository. The public repository is not touched, and its Hub workflow stays disabled there.
