# Making the repository public: what was checked, found and done — a decision record

**Status: ordered by the owner on 2026-11-10 and done the same day.** The repository is public, under a history that was read for secrets and rewritten once. The earlier history is a private archive. What is guarded, what was found and what is not proved are on this page.

## The owner's words

"You can continue. I also want you to make the GitHub project PUBLIC. That way, it doesn't cost build minutes. Make sure that can be done safely; check for credentials, branch control, etc. I want the project to be public. Continue your work, make the project securely public and continue using GitHub after that."

Until then the rule was his order of 2026-10-31 that the repository stays closed until he says to switch it ([AGENTS.md](../../AGENTS.md), rules 1 and 37).

## What was decided, and why the old repository was not simply switched

A repository that is switched from private to public shows everything it has ever held: every branch, every commit on every branch, the pull-request refs, the texts of the pull requests and their comments, and the logs of the workflow runs. GitHub does not let an owner erase the pull-request refs or the run logs of a repository that exists (they go only with the repository), and the history held things that must not be public (below). So the history was copied, scrubbed and published as a **new** repository, and the old one was renamed and kept private:

- **This repository**, `tinodo/meternaut`: the branch `main` and the 17 tags (the editions of the documents), with the same graph of 481 commits, the same files and the same dates. Only text that must not be public was replaced, in file contents, commit messages and the author lines; every commit has a new id ([the table of old and new ids](../history/commit-ids-before-2026-11-10.md)). The last commit of the old history and the commit that stands for it here have the same files; they differ only in the text that the rules replace (54 files).
- **The archive**, `tinodo/meternaut-archive` (private, Actions off): the old history as it was, the 42 branches, the 109 pull requests (three of them open), the 469 workflow runs and the pre-publication reports. It is the owner's, and nothing is deleted from it.

## How it was checked

1. **Every blob of every ref** of the old repository (the branches, the 17 tags and the pull-request refs; about 6,500 objects, 3,657 of them text), every commit message and tag message, the names of all files that ever existed, and the text of the 109 pull requests with their comments and reviews were read by a scanner written for it (standard library only): private keys, GitHub, AWS and Slack tokens, JSON Web Tokens, bearer tokens, connection strings, storage and Service Bus keys, signed addresses, URLs with a password, high-entropy strings, e-mail addresses, IP addresses, host names, GUIDs, resource-group names, personal names and internal words. **No real credential was found:** every hit was a short invented value of a test.
2. **Every GUID** (2,055 different ones) was sorted: public (built-in roles, first-party applications, Azure meter ids), invented (patterned), and the rest, which were read one by one. The identifiers of the owner's live Azure estate (the subscriptions, the tenant, every resource, role assignment, identity and application, read through Azure Resource Graph and the directory) were looked up in every revision.
3. **Names**: of the owner's other projects ([AGENTS.md](../../AGENTS.md) rule 31), of the owner's estate, and an internal program name of his employer.
4. **An independent review**: an agent that had not written any of it read the candidate history with the rules of a security review, and its verdict was *safe after the listed fixes*. Its findings, and the ones that the owner-side checks added, are in the next section.
5. **The result was checked again** after the fixes: the new history has the same graph (481 commits, 134 merges, 17 tags) and its last commit holds exactly the scrubbed files of the old one; no revision matches any of the patterns above (counted over every blob, every message and every author line, also with the pieces of strings that are joined in code put together); the scanner finds the same categories as before and none of the replaced ones.

## How the new repository is guarded

| Setting | Value |
|---|---|
| Content pushed | `main` and the 17 tags, and nothing else (read back with `git ls-remote` before the repository was switched) |
| Rulesets | `main`: no deletion, no force push, a pull request is required (no approval is demanded: there is one maintainer), the check `checks` has to pass, merge commit or squash (no rebase: the documents quote commit ids). Tags: no deletion and no move. No one may bypass them |
| Actions | Only GitHub's own actions (and, since 2026-11-11, `azure/login`) may run, and every action has to be pinned to a full commit; the token of a run is read-only; a workflow cannot approve a pull request; a run from a fork waits for the owner's approval, for every outside contributor, and gets no secret; logs and artifacts are kept 30 days |
| Workflows | `checks.yml` runs on every pull request and every push to `main`; `deploy-hub.yml` is disabled until the owner has made its environment and says yes (it then starts by hand only, from `main`); `drift.yml` stays disabled |
| Secrets and variables | None at repository level. Since 2026-11-11 the environment `hub`, which takes a deployment from `main` alone, is to hold the identifiers of the estate as secrets and plain configuration as variables ([BOOTSTRAP](../../environment/BOOTSTRAP.md)) |
| Security features | Secret scanning with push protection, Dependabot alerts and security updates (and the version updates of [`dependabot.yml`](../../.github/dependabot.yml): pip, npm and the actions), code scanning (CodeQL, default setup: the workflows, the Python and the JavaScript), private vulnerability reporting ([SECURITY.md](../../SECURITY.md)) |
| Features | Issues on; the wiki, projects, discussions and Pages are off. The branch of a merged pull request is deleted. No collaborator, deploy key or webhook |
| Azure | No federated credential trusts this repository yet. The one that will trusts the subject of the environment `hub` and nothing else (no branch, no pull request), and the Hub workflow is disabled until the owner says yes ([rule 18](../../AGENTS.md)) |

**Changed on 2026-11-11.** The owner ordered that the Hub run in this repository, directly, in the environment `hub` (the owner rejected a plan of the same day, in which a private repository would call it: [proposal 16](16-the-hub-on-the-owners-machine.md#what-replaced-it)). The rows above for the actions, the workflows, the secrets and variables and Azure say what that changes. The read-back below is of 2026-11-10 and stays as it was.

## A second review, of the public repository itself

After the switch, a second independent review (a read-only security review by an agent that had not written any of it, from 21:30) read an unauthenticated clone of the public repository, every revision of it with the pull-request refs, and its settings as GitHub reports them. Its verdict was *safe after the listed fixes*: no credential, no identifier of the owner's estate and no path from outside to a secret or to Azure, in any revision or setting, and nothing that asked for the repository to be made private again. It found one medium and three low points:

| What was found | What was done |
|---|---|
| **Medium.** `tools/hub-local.py` (deleted on 2026-11-11) ran the Hub's steps with the owner's own sign-in, and the tools they call can be changed by a pull request: a change of a stranger that was merged unread would run with his rights, and the controls against it were only rules of process | The tool refuses every run, one that only reads too, until a person says, with `--reviewed` and the commit, that everything but the folder `docs/` and a few plain files that changed since the commit last read was read ([the guards](16-the-hub-on-the-owners-machine.md#the-guards)). The reviewer looked at three versions of that gate and found a way round each (a path in another case, code outside four folders, a read-only action, a record that a merge could write; then a new file in the script's folder that shadows a module of the standard library, the rules of the agents counted as documents, a file named like the recorded commit, a link; then a `git.exe` in the folder that the tool is started from, a compiled file planted next to a source, and agent files under `docs/`); the fourth version, which is merged, closes them, and the reviewer confirmed that, with one low point: the names of the agent files are a list, so `AGENT.md`, `QWEN.md` and `.cursorrules` stayed documents under `docs/` (every path with a segment that starts with a dot is code now, and the two names are on the list). What it cannot do is guard `tools/hub-local.py` and `tools/hubguard.py` themselves, which run before any gate can look at them: their diff is the first thing to read, and whoever gives the word may not have read anything. The required check `checks` is pinned to the GitHub Actions app, so no other status can stand for it; [rule 37](../../AGENTS.md) (e) says that an agent reads the diff before it merges and treats the text of a pull request or an issue as untrusted. **The tool was deleted on 2026-11-11**: the owner ordered it, and the Hub is a GitHub workflow again ([proposal 16](16-the-hub-on-the-owners-machine.md)), so this finding ended with it |
| Low. [SECURITY.md](../../SECURITY.md) said that code scanning reads the Python | It read the workflows only then: GitHub had not reported any language of the new repository an hour after the push. It reported them two and a half hours after, and code scanning now reads the Python and the JavaScript too, as the sentence says |
| Low. The lock file of the npm packages is not committed, so what they depend on is not pinned | A lock file made on the maintainer's machine would name that machine's package feed. The install is documented with `--ignore-scripts`; a lock file made against the public registry is left to the owner |
| Low. The two Azure workflows would print values of the estate if they were enabled, and they ask for an OpenID Connect token, so "a read-only token" was not literally true of them | The texts say what is true: they are disabled; enabled, they would fail at the start, because `azure/login` is not an allowed action, and would find no variable to print; the token that they ask for can be used by nothing. Since 2026-11-11 this holds for `drift.yml` only: the Hub's identifiers are secrets of an environment, which GitHub masks, its steps mask what they read, and `azure/login` is an allowed action for it ([rule 18](../../AGENTS.md)) |

Of the fourteen items of the first review the reviewer found eleven closed and three partly: the workflows that print values of the estate are disabled and not removed, the Azure side of the credential could not be read by the reviewer, and the lock file (above).

## What is left to the owner, and what is not proved

- **The employer.** The copyright holder in [`LICENSE`](../../LICENSE) is the owner personally, and nothing in the repository shows that his employer has approved the publication of a project about Azure under his name, or of its name and its text. The owner decides whether a review (an open-source office) is needed; no agent can say.
- **What the documents still say about the tenant.** The changelog and the proposals describe how the owner's tenant governs resources (a tag that opts out of the automatic changes of its Modify policies, a policy waiver on one subscription, the right *Reader* at the root of the tenant's groups). The tag is discussed in public repositories of Microsoft's field teams, and none of it is a secret or an identifier, but it is the owner's estate. He may want it reworded; the rules that rewrote the history can do that again.
- **A search by patterns is not a proof.** A secret in a form that no pattern knows would not have been found. The second net is GitHub's secret scanning with push protection, which is on, and the hashes of the estate's identifiers that a test checks on every change.
- **The archive** is private and holds everything that was removed. It has the old identity's credential, which trusts it, and Actions are off in it. A person removes the credential and the identity when the owner says ([rule 18](../../AGENTS.md)).
- **The fifteen dismissed alerts of code scanning** are tests, an archived tool, a pattern for Mermaid arrows, a class of control characters on purpose, and the Hub's console, which masks the owner's ids before it prints them. The reason is written on each alert, and a person can reopen any of them (Security, Code scanning, Closed); if the owner reads one differently, the alert is the place to say so.
- **The first run of the checks on GitHub** had not run since 2026-11-08, on the owner's machine only. It failed on 2026-11-10 in five tests of the Hub's local runner (they pin Windows behaviour, and the stand-ins were not executable there); the fix is pull request 4, and the checks have passed since.
