# Access and onboarding — the requirements

**Status: written on 2026-11-05, after the first cases ran on the real estate; changed on 2026-11-07. Meternaut holds no write right: every grant below only reads, and a change to Azure is made with the token of the person who approves it. The installer in this page is built; the pipeline is not. On 2026-11-07 the owner ordered the undo of what Meternaut added to his API Management instance: the cases app reads no key any more, so the custom role that read one and its grant (R3) are retired (W7), and nothing of the cases app depends on that instance. R4 and R5, the usage app's reads of the gateway's telemetry, stay for now. The same day the owner ordered that the Watch watch the entire estate: it reads every subscription that its own identity can read, and a person gave R1 and R2 once at the tenant root management group (2 of 2 present; the Watch then read 10 subscriptions: [the Watch's estate](#the-watch-reads-every-subscription-that-its-identity-can-read)). Since the second part of the undo, nothing in the repository (workflow, templates or tools) can create, change or read an object on that instance: the Hub's actions that made objects there are gone, and the deploy identity's own custom role there, which no action uses, is retired too (W8; [the bootstrap page](../../environment/BOOTSTRAP.md#the-custom-role-no-longer-used)).** This page says what Meternaut needs granted outside its own resource group, who must grant it, why a pipeline cannot make the first grant on its own, and what an installer or a pipeline has to do. The design's [onboarding steps](../design/09-delivery-and-operations.md#9-onboarding-an-estate) describe the finished system; this page is what is true and built today. The changelog says what was done and checked.

## The problem

- The deployment workflow's identity may change only the project's own resource group. It holds no right in the subscriptions that Meternaut reads or in the gateway's, and it must not get one ([rule 18](../../AGENTS.md)).
- The workflow makes the two function apps, the usage recording's and the first cases', and the identities that they run as. Those identities need rights in other places, and only a person who may assign roles there can give them.
- Until now a person did that by hand, once for each identity, on the owner's written word, and reported it at once. The commands are in [the bootstrap page](../../environment/BOOTSTRAP.md).
- That does not scale to a second subscription, a second estate or another organisation. So the grants are written down as data, in [`environment/access-requirements.json`](../../environment/access-requirements.json), and a tool reads them: [`tools/access-requirements.py`](../../tools/access-requirements.py).

## What must be granted

One line is one role of one identity at one place. An identity here is what a function app runs as, and the **Identity** column names the holder of the line: the system-assigned identity of the app, which the tool reads from the app (`--cases-site` and `--usage-site` name the two apps). While an app moves from a user-assigned identity, the file lists both, so that the app is never without access ([below](#the-apps-run-as-system-assigned-identities)). The table is printed by `python tools/access-requirements.py markdown`, and a test fails when this page and the file differ. Every line only reads: Meternaut holds no write right, and [the next section](#a-change-is-made-as-the-person-who-approves-it) says how a change is made.

What the roles allow, read from Azure on 2026-11-05:

- **Reader** is `*/read` and nothing else. **Cost Management Reader** reads cost, billing periods, Advisor recommendations and management groups, and, as the built-in role has it, holds `Microsoft.Support/*` (support requests). **Monitoring Reader** is `*/read`, a workspace search and `Microsoft.Support/*`.
- **The one custom role** holds three actions (usage reader, all reads of one table) and is defined for one resource group only. The key reader that an earlier version had is retired ([below](#what-earlier-versions-granted-and-is-retired)); the file has no role that reads a key.
- **Which call needs which grant.** The Watch and the timer's checks make 21 kinds of call outside the app's own store, its mailbox, the sign-in and its own Foundry project, and the file names all 21. The Watch makes nineteen: the list of the subscriptions that its identity can read, Resource Graph queries, Advisor reads, management lock lists, the platform metrics and their definitions, the pricing settings of the Defender plans, and, for the read-only tools of the investigator ([the investigation toolbox](12-investigation-toolbox.md)), the settings, tables, saved searches and Sentinel rules of a workspace for logs, the query API of a workspace, the workbooks of a subscription, diagnostic settings, the deployments of an AI services account and the Activity Log need R1; the Cost Management query and the two purchase recommendations (savings plans and reservations) need R2. The timer's checks add two reads in the project's own resource group, of a managed disk and of a public IP address, to see that a deleted resource is gone (its list holds the lock read too, the same kind as the Watch's). They need R1, so R1 has to cover the project's subscription; it does when the estate is the project's subscription, which is the installer's default, and at the tenant root management group, which is above it. The calls to the app's own Foundry project need no line of this file: its agents and conversations, and the chat completions of the Detective and the Skeptic (the model deployments of that project, called with the app's own identity and no key). The app's identity holds *Foundry User* on that project, which the template assigns inside the project's own resource group ([the Foundry agents](06-foundry-agents.md)). Since 2026-11-07 no model call goes through the owner's API Management instance, and the app reads no key.
- **The calls are checked against the file.** Tests compare the Watch's list of allowed calls and the timer's list with the file, in both directions, so a new call cannot ship without a requirement and the file lists no call that the app does not make. Two further checks fail if the Watch's list holds anything but reads and queries, or if the timer's list holds anything but reads.
- **No write, and no key.** The file holds no role that changes Azure and no identity that does. A test fails if any custom role gets an action that is not a read, a wildcard, a write or a delete, if a role is marked as one that changes Azure, or if the file lists an identity other than the two that read. Since 2026-11-07 the file lists no action that reads a key either. What the apps write in their own resource group (their own store, with the roles that the deployment gives them) and the letters that they send as the one shared mailbox are not rights over anything of the customer's, and are not in this file.

## The apps run as system-assigned identities

Each function app runs as its own system-assigned managed identity: an identity that is made with its app, ends with it, and that nothing else can use. It replaces the user-assigned identities that the apps ran as before (`id-meternaut-cases`, `id-meternaut-usage`), whose grants are retired [below](#what-earlier-versions-granted-and-is-retired). One user-assigned identity stays, `id-meternaut-console-auth`: it is only the subject of the console's federated credential ([below](#a-change-is-made-as-the-person-who-approves-it)) and holds no role. The apps' code asks the platform for a token without a client id (the app setting `AZURE_CLIENT_ID` is not set), and the platform answers for the system-assigned identity ([Learn](https://learn.microsoft.com/azure/app-service/overview-managed-identity#rest-endpoint-reference)); a client id in that setting would name a user-assigned identity instead. The move is made in an order that never leaves an app without access, and a later change of identity follows the same order:

1. **Add.** The app gets a system-assigned identity next to its user-assigned one, and the same roles are granted to the new identity. No app setting changes, so the app still runs as the user-assigned identity. While the move lasts, the file lists both as holders of every line, and `check` and `grant` print one line for each holder. A grant that is not an Azure role is made for the new identity too: the Exchange role that lets the cases app send letters ([`tools/exchange-setup.py`](../../tools/exchange-setup.py)).
2. **Flip.** Only when `check` shows every line present for the system-assigned identities, and the Exchange role as well, does the client id leave the app's settings, so that the app uses its system-assigned identity. The tool cannot see which identity an app runs as: that the flip has worked is a person's check, made with the app's own answers.
3. **Remove.** After the flip nothing needs the user-assigned identities. The file then lists only the system-assigned identities as holders and retires the grants of the user-assigned ones (W2, W3, W5 and W6); `retire` removes them while the identities still exist, and the identities are removed after that.

`--cases-site` and `--usage-site` (or the settings `ACCESS_CASES_SITE` and `ACCESS_USAGE_SITE`) name the two apps in the project's resource group. The tool reads each app, never changes it, and reports an app that does not exist, or has no system-assigned identity yet, as "cannot yet".

```powershell
python tools/access-requirements.py check --project-subscription $sub --project-group $group --cases-site $casesApp --usage-site $usageApp --gateway $gateway --gateway-insights $insights
python tools/access-requirements.py grant --project-subscription $sub --project-group $group --cases-site $casesApp --usage-site $usageApp --gateway $gateway --gateway-insights $insights --apply
```

What the move gives up: a user-assigned identity survives a new app and keeps its roles, and a system-assigned one does not. If an app is deleted and made again, its identity has a new object id, and a person grants the lines of the table again at their places, and the Exchange role again. The client id of a system-assigned identity's service principal is not on the app: `tools/exchange-setup.py` needs it with the object id, and it is read from Microsoft Entra, with the signed-in person's own session (`az ad sp show --id <object id> --query appId`).

## A change is made as the person who approves it

Meternaut finds waste, judges it and, for the one kind of resource that it plants itself, proposes a change. It makes no change with a right of its own. When a person approves a plan, the console sends the person to Microsoft Entra to sign in to Azure Resource Manager, and the one change is made with that person's own token. Azure checks that person's rights, and the Activity Log is expected to show the person as the caller. The decision and the options that were compared are in [run as the approver](05-run-as-the-approver.md).

- **The sign-in.** The OAuth 2.0 authorization code flow with PKCE, with the delegated scope `https://management.azure.com/user_impersonation` and the OpenID Connect scopes `openid` and `profile` (`profile` is needed for the `oid` claim, which names the person who signed in). The consent that the platform's own sign-in already uses (`User.Read`) covers the two OpenID Connect scopes, so no permission is added to the file for them. No refresh token is requested, so nothing can use the permission after the person has left.
- **The credential.** The console redeems the code with the app registration's federated credential: the managed identity `id-meternaut-console-auth` presents a token for `api://AzureADTokenExchange` as the client assertion. There is no secret and no certificate ([rule 23](../../AGENTS.md)). The app registration is a confidential client: public client flows are off (`isFallbackPublicClient` is false, E4 below), so a sign-in code can be redeemed only with that credential and is worth nothing to anybody else.
- **The token.** It is used for one change, kept in memory for that request, and never stored or logged.
- **The rights.** What the change may do is what the person may do: a person who may not delete the resource cannot make Azure delete it by approving.

**Why.** No customer should give a tool a standing right to write to its resources: a right that is held between uses can be used at any time, by a fault in the tool or by anyone who takes over its identity. The Well-Architected Framework's security guidance on identity and access management asks for access that is limited to what is needed ([SE:05](https://learn.microsoft.com/azure/well-architected/security/identity-access)), and the Microsoft cloud security benchmark asks to avoid standing privileged access ([PA-2](https://learn.microsoft.com/security/benchmark/azure/mcsb-v2-privileged-access)). A delegated sign-in follows both: the standing rights of Meternaut over a customer's resources are the reads in the table above, and a write exists only while the person who approved it is present, and only with that person's rights.

**What Microsoft Entra needs for it.** The console's one app registration, "Meternaut console", carries this sign-in next to the platform's own sign-in of the console's pages. `tools/entra-setup.py` reads and makes all four requirements, and `check` reports each of them. The tool adds and never removes: a redirect address or a permission that somebody else added to the app registration stays. It sends back every address and permission that is there together with what is missing, reads the app registration again just before it writes, and shows what it leaves alone as a note, never as a difference. The one thing that it turns off is public client flows (E4), and only when they are on; it sends nothing else of the app registration with that.

**What a customer's tenant administrator does.** Grants the consent for that one delegated permission, once, for the whole tenant: by opening `https://login.microsoftonline.com/<tenant id>/adminconsent?client_id=<client id>` and accepting, or with `tools/entra-setup.py` when the administrator is also the person who makes the app registration. The consent gives Meternaut no standing right. Meternaut can act only as a signed-in person, with that person's own rights, while that person is present; no refresh token is requested; and the person's token is used for one change and never stored or logged. The administrator can remove the consent at any time: after that no change can be made, and the reads go on.

`python tools/access-requirements.py retire` removes what is still there, and nothing else:

- **It reads first.** For each retired item it looks for the identity by name in the project's resource group (W8 names the deployment identity, which is in the bootstrap group and stays, so it is not looked up). For a retired custom role (W1, W7 and W8) it looks for the assignments of the role at that place and below it, whoever holds them, and for the custom role: an identity that was deleted leaves its assignment in Azure, which the portal shows as "Identity not found", and the tool finds it by the role, not by the identity. For the grant of an identity that an app no longer runs as (W2, W3, W5 and W6) it looks only for the assignments that this identity holds, found by its object id, at that place and below it: another holder of the same role at the same place is never touched. An assignment of that identity above the place is reported as "left alone".
- **It keeps a grant until its replacement is in place.** It removes the assignment of an old identity only while the grant that replaces it is present for the system-assigned identity of the app, read the way `check` reads it, so the name of the app is needed (`--cases-site`, `--usage-site`) when there is something to remove. Until then the line says "kept", so that an app is not left without access. That is all it can see: which identity an app really runs as is the flip's check (above), not the tool's. W7 has no replacement: nothing reads a key any more. W8 has none either: no Hub action needs the role.
- **It is a dry run unless told otherwise.** Without `--apply` it prints the exact `az` commands and exits 1 while something is left to retire. With `--apply` it runs them with the signed-in person's own sign-in: the assignments first, then, for a retired custom role only, the role, and only when no assignment of it remains. A role that can also be assigned outside the place is not the one that was granted there, and is left alone. The role of W2, W3, W5 and W6 is never removed: a current grant needs it.
- **It runs while the old identity exists.** It finds the assignments of an old identity by the object id of the identity. Azure keeps the assignments of a deleted identity and shows them as "Identity not found", and the tool cannot tell whose they were: it says so and leaves them, and a person removes them in the portal. So `retire` runs before the identities are removed.
- **It never deletes an identity.** It reports the identity and says that the deployment workflow or the owner removes it.
- **It repeats safely and is refused in a pipeline.** A second run says that there is nothing to retire, and `--apply` is refused under GitHub Actions like the other commands.

The retired items name the same places as the requirements, so the places are those of `check`; `--only` retires some of them, for example `--only W1` for the writer alone, which needs no place but the project's group, and `--only W7` for the key reader or `--only W8` for the deployer alone, which need `--gateway` (the resource group of that instance is their place).

```powershell
python tools/access-requirements.py retire --project-subscription $sub --project-group $group --cases-site $casesApp --usage-site $usageApp --gateway $gateway --gateway-insights $insights
python tools/access-requirements.py retire --project-subscription $sub --project-group $group --cases-site $casesApp --usage-site $usageApp --gateway $gateway --gateway-insights $insights --apply
```

## Who may grant

- To assign a role at a place, a person needs `Microsoft.Authorization/roleAssignments/write` there. *Owner*, *User Access Administrator* and *Role Based Access Control Administrator* have it ([Learn](https://learn.microsoft.com/azure/role-based-access-control/delegate-role-assignments-overview)). The last can be limited by a condition to some roles and some principals.
- To make a custom role, a person needs `Microsoft.Authorization/roleDefinitions/write`. *Owner* and *User Access Administrator* have it; *Role Based Access Control Administrator* and *Contributor* do not (read from Azure on 2026-11-05). Removing an assignment and removing a custom role (`retire`) take the delete actions at the same places.
- The places usually have different owners: the estate's subscription, the gateway, the central workspace. One person who holds the right at all three is the exception; the pilot is one.
- To give the consent for the whole tenant (E2), a person needs a Microsoft Entra role that may grant tenant-wide admin consent ([Learn](https://learn.microsoft.com/entra/identity/enterprise-apps/grant-admin-consent)). To make the app registration and assign people to its enterprise application (E1, E3, E4), a person needs Microsoft Entra roles that allow that. One person who holds all of them, a Global Administrator for example, does everything in one run of `tools/entra-setup.py`. Where that is two people, the one who may not give the consent runs the tool all the same: it makes the rest and prints the address that the other opens.
- The deployment workflow's identity is none of these and must not become one.

## Why a pipeline cannot make the first grant

A pipeline can assign a role only with an identity that already may assign roles at that place. So either a person assigns, or a person first gives a pipeline identity that right. A right to assign roles is the most valuable one an identity can hold, so it must be narrow: *Role Based Access Control Administrator* with a condition that names the roles in the file and the identities of Meternaut. That identity itself needs one grant from a person at each place it works in, or once at a management group above them. It cannot make a custom role either, so the custom role is made by a person first.

## The Watch reads every subscription that its identity can read

The owner's order of 2026-11-07: "Watch is what checks for cost savings? That must be on the root management group; watch the entire estate." So the Watch no longer reads a list that is written into its settings. At the start of each run it asks Azure Resource Manager which subscriptions its own identity can read (`GET /subscriptions`, the ones that are enabled, at most 1000, the most that one Resource Graph query takes) and reads those. The app setting `SCOPE_ALL_SUBSCRIPTIONS` switches that on, and the Hub's parameter builder sets it (`SCOPE_ALL_SUBSCRIPTIONS` in `tools/environment-params.py`). `SCOPE_SUBSCRIPTIONS`, a list of subscription ids, is what the Watch reads when the list cannot be had, and the only list while the switch is off; a run that has neither ends with a plain reason and never watches nothing in silence.

- **What a person does.** One grant of R1 and R2 at the tenant root management group, by hand and on the owner's word, as always (rule 18): `python tools/access-requirements.py grant --estate /providers/Microsoft.Management/managementGroups/<the group's id> --only R1,R2` is a dry run, and `--apply` assigns the two roles with that person's own sign-in; `check` reads them back. Until the grant exists the identity reads only the subscription that it holds the roles on, and the Watch reads that one: nothing breaks. Taking the roles away narrows the Watch again. Neither the template nor the Hub grants anything there. **Done on 2026-11-07:** a person did it in the owner's own session and on his word, and `check` read back 2 of 2 present.
- **Reading more changes nothing else.** A change to Azure is still made only in the one resource group of `CHANGE_RESOURCE_GROUP` in `CHANGE_SUBSCRIPTION_ID`, with the token of the person who approves it (since 2026-11-08 the setting is `CHANGE_SCOPES`, a list of such groups: [families of change](14-families-of-change.md)). A finding about a resource of another team is a result that a person reads ([rule 31](../../AGENTS.md)); the Watch plants, proposes and changes nothing there. The limits of rule 15 (g) are as they were: no more cases, tokens or calls for a larger estate.
- **A large estate.** The Watch reads the subscription of the approval loop first, then the others in the order of their ids, and stops starting new subscriptions when the share of the run's deadline for reading is used (60%, and a subscription that was started inside it may finish within 10% more). The History then says which subscriptions were not read, in a note; the run does not fail. A throttled answer from Resource Graph or Cost Management (HTTP 429) is waited for, as far as the deadline allows, and a source that cannot be read is a note, not a stop. `run.started` carries the count of the subscriptions and the first five ids (eight characters each), never all of them.
- **What was checked on 2026-11-07, and what is not.** With the roles at the tenant root management group, Hub `cases` deployed the app with `SCOPE_ALL_SUBSCRIPTIONS` true, and Hub `cases-run` ended well: the Watch read 10 subscriptions in 345 seconds ([the changelog](../../CHANGELOG.md) has the runs and what was found). Not checked: the scheduled daily run on the whole estate, unattended; Advisor, which is still read for each subscription; throttling on a much larger estate.

## The app should say what is missing

When a read is refused, the Watch writes Azure's own message, which is correct and long. It should name the requirement that is missing (R1, R2, R4 and R5). A caller can read its own effective permissions at a place, so the Watch can check each requirement at the start of a run and write one plain line for each that is missing. Not built. Until then `check` is the read-back.

## Known limits

- **`check` reads role assignments.** It does not evaluate conditions, deny assignments or role eligibility. The proof that a grant works is a run of the Watch.
- **A grant above a named management group is not recognised.** An assignment at that group, and at a management group above a subscription, is.
- **The built-in roles are wider than the Watch needs.** Reader reads every resource of the subscription; Cost Management Reader and Monitoring Reader carry `Microsoft.Support/*`. Custom read roles are the tightening that [the first cases' known limits](02-first-cases.md#known-limits) already name.
- **A new assignment can take minutes to apply.** The first run after the grants of 2026-11-05 worked within three minutes.
- **`retire` sees what the signed-in person can read.** An assignment of the retired role at a place that the person cannot read is not listed. Azure refuses to remove a role that still has an assignment, and the tool then stops and says so.
- **`retire` finds the grants of an old identity by its object id.** If the identity was deleted first, Azure keeps its assignments as "Identity not found", and the tool cannot tell whose they were: it leaves them and says so, and a person removes them in the portal. It also cannot see which identity an app runs as, so that the flip has worked is checked by a person before `retire` runs.
- **`retire` has been run against the real environment as a dry run only, and the new items of `tools/entra-setup.py` not at all.** The steps of `retire` that remove something (`--apply`) and the new items of `tools/entra-setup.py` have run only against models of Azure and of Microsoft Entra; the first run of each in the real environment is read back with the tool's own second run.
- **`tools/entra-setup.py` removes nothing, so a redirect address or a permission that nobody meant stays until a person removes it in the portal.** `check` shows each as a note under the line of the app registration. An extra redirect address is an address that receives sign-in responses, so the note is worth reading; the tool does not judge it.
- **The permission is not narrower than the person.** `user_impersonation` lets the console act in Azure Resource Manager with everything that the signed-in person may do; the permission does not limit it to one kind of change. What the console does with a token is limited by the app's own short list of calls and by a test, not by the consent. Removing the consent ends the permission for everyone.
