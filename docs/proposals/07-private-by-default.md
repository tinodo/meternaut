**Status: decided on 2026-11-06, after the owner found public network access on the Event Hubs namespace, both function apps, Application Insights and the workspace, and asked that all of it be switched off. The identity, the subnet, the tool that runs one container group and the first script (the probe) are built, and the probe ran twice on the real estate on 2026-11-06 and passed every check ([what it proved](#what-the-probe-proved-on-2026-11-06)). The control event and the telemetry read of the two check actions, `recording-check` and `cases-run`, now go through the Operator ([built, not yet run](#the-checks-of-the-usage-recording-and-the-first-cases-run-in-the-operator)). The two function apps get a private endpoint each in the templates, and the probe learns what publishing code from the Operator needs ([phase 1 of publishing code to the private apps](#publishing-code-to-the-private-apps-phase-1): built, not yet run; the apps stay public). The Event Hubs namespace is private-only in the templates and the workflow, and the deploy identity's right to send to the two control hubs is retired by the actions that deploy them ([built, not yet deployed](#event-hubs-private-only-built-not-yet-deployed)). Nothing is private yet. A statement that was inferred and not read in a source is marked (inferred).** This page records one decision: no resource of Meternaut has a public endpoint, and what the deployment workflow can then no longer do from outside the network is done by a short-lived container inside it, the Operator. ## What private access breaks

Once the four services above are private, these stop working from the GitHub-hosted runner, which is outside the network. Azure Resource Manager, the control plane, stays reachable, so everything that is a deployment or a read of a resource's own properties keeps working.

| What | Today | Why it stops |
|---|---|---|
| Publishing code | The runner posts the package to the app's deployment site (Kudu) | That site is reached through the app's private endpoint, with a DNS record of its own next to the app's ([App Service private endpoints](https://learn.microsoft.com/azure/app-service/overview-private-endpoint)). With public access off there is no other way in |
| Starting a run | The runner sends one event to the control hub | A namespace with public network access Disabled takes traffic only through its private endpoints: "Disable public access to your Event Hubs namespace to allow access only via private endpoints" ([Restrict Event Hubs namespace to private endpoints](https://learn.microsoft.com/azure/event-hubs/private-link-service), read on 2026-11-06). The Operator sends the event from inside the network now |
| Reading telemetry | The runner queries the component for the History and for the copy jobs' results | "Queries sent through the Resource Manager API can't use Azure Monitor private links. These queries can only gain access if the target resource allows queries from public networks", and blocking public queries blocks every client outside the private link scope ([Azure Monitor private link design](https://learn.microsoft.com/azure/azure-monitor/fundamentals/private-link-design#control-network-access-to-ampls-resources)) |
| Checking the console's access | `tools/console-check.py door` asks the console from outside and expects a sign-in or a refusal | A request from outside no longer reaches the sign-in: the platform refuses it earlier (inferred), so the check would pass without testing what it was written to test |
| The agents' traces | The Foundry project sends them to the component with the project's identity | Foundry's own page lists public addresses that traces and evaluations need on the Application Insights side ([network isolation for Foundry](https://learn.microsoft.com/azure/foundry/how-to/configure-private-link), firewall allowlisting). The project is a Basic agent setup, which runs in Microsoft's network and not in ours (inferred), so a component whose ingestion is Disabled cannot take them |
| People using the console | A person opens the console's public address and signs in | A private console is reached only from a network that has a path to its private endpoint. Whether the approvers have one is not known to this record (inferred); it is a decision for the owner below |

## The options

The research of 2026-11-06 looked for a way to keep every one of the four actions working without a public endpoint, without a key and without a machine that runs between two runs.

| Option | Keyless | Why it does not do, or what it needs |
|---|---|---|
| Keep public access and restrict it by address | yes | Breaks the rule: the endpoint stays public. The runner's addresses are GitHub's, a large and changing set (inferred) |
| An ARM deployment of the app's `onedeploy` extension with a `packageUri` | no, for a private blob | The platform downloads the package from the URL. A private blob needs a shared access signature, which rule 23 forbids. A public URL needs none: that is route (b) below |
| `WEBSITE_RUN_FROM_PACKAGE` from a blob, with a managed identity | yes | Not supported on Flex Consumption. On the Basic plan it could work (inferred), but somebody has to write the blob, and the storage account is private: the same problem one step earlier |
| The ARM `hostruntime` proxy | yes | Not documented, so nothing is built on it |
| An ARM `deploymentScripts` resource | no | It mounts a storage account with the account key |
| GitHub-hosted runners inside the virtual network | yes | Azure private networking needs larger runners, and the page is written for organizations ([GitHub docs](https://docs.github.com/en/organizations/managing-organization-settings/about-azure-private-networking-for-github-hosted-runners-in-your-organization)); the plan needed is Team or Enterprise (from the research, not re-read). The repository belongs to a person |
| A self-hosted runner inside the virtual network | no | Registering it takes a GitHub credential, and the machine runs and costs money between two runs |
| **The Operator: a container group in a delegated subnet** | yes: its own managed identity | What follows. It is the only option that meets the rule, needs no standing compute and no organization. It is not proven here: the probe is what proves it |

## The Operator

**What it is.** A container group of Azure Container Instances that the workflow makes through Azure Resource Manager when a step needs the inside of the network. One script runs in it. The workflow reads its log through Azure Resource Manager and deletes the group. [`tools/operator-run.py`](../../tools/operator-run.py) does all four, and it deletes the group in every case: after an error, after a timeout (exit code 124) and after an interrupt (130). The group runs in the subnet `snet-ops`, which is delegated to container groups and gives it no public address, as the user-assigned identity `id-meternaut-operator`. The template is [`environment/operator/main.bicep`](../../environment/operator/main.bicep); the Hub actions are `operator` (make the identity, the subnet and the roles) and `operator-probe` (the first run), and `recording-check` and `cases-run` run their check tools in it.

**How a script gets in.** The script and any files travel in the request as one secret volume at `/mnt/op`. The volume is kept in memory in the container and is read-only ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-volume-secret)). A value that must not be seen is passed as a secure environment variable. The tool takes every such value out of everything it prints, including what Azure and the container say, and the request body is written to a file that only the tool's user can read and is removed at the end.

**The image** is `mcr.microsoft.com/azure-cli`, pinned by digest. On 2026-11-06 the tags `2.92.0`, `latest` and `azurelinux3.0` were the same manifest list (Azure CLI 2.92.0 on Azure Linux 3.0). Container Instances runs amd64 images only ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-resource-and-quota-limits)), so the workflow names the digest of the linux/amd64 manifest, which two requests to MCR with `curl` give and no container tool is needed. The pinned reference is `mcr.microsoft.com/azure-cli@sha256:67afdcb4f3efce0b33aadba0b8a72402b6f071741400fd75cc5cb8a1d7bf1d98`. To read it again: a HEAD request to `https://mcr.microsoft.com/v2/azure-cli/manifests/<tag>` with the header `Accept: application/vnd.docker.distribution.manifest.list.v2+json` gives the digest of the manifest list in `Docker-Content-Digest`, and a GET of the same address lists the manifests, of which the one with architecture `amd64` and operating system `linux` is the one to pin. A tag can move and a digest cannot, so the pin is changed by a person, on purpose, with the same two requests. The layers of that image, listed from MCR without running it, hold bash, curl, getent, python 3.12 and jq. They hold no awk, so nothing in the probe uses one.

**The log.** A running container keeps up to 4 MB of log, a stopped one only 16 KB or 1,000 lines ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-resource-and-quota-limits)). So a script prints little (the probe at most 120 short lines, about 12 KB), the tool reads the log every few seconds while the container runs and once more at the end, prints each line once, prints the group's events when the container never started (an image that cannot be pulled is the likely cause), and says when the last read is as long as the limit. The workflow also puts the log into the run's summary.

**Facts about container groups in a virtual network** that shape the design ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-virtual-network-concepts), [Learn](https://learn.microsoft.com/azure/container-instances/container-instances-vnet)):

- The subnet holds container groups only. Learn says that a subnet smaller than /24 is known to run out of addresses, because the platform releases the address of a deleted group slowly, and it names /28 as one of the sizes. A /24 does not fit a small virtual network, so the subnet is the largest the network can spare, a /27 (27 usable addresses), and the probe is run several times in a row to see whether that is enough.
- A group does not take the DNS servers of the virtual network. The tool gives it the landing zone's, which is what lets the name of a private endpoint resolve to its private address.
- Learn says, on two pages, that a NAT gateway is the only supported way out for a container group in a virtual network. The landing zone sends the traffic of a subnet through its firewall with a route table, and the same site documents a container group behind Azure Firewall ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-egress-ip-address), not re-read). Whether the landing zone's route works for a container group is the first thing the probe finds out: the image is pulled through it.
- A Linux container in a virtual network can get a token of its managed identity. Learn says that only Windows containers in a virtual network cannot ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-managed-identity)).
- The landing zone's network manager puts a route table on the new subnet some minutes after the subnet is made. The template makes the subnet once and leaves it alone ([rule 27](../../AGENTS.md)), and the action `operator` waits until the table is there.

**Identity and roles.** The identity is user-assigned, which is an exception to the owner's preference for system-assigned identities ([changelog](../../CHANGELOG.md), 2026-11-06); the console's sign-in identity is the other one. A system-assigned identity belongs to one container group, and a group exists for the minutes of one run, so every run would make a new identity whose roles have to be assigned and applied before the container can use them, and the changelog gives up to ten minutes for a role to apply. A user-assigned identity is made once, holds its roles, and is attached to each group (inferred: that the roles of a system-assigned identity of a container group cannot be given in advance). It is attached to no app. Each role below goes on one resource and is added with the step that uses it. Each also has to be in the condition of the deploy identity's role-assignment right ([bootstrap](../../environment/BOOTSTRAP.md)): Reader was added to it by a hand step, and Azure Event Hubs Data Sender was in it already (the usage recording gave it to the gateway's identity and, until [the retirement below](#event-hubs-private-only-built-not-yet-deployed), to the workflow's identity), so the two roles on the control hubs need none. Until a role is in the condition, the deploy of that role is refused and nothing else changes.

| Role | Where | What the Operator does with it | Added with |
|---|---|---|---|
| Reader | The project's resource group | Shows that it signs in and can read; reads the telemetry of the two function apps through Azure Resource Manager (the checks of the usage recording and the first cases) | The probe (run twice on 2026-11-06) |
| Azure Event Hubs Data Sender | The two control hubs, `usage-control` and `cases-control`, one role on each hub | Sends the control event that starts a copy job or a Watch | The checks (built, not yet run) |
| Website Contributor | Each of the two function apps | Publishes code with its own token to the private deployment site | The publish step |
| Reader, which the Operator already holds through the group (inferred), and Monitoring Reader only if a read is refused | The component, or a scope above it | Queries the telemetry through the data plane of Application Insights and the Azure Monitor private link, once Application Insights is private | The read step: [what Learn says, and who gives the role](#reading-telemetry-when-the-component-is-private) |

**What the Hub actions will do with it.** An action that only deploys or reads a resource's own properties does not change. These change:

| Hub action | Through the Operator |
|---|---|
| `recording`, `cases` | Gets the package (the routes below), posts it to the private deployment site with its identity's token, and reports the result |
| `recording-check`, `cases-run` | Runs the check tool (`tools/recording-check.py`, `tools/cases-check.py`) in the Operator: it sends the control event with the Event Hubs REST API and a token of the Operator's identity, then queries the telemetry for the answer and prints what the tool prints. Built, not yet run: [below](#the-checks-of-the-usage-recording-and-the-first-cases-run-in-the-operator) |
| `loop-check`, and the check at the end of `cases` | Makes the same requests as `tools/console-check.py door` from inside the network, with that tool sent in the secret volume |

**Rule 29.** [Rule 29](../../AGENTS.md) says that no identity of Meternaut holds a role that writes in Azure. Website Contributor writes. The Operator is the deployment workflow's arm inside the network, not a part of the product: the workflow's identity already holds Contributor on the group and can do all of it; the Operator's identity is attached to no app, is used only by a group that the workflow makes, and has the role on the two apps and nowhere else. Whether that is inside rule 29, or the role is given just before a run and taken away after it, is the owner's to say (decisions below). The two roles that exist now do not write in Azure: Reader reads, and Azure Event Hubs Data Sender lets the Operator send events to the two control hubs of Meternaut's own namespace, which is what the workflow's own identity did until [the retirement below](#event-hubs-private-only-built-not-yet-deployed) took its role away. Like the Foundry User role of rule 30, it is a data-plane right inside Meternaut's own group, over Meternaut's own hubs, that changes no resource in any estate (inferred: that this is inside rule 29; the owner may say otherwise).

## The checks of the usage recording and the first cases run in the Operator

**What changes.** The Hub actions `recording-check` and `cases-run` used to send the control event and read the telemetry from the runner, with the workflow's own token. They now run the same tools, [`tools/recording-check.py`](../../tools/recording-check.py) and [`tools/cases-check.py`](../../tools/cases-check.py), in the Operator, with the same arguments, so that the Event Hubs namespace can have public access switched off (that switch is [the next change](#event-hubs-private-only-built-not-yet-deployed)). One generic script, [`operator/run-tool.sh`](../../operator/run-tool.sh), runs a tool that is in the secret volume. It checks its input before anything runs (the identity's client id, a plain tool name, and arguments made of letters, digits and `. / : _ = -` only, split on single spaces and handed over as separate words: nothing is evaluated or expanded, and a value cannot become a command), signs in with `az login --identity` (three tries, because the first minute of a group can be noisy), runs `python3 /mnt/op/<tool>.py <arguments>` once, hides a string that looks like a token in what the tool prints, and exits with the tool's own exit code. It never runs the tool twice: an event that arrived would start the job twice. The workflow sets `GITHUB_ACTIONS=true` in the container, because the tools refuse to start a job anywhere else (rule 18) and only a run of the Hub workflow makes a group of the Operator.

**Why the tools themselves.** The tools use the standard library only, the image has `python3` (3.12) and `az`, and the secret volume takes a file of 400,000 bytes whole (the probe), so the two tools, about 33 KB, travel in the request. The telemetry read has to move into the network as well, because a later step makes Application Insights private. `tools/cases-check.py` loads `tools/recording-check.py` from its own folder, so both files are sent for `cases-run`. The tools have no new option and no new behaviour. CI and the function app use Python 3.13 and the image has 3.12, so a test parses both tools as 3.12 and runs them from a folder that holds only the files that are sent.

**What Reader does here.** The tools query the telemetry through Azure Resource Manager (`POST .../components/<name>/query`), which is a read. Learn lists the operation `Microsoft.Insights/Components/Query/Read` for "Run queries against Application Insights logs" ([Azure permissions for Monitor](https://learn.microsoft.com/azure/role-based-access-control/permissions/monitor#microsoftinsights)), and the built-in Reader role includes `*/read` for the control plane ([built-in roles for General](https://learn.microsoft.com/azure/role-based-access-control/built-in-roles/general#reader)); both were read on 2026-11-06. The Operator holds Reader on the project's resource group already, so the read needs no new role. That the endpoint is authorised by that operation is (inferred); the first `recording-check` in the Operator shows it.

**What stops working later, and the next step.** A query through Azure Resource Manager "can't use Azure Monitor private links" and works only while the component allows queries from public networks ([Azure Monitor private link design](https://learn.microsoft.com/azure/azure-monitor/fundamentals/private-link-design#control-network-access-to-ampls-resources)). So when Application Insights gets private-only query access, the query of the tools stops working, and they have to query the data plane instead: `https://api.applicationinsights.io/v1/apps/<appId>/query`, with a Microsoft Entra token for that resource (the Operator gets it with `az account get-access-token --resource https://api.applicationinsights.io`) and a read role on the component (the example in [Microsoft Entra authentication for Application Insights](https://learn.microsoft.com/azure/azure-monitor/app/azure-ad-authentication#query-application-insights-by-using-microsoft-entra-authentication) gives Reader on the component, which the Operator's Reader on the group may already be (inferred); a narrower monitoring role is the alternative). The probe showed that `api.applicationinsights.io` is reachable from the subnet. That is the next step, and it is not built here. The list of the functions, `tools/recording-check.py functions` and `tools/cases-check.py functions`, is still made from the runner through Azure Resource Manager before the group is made; whether it still answers when the apps are private is not known.

**Time and cost.** The group is given 1,500 seconds for `recording-check` (the tool waits 20 minutes at most for the telemetry) and 2,400 seconds for `cases-run` (30 minutes), and the step is given more than that. The tool deletes the group at the end of every run, and a last step deletes any group named `op-check-<run id>` that a cancelled run left. A stopped container keeps only the last 16 KB of its log, and the tool that polls reads the log every few seconds while the container runs, so the script stays 20 seconds after the tool has ended: the poll then reads the whole log while the container still runs. At most about 4 US cents for a run of `cases-run` ([what it costs](#what-it-costs)).

## What it costs

Container Instances bills the vCPU and the memory of a group for the seconds it exists. The Retail Prices API on 2026-11-06 gives, for Sweden Central and a Linux group, 0.0466 US dollars for a vCPU-hour and 0.00511 for a gigabyte-hour. A group of 1 vCPU and 1.5 GB costs about 0.054 US dollars an hour, so a probe of 10 minutes costs about 0.9 US cents, and 30 such runs a month about 27 cents. The identity, the subnet and its network security group cost nothing. The private endpoints that the later steps add (one for each app, which [phase 1 of publishing code](#publishing-code-to-the-private-apps-phase-1) makes, and one for the Azure Monitor private link scope) cost about 6.57 euros a month each ([the first environment](01-first-environment.md)). Two fallbacks have a standing price, and the probe says whether either is needed:

- A NAT gateway, if the landing zone's route does not work for a container group: 0.045 US dollars an hour, about 33 a month, plus a Standard public IP address at 0.005 an hour, about 3.65, so about 37 a month.
- A private container registry, if MCR cannot be reached from the subnet: Azure Container Registry Premium, which private links need, is 1.67 US dollars a day, about 50 a month, which is the owner's line.

## What the probe checks

[`operator/probe.sh`](../../operator/probe.sh) runs in the container and prints one `ok:` or `FAIL:` line for each check: at most 120 short lines, never a token or a secret, always ending in `probe-done`, and always exiting 0, because the facts are the product. That the image is pulled at all is the first answer, and the tool's events show it when it is not.

| Check | What it shows | What it decides |
|---|---|---|
| The container starts | MCR is reachable from the subnet, and the landing zone's route lets a container group out | Whether the Operator can work at all, and whether a NAT gateway or a private registry is needed |
| `az login --identity`, `az group show` | The identity signs in inside a group in a network, and its Reader role works | Everything else |
| The resolvers, and the names that are passed in | The DNS servers the group got, and whether a private endpoint's name gives a private address | Whether private endpoints can be used from the Operator |
| `management.azure.com`, `login.microsoftonline.com` | The Operator's own calls | Whether it can sign in and call Azure |
| `api.github.com`, `codeload.github.com` | The GitHub API and the repository archive at a commit | Route (a) from the repository |
| `api.github.com` and the host of the workflow artifacts | The download of an artifact that the job uploaded | Route (a) from an artifact |
| `github.com`, the release-asset hosts | A release asset with a public address | Route (b) |
| `pypi.org`, `files.pythonhosted.org` | Installing a package inside the container | Building inside the container |
| `api.applicationinsights.io`, `api.loganalytics.io` | The query endpoints that the read step will use | Whether the telemetry can be read from inside after the private link exists |
| A file of a stated size in the secret volume | How many bytes the request body and the volume carry | Route (c) |

**How the answers choose the package route.** The usage app's package is tens of megabytes (the Azure SDK wheels), so it cannot ride in the request. The cases app's package is about 200 KB of source and one wheel. The route that [phase 1 of publishing code](#publishing-code-to-the-private-apps-phase-1) builds on is a mix of (c) and a build inside the container, which is why the probe got a second set of checks.

- **(a) The job's own token.** The workflow hands the container its token for the run as a secure value, and the container downloads the package that the job built and uploaded as an artifact, or the repository archive at the commit. The token expires when the job ends, and on a GitHub-hosted runner at the latest after 6 hours ([GitHub docs](https://docs.github.com/en/actions/concepts/security/github_token)). It would need `actions: read` next to `contents: read`. If the API and the artifact host answer, this is the route, and nothing needs to be built in the container. If only the archive host answers, the container would have to build the package itself, which needs the two package hosts and Python 3.13 (the image has 3.12, so the build would have to target 3.13 wheels: inferred): possible, and clumsy.
- **(b) A public repository and a release asset** at a public address. It needs no token, and it also allows the `onedeploy` extension to take that address as its `packageUri`, so that even the publish step would need no Operator (inferred: whether the platform follows the redirect of a release asset is not documented). It needs the owner's decision on visibility, rule 1.
- **(c) A package inside the request**, as a file of the secret volume, for the cases app only. It works if the size check passes with room above the package (base64 adds a third), and it does not help the usage app.
- **None of them**: if no GitHub host and no size is enough, the usage app has no route until the platform team of the landing zone allows one host, or the owner chooses a private registry.

## What the probe proved on 2026-11-06

`operator-probe` ran twice on the real estate and every check passed both times. The run pages are the record; the results were passed on to this change by the session that ran them.

| Check | Result |
|---|---|
| The container starts | The image was pulled from MCR and the group ran in `snet-ops`, so the landing zone's route lets a container group out |
| `az login --identity` and `az group show` | The identity signs in inside the network, and its Reader role on the project's resource group works |

A run takes about one to two minutes. What this decides: the Operator works as designed. It signs in with its own identity, it resolves the private endpoints through the landing zone's DNS servers, and it reaches Azure Resource Manager and Microsoft Entra, so the control event and the telemetry read can be done from it. The container started from MCR with no NAT gateway and no private registry, so neither of the two fallbacks of [what it costs](#what-it-costs) is needed for what the probe tested. The secret volume takes the two check tools whole.

What is still open: publishing code to the private deployment sites (the package route), the telemetry read once Application Insights is private ([the next section](#reading-telemetry-when-the-component-is-private): the two tools can ask the data plane since that change, and the two steps do not pass the option yet), and the check of the console's front door (`loop-check`) from inside the network.

## Publishing code to the private apps: phase 1

**Why.** The rule ends with both function apps, the usage app on Flex Consumption and the cases app on a Basic plan (which also serves the console), at public network access Disabled. The workflow publishes their code today from the GitHub-hosted runner, to each app's deployment site, `<app>.scm.azurewebsites.net`. Learn says that with private endpoints and public access disabled that site cannot be reached from outside, and that the machine that deploys needs a network path and DNS to it ([deployment technologies, secured virtual networks](https://learn.microsoft.com/azure/azure-functions/functions-deployment-technologies), read on 2026-11-06). So the code is published from inside the network, by the Operator, in three phases. This is phase 1: it changes nothing about how the code is published and nothing about who can reach the apps.

| Phase | What | State |
|---|---|---|
| 1 | One private endpoint for each app, and a second set of checks in the probe: can the Operator sign in as the deploy identity, build the usage app's libraries and reach the apps' deployment sites. The apps stay public | built, not yet run |
| 2 | The two publish steps run in the Operator, as the deploy identity, while the apps are still public, so that the path through the private endpoint is proved with nothing to lose | later |

## Reading telemetry when the component is private

**What changed.** [`tools/recording-check.py`](../../tools/recording-check.py) and [`tools/cases-check.py`](../../tools/cases-check.py) read the telemetry for their answer: the results of the copy jobs and the History of a Watch. Until now they did that only through Azure Resource Manager, which is the row "Reading telemetry" of the table above. Both tools now take `--query-via arm|data-plane` on `run`, the one subcommand of each that queries. The default is `arm`, so nothing changes while the component accepts queries from public networks. With `data-plane` a tool does four things:

1. It reads the component's Application ID once through Resource Manager (`GET <component id>?api-version=2020-02-02`, the property `AppId`) and keeps it for the rest of the run. It does this before it sends the event that starts a job, so a component that cannot be read stops the run first. The read is on the control plane, which stays reachable while the component is private.
2. It asks the Azure CLI for a token for the resource `https://api.applicationinsights.io`, the way the tools ask for their other tokens. It asks again for each query, keeps no token and prints none.
3. It posts the KQL, as `{"query": "..."}`, to `https://api.applicationinsights.io/v1/apps/<Application ID>/query`.
4. It checks the answer, which has the shape of Resource Manager's (`tables`, each with `columns` and `rows`), and passes the rows on unchanged. A status other than 200, an answer that does not have that shape and a network error each become one short message. The loops that wait for the telemetry keep waiting, as they already do for a query that fails right after a deploy.

A 403 is reported as what it most probably is: the identity has no Reader or Monitoring Reader role on the component or above it (a new role takes minutes to apply), or the component refuses queries from this network. What a service says back is cut to one line, and the token is taken out of it. The tool does not follow a redirect: Python's standard client repeats a POST that was answered with 301, 302 or 303 as a GET at the new address and keeps the `Authorization` header (seen on two local servers), which would hand the token to another host. No API key is used.

The option is for the Operator, inside the network, where `api.applicationinsights.io` resolves to the private endpoint. From the GitHub-hosted runner the name resolves to a public address, and a component that refuses public queries refuses that request. The workflow steps and the Operator script that call the tools with this option are a later change.

1. `operator`, if the Operator does not hold Data Sender on both control hubs yet, and about ten minutes of waiting.
2. `recording-check` and `cases-run`, through the Operator, **while the namespace is still public**. Both have to pass first: that proves the Operator's path with nothing else changed.
3. `recording`: it deploys the template that makes the namespace private, reads the namespace back, and retires the deploy identity's right on `usage-control`. Then `cases`: it retires the right on `cases-control`.
4. `recording-check` and `cases-run` again, as the proof.
5. The first call through the gateway that sends to the usage hubs, as the second proof ([below](#whether-the-gateway-reaches-the-private-namespace)).

**The way back** is to revert this change and run `recording` and `cases`: the earlier templates set public access Enabled again and give the deploy identity its role again.

### Whether the gateway reaches the private namespace

**Not known yet.** The gateway's two Event Hub loggers send with the gateway's identity from an API Management instance in another virtual network than the project's. Learn says that "Effective 15 March 2026, Azure API Management is retiring trusted service connectivity by the API Management gateway to supported Azure services", Event Hubs among them, and that the gateway "needs alternative ways to communicate and have network line-of-sight", Private Link being one ([the retirement notice](https://learn.microsoft.com/azure/api-management/breaking-changes/trusted-service-connectivity-retirement-march-2026), dated 2026-01-15, updated 2026-06-25, read on 2026-11-06). So once the namespace is private, the gateway can reach it only through the private endpoint, over the peering and the hub. Whether the landing zone's routes and firewall let it, and whether the gateway's resolver answers the namespace's name with the private address, was not read in the landing zone and has not been tried. Nothing can show it yet: no API policy includes the `ai-usage` fragment, and nothing has sent to the `ai-usage` and `pii-usage` hubs (a measurement of 2026-11-06 found no message in 14 hours).

**How the first gateway call will show it.** After a policy of the gateway first sends through the fragment, and a few minutes:

- The namespace's metric `IncomingMessages` (Total, one-minute grain), split by the dimension `EntityName`, has a count for `ai-usage`, and for `pii-usage` when that fragment ran ([Supported metrics for Microsoft.EventHub/Namespaces](https://learn.microsoft.com/azure/azure-monitor/reference/supported-metrics/microsoft-eventhub-namespaces-metrics), read on 2026-11-06). It is a platform metric that Azure Monitor keeps, which a private namespace does not hide (inferred).
- The gateway's own metrics for its Event Hub loggers: `EventHubSuccessfulEvents` rises when it works, and `EventHubTimedoutEvents`, `EventHubTotalFailedEvents`, `EventHubRejectedEvents` (wrong configuration or unauthorized) or `EventHubDroppedEvents` rise when it does not ([Supported metrics for Microsoft.ApiManagement/service](https://learn.microsoft.com/azure/azure-monitor/reference/supported-metrics/microsoft-apimanagement-service-metrics), dated 2026-07-31, read on 2026-11-06). A timeout would point at a missing network path or a name that does not resolve to the private address, and a rejection at the gateway identity's role; no page says that the metrics behave that way (inferred).

**If there is no path**, a public endpoint is not an option under the rule, so what is left is a network path that the platform team of the landing zone grants (a route, a firewall rule or the resolver), and what to ask for is the owner's decision. This change does not ask for it: the answer is read from the first call and not guessed.

### Whether the usage app wakes from zero on a private namespace

The usage app runs on the Flex Consumption plan and scales to zero when nothing is to do. The control event of `recording-check` arrives on `usage-control` through the private endpoint, and the app has to wake and run the copy jobs. Learn says: "The Flex Consumption plan natively supports virtual network triggers. Your function app can be triggered from event sources protected by a virtual network without requiring extra configuration for runtime scale monitoring" ([Azure Functions networking options, virtual network triggers](https://learn.microsoft.com/azure/azure-functions/functions-networking-options), dated 2026-09-15, updated 2026-10-16, read on 2026-11-06). It also says that apps on the plan "can connect to other Azure services secured inside a virtual network" ([Flex Consumption plan](https://learn.microsoft.com/azure/azure-functions/flex-consumption-plan), updated 2026-09-30, read the same day), and the first page lists a quickstart template named "Private Event Hubs triggered function app".

**What could not be verified.** Neither page says that a Flex Consumption app wakes from zero on an event hub whose public network access is Disabled, through an identity-based connection (`EventHubConnection__fullyQualifiedNamespace`), which is this app. Nothing has run. **The first `recording-check` after the flip is the proof**: the app has been idle, the event has to wake it, and the check waits 20 minutes for the result that the job writes to its telemetry. If no result arrives while `IncomingMessages` of `usage-control` rises, the app did not wake. The ways out each have a price that the owner decides before anything is built ([rule 22](../../AGENTS.md)): an instance that is always ready for the control function (a standing price, to be taken from the Retail Prices API), or a plan that does not scale to zero.

## Decisions for the owner

**Phase 1 of [publishing code](#publishing-code-to-the-private-apps-phase-1) changes three of the decisions below.** Its route needs no public repository (the cases package rides in the request and the usage libraries come from PyPI), no job token in the container (the container gets an OpenID Connect token for the deploy identity instead, which no key replaces and which lives five minutes), and no Website Contributor for the Operator (it publishes as the deploy identity, which holds the right already). The three stay below as they were decided, and matter again only if that route fails.

**A public repository** (rule 1). Needed only for route (b). Cost: none. The way back: none in practice, because published content can be copied. Recommendation: do not decide now. Run the probe first; route (a) needs no change of visibility.

**The job's token inside the container** (rule 23). It is not a key that anyone keeps: it exists for one job. It is a bearer token, though, and whoever holds it can read the whole private repository until the job ends. Whether that counts as "an identity of the run" under rule 23 is the owner's to say (inferred reading of the rule). Way out: route (b) or (c). Recommendation: allow it for the packages of the two apps and nothing else, if the probe shows that route (a) is the only one.

**The Operator's Website Contributor** (rule 29), as above. Recommendation: standing, on the two apps only. The Operator can be used only by a group that the deploy identity makes, and that identity can already do everything the role allows, so a standing role adds no right that the workflow does not hold. Counter-disclosure: it is a standing right to write that a person who may assign that identity could use. The alternative, given just before a run and taken away after it, needs the same entry in the condition and a wait for the role to take effect (inferred).

**The console for people.** A private console cannot be opened from the public internet. The approvers need a path into the landing zone's network (a VPN, ExpressRoute, or a machine inside), or a public front end such as Azure Front Door with Private Link in front of it, which is a public endpoint again and costs a standing price. Until the owner says which, the cases app stays public and everything else goes private first.

**The agents' traces.** Foundry's Basic agent setup cannot send traces to a component whose ingestion is Disabled. Three ways:

| Way | What it gives | What it costs |
|---|---|---|
| No traces from Foundry | The agents run; the History is unchanged | Nothing. The agents' own steps stay in the History that the app writes |
| A separate component for the traces, ingestion public, Microsoft Entra ID only | The traces | One public ingestion point that holds the agents' traces and not the History, and takes no key. A few cents a month. Taken away by removing the connection |
| The Standard agent setup, with a delegated subnet | Traces and agent state inside the network | It needs a Cosmos DB account, a storage account and an AI Search service of the project's own. AI Search Basic alone is 0.101 US dollars an hour, about 74 a month, so the whole is above the owner's line |

Recommendation: no traces from Foundry while the component is private, and a separate component only if the owner wants the traces and accepts one public ingestion point.

**A NAT gateway or a private registry**, if the probe shows that either is needed. Both are named with their prices above. The probe of 2026-11-06 passed without either, so there is nothing to decide now; the paragraph stays for the case that the landing zone changes its route. Recommendation then: the NAT gateway first, because it costs less and the registry also needs an image import.

**The gateway's path to the namespace**, only if the first call through the gateway shows that there is none ([the section](#whether-the-gateway-reaches-the-private-namespace)). A public endpoint is not an option under the rule, so what is asked is a route, a firewall rule or name resolution from the platform team of the landing zone, whose cost and way back are theirs to say. Recommendation then: ask for the narrowest path, from the gateway's network to the namespace's private endpoint and nothing else.

## The order of the work

1. **The identity switch**, in its own change, first. Both steps are merged: both apps run as their system-assigned identities and the grants of the user-assigned ones are retired in the code ([changelog](../../CHANGELOG.md), 2026-11-06). What is left is a person's: deploy it, read it back, and remove the old identities. The roles and the private endpoints below are given to identities, and changing an identity after that repeats them (inferred).
2. **The Operator and the probe** (done). A person registered the resource provider `Microsoft.ContainerInstance` in the project's subscription and added Reader to the deploy identity's condition ([bootstrap](../../environment/BOOTSTRAP.md)). The Hub actions `operator` and `operator-probe` ran, and the probe passed twice ([what it proved](#what-the-probe-proved-on-2026-11-06)). Nothing is private yet.
3. **The checks run in the Operator** (built in the change before this one; not yet run when this page was written, and the run pages of `recording-check` and `cases-run` say whether they have passed). The control event and the telemetry read of `recording-check` and `cases-run` go through the Operator, with Azure Event Hubs Data Sender on the two control hubs ([the section above](#the-checks-of-the-usage-recording-and-the-first-cases-run-in-the-operator)). The order on an estate is `recording`, `cases`, `operator`; then `operator` is run again so that the two roles are assigned, about ten minutes are waited for them to apply, and `recording-check` and `cases-run` are run. Step 4 is not run before both have passed.
4. **Event Hubs private** (this change: built, not yet deployed). The namespace's public network access is Disabled in the template, and the deploy identity's right to send to the control hubs is retired by the actions that deploy them. What runs, in this order, and what each run shows is in [the section](#event-hubs-private-only-built-not-yet-deployed): `recording-check` and `cases-run` through the Operator while the namespace is still public, then `recording`, then `cases`, then `recording-check` and `cases-run` again as the proof. Whether the gateway's loggers still reach the namespace is not known and cannot be tested before a policy of the gateway sends ([the question](#whether-the-gateway-reaches-the-private-namespace)); it is read when the first call goes through the gateway, and it is a change of its own if it asks for one.
5. **The two apps private**, one private endpoint each, with the central zone for App Service sites registered by the landing zone's policy for both records (the app's and the deployment site's: not read in the landing zone; a fact to check, which the probe reports). It is done in three phases ([above](#publishing-code-to-the-private-apps-phase-1)): the endpoints and a second set of checks in the probe, with the apps still public (built, not yet run); the publish steps through the Operator, still with the apps public; and then `Disabled` for each app, with the access check and the list of the functions moved inside. The console stays public until the decision about people is taken.
6. **Application Insights and the workspace private**, through an Azure Monitor private link scope with one private endpoint. The central zones `privatelink.monitor.azure.com`, `privatelink.oms.opinsights.azure.com`, `privatelink.ods.opinsights.azure.com`, `privatelink.agentsvc.azure-automation.net` and `privatelink.blob.core.windows.net` exist in the hub (the owner's finding), and the built-in policy "Configure Azure Monitor Private Link Scope to use private DNS zones" (`437914ee-c176-4fff-8986-7e05eb971365`, part of the Azure landing zone reference's DNS initiative) has to be assigned in the landing zone: a fact to check, not to assume. The scope starts in Open access mode and moves to Private Only after every resource is in it ([Learn](https://learn.microsoft.com/azure/azure-monitor/fundamentals/private-link-design)). The query of the check tools has to move to the data plane before that ([above](#the-checks-of-the-usage-recording-and-the-first-cases-run-in-the-operator)), and the Foundry decision above comes first.

- Whether the usage app wakes from zero on an event that arrives only through the private endpoint, and whether the gateway's two loggers reach the namespace ([the section](#event-hubs-private-only-built-not-yet-deployed) says what is known, what could not be verified, and what shows each).
