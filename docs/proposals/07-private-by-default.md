## What private access breaks

Once the four services above are private, these stop working from the GitHub-hosted runner, which is outside the network. Azure Resource Manager, the control plane, stays reachable, so everything that is a deployment or a read of a resource's own properties keeps working.

With public access off there is no other way in. The Operator publishes from inside the network since phase 2, and it did so for both apps on 2026-11-06, the usage app also into the app that was already private ([phase 2](#publishing-code-to-the-private-apps-phase-2)) |

## The options

The research of 2026-11-06 looked for a way to keep every one of the four actions working without a public endpoint, without a key and without a machine that runs between two runs.

| Option | Keyless | Why it does not do, or what it needs |
|---|---|---|
| Keep public access and restrict it by address | yes | Breaks the rule: the endpoint stays public. The runner's addresses are GitHub's, a large and changing set (inferred) |
| An ARM deployment of the app's `onedeploy` extension with a `packageUri` | no, for a private blob | The platform downloads the package from the URL. A private blob needs a shared access signature, which rule 23 forbids. A public URL needs none: that is route (b) below |
| `WEBSITE_RUN_FROM_PACKAGE` from a blob, with a managed identity | yes | Not supported on Flex Consumption. On the Basic plan it could work (inferred), but somebody has to write the blob, and the storage account is private: the same problem one step earlier |
| The ARM `hostruntime` proxy | yes | Not documented, so nothing is built on it |
| An ARM `deploymentScripts` resource | no | It mounts a storage account with the account key |
| GitHub-hosted runners inside the virtual network | yes | Azure private networking needs larger runners, and the page is written for organizations ([GitHub docs](https://docs.github.com/en/organizations/managing-organization-settings/about-azure-private-networking-for-github-hosted-runners-in-your-organization)); the plan needed is Team or Enterprise (from the research, not re-read). The repository belongs to a person |
| A self-hosted runner inside the virtual network | no | Registering it takes a GitHub credential, and the machine runs and costs money between two runs |
| **The Operator: a container group in a delegated subnet** | yes: its own managed identity | What follows. It is the only option that meets the rule, needs no standing compute and no organization. It is not proven here: the probe is what proves it |

## The Operator

**What it is.** A container group of Azure Container Instances that the workflow makes through Azure Resource Manager when a step needs the inside of the network. One script runs in it. The workflow reads its log through Azure Resource Manager and deletes the group. [`tools/operator-run.py`](../../tools/operator-run.py) does all four, and it deletes the group in every case: after an error, after a timeout (exit code 124) and after an interrupt (130). The group runs in the subnet `snet-ops`, which is delegated to container groups and gives it no public address, as the user-assigned identity `id-meternaut-operator`. The template is [`environment/operator/main.bicep`](../../environment/operator/main.bicep); the Hub actions are `operator` (make the identity, the subnet and the roles) and `operator-probe` (the first run); `recording-check` and `cases-run` run their check tools in it, and `recording` and `cases` publish the code of their app in it ([phase 2](#publishing-code-to-the-private-apps-phase-2)).

**How a script gets in.** The script and any files travel in the request as one secret volume at `/mnt/op`. The volume is kept in memory in the container and is read-only ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-volume-secret)). A value that must not be seen is passed as a secure environment variable. The tool takes every such value out of everything it prints, including what Azure and the container say, and the request body is written to a file that only the tool's user can read and is removed at the end.

**The image** is `mcr.microsoft.com/azure-cli`, pinned by digest. On 2026-11-06 the tags `2.92.0`, `latest` and `azurelinux3.0` were the same manifest list (Azure CLI 2.92.0 on Azure Linux 3.0). Container Instances runs amd64 images only ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-resource-and-quota-limits)), so the workflow names the digest of the linux/amd64 manifest, which two requests to MCR with `curl` give and no container tool is needed. The pinned reference is `mcr.microsoft.com/azure-cli@sha256:67afdcb4f3efce0b33aadba0b8a72402b6f071741400fd75cc5cb8a1d7bf1d98`. To read it again: a HEAD request to `https://mcr.microsoft.com/v2/azure-cli/manifests/<tag>` with the header `Accept: application/vnd.docker.distribution.manifest.list.v2+json` gives the digest of the manifest list in `Docker-Content-Digest`, and a GET of the same address lists the manifests, of which the one with architecture `amd64` and operating system `linux` is the one to pin. A tag can move and a digest cannot, so the pin is changed by a person, on purpose, with the same two requests. The layers of that image, listed from MCR without running it, hold bash, curl, getent, python 3.12 and jq. They hold no awk, so nothing in the probe uses one.

**The log.** A running container keeps up to 4 MB of log, a stopped one only 16 KB or 1,000 lines ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-resource-and-quota-limits)). So a script prints little (the probe at most 120 short lines, about 12 KB), the tool reads the log every few seconds while the container runs and once more at the end, prints each line once, prints the group's events when the container never started (an image that cannot be pulled is the likely cause), and says when the last read is as long as the limit. The workflow also puts the log into the run's summary.

**Facts about container groups in a virtual network** that shape the design ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-virtual-network-concepts), [Learn](https://learn.microsoft.com/azure/container-instances/container-instances-vnet)):

- The subnet holds container groups only. Learn says that a subnet smaller than /24 is known to run out of addresses, because the platform releases the address of a deleted group slowly, and it names /28 as one of the sizes. A /24 does not fit a small virtual network, so the subnet is the largest the network can spare, a /27 (27 usable addresses), and the probe is run several times in a row to see whether that is enough.
- A group does not take the DNS servers of the virtual network. The tool gives it the landing zone's, which is what lets the name of a private endpoint resolve to its private address.
- Learn says, on two pages, that a NAT gateway is the only supported way out for a container group in a virtual network. The landing zone sends the traffic of a subnet through its firewall with a route table, and the same site documents a container group behind Azure Firewall ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-egress-ip-address), not re-read). Whether the landing zone's route works for a container group is the first thing the probe finds out: the image is pulled through it.
- A Linux container in a virtual network can get a token of its managed identity. Learn says that only Windows containers in a virtual network cannot ([Learn](https://learn.microsoft.com/azure/container-instances/container-instances-managed-identity)).
- The landing zone's network manager puts a route table on the new subnet some minutes after the subnet is made. The template makes the subnet once and leaves it alone ([rule 27](../../AGENTS.md)), and the action `operator` waits until the table is there.

**Identity and roles.** The identity is user-assigned, which is an exception to the owner's preference for system-assigned identities ([changelog](../../CHANGELOG.md), 2026-11-06); the console's sign-in identity is the other one. A system-assigned identity belongs to one container group, and a group exists for the minutes of one run, so every run would make a new identity whose roles have to be assigned and applied before the container can use them, and the changelog gives up to ten minutes for a role to apply. A user-assigned identity is made once, holds its roles, and is attached to each group (inferred: that the roles of a system-assigned identity of a container group cannot be given in advance). It is attached to no app. Each role below goes on one resource and is added with the step that uses it. Each also has to be in the condition of the deploy identity's role-assignment right ([bootstrap](../../environment/BOOTSTRAP.md)): Reader was added to it by a hand step, and Azure Event Hubs Data Sender was in it already (the usage recording gave it to the gateway's identity and, until [the retirement below](#event-hubs-private-only-deployed-and-proven-on-2026-11-06), to the workflow's identity), so the two roles on the control hubs need none (the run of `operator` on the real estate made both with no hand step). Until a role is in the condition, the deploy of that role is refused and nothing else changes.

| Role | Where | What the Operator does with it | Added with |
|---|---|---|---|
| Reader | The project's resource group | Shows that it signs in and can read; reads the telemetry of the two function apps through Azure Resource Manager (the checks of the usage recording and the first cases) | The probe (run twice on 2026-11-06) |
| Azure Event Hubs Data Sender | The two control hubs, `usage-control` and `cases-control`, one role on each hub | Sent the control event that started a copy job or a Watch. Since 2026-11-08 (built, not deployed) the Operator has no role on a hub: its role is *Storage Queue Data Contributor* on the queue `cases-control` alone (wider than a sender needs, because the narrower *Storage Queue Data Message Sender* is not among the roles that the deploy identity may assign; the queue holds only job names and request ids) | The checks (the action `operator`, run on 2026-11-06 with no hand step) |
| Website Contributor | Each of the two function apps | Publishes code with its own token to the private deployment site | The publish step |
| Reader, which the Operator already holds through the group (inferred), and Monitoring Reader only if a read is refused | The component, or a scope above it | Queries the telemetry through the data plane of Application Insights and the Azure Monitor private link, once Application Insights is private | The read step: [what Learn says, and who gives the role](#reading-telemetry-when-the-component-is-private) |

**What the Hub actions will do with it.** An action that only deploys or reads a resource's own properties does not change. These change:

| Hub action | Through the Operator |
|---|---|
| `recording`, `cases` | Publish the code from inside the network, as the deploy identity with the run's token and not with the Operator's own token: the runner sends each app's sources, and the container builds the package and publishes it ([phase 2](#publishing-code-to-the-private-apps-phase-2); done for both apps on 2026-11-06) |
| `recording-check`, `cases-run` | Runs the check tool (`tools/recording-check.py`, `tools/cases-check.py`) in the Operator: it sends the control event with the Event Hubs REST API and a token of the Operator's identity, then queries the telemetry for the answer and prints what the tool prints. Ran on 2026-11-06 and passed, before and after the namespace was made private: [below](#the-checks-of-the-usage-recording-and-the-first-cases-run-in-the-operator). Since 2026-11-08 (built, not deployed) `cases-run` puts the control message in the queue `cases-control` with the Storage queue REST API (Put Message) and a token of the Operator's identity for `https://storage.azure.com/`, through the queue's private endpoint |

**Rule 29.** [Rule 29](../../AGENTS.md) says that no identity of Meternaut holds a role that writes in Azure. Website Contributor writes. The Operator is the deployment workflow's arm inside the network, not a part of the product: the workflow's identity already holds Contributor on the group and can do all of it; the Operator's identity is attached to no app, is used only by a group that the workflow makes, and has the role on the two apps and nowhere else. Whether that is inside rule 29, or the role is given just before a run and taken away after it, is the owner's to say (decisions below). The two roles that exist now do not write in Azure: Reader reads, and Azure Event Hubs Data Sender lets the Operator send events to the two control hubs of Meternaut's own namespace, which is what the workflow's own identity did until [the retirement below](#event-hubs-private-only-deployed-and-proven-on-2026-11-06) took its role away. Like the Foundry User role of rule 30, it is a data-plane right inside Meternaut's own group, over Meternaut's own hubs, that changes no resource in any estate (inferred: that this is inside rule 29; the owner may say otherwise).

## The checks of the usage recording and the first cases run in the Operator

**What changes.** The Hub actions `recording-check` and `cases-run` used to send the control event and read the telemetry from the runner, with the workflow's own token. They now run the same tools, `tools/recording-check.py` (since 2026-11-07 `tools/check-helpers.py`, which holds what the cases check needs of it) and [`tools/cases-check.py`](../../tools/cases-check.py), in the Operator, with the same arguments, so that the Event Hubs namespace can have public access switched off (that switch was [the next change](#event-hubs-private-only-deployed-and-proven-on-2026-11-06), and it is made). One generic script, [`operator/run-tool.sh`](../../operator/run-tool.sh), runs a tool that is in the secret volume. It checks its input before anything runs (the identity's client id, a plain tool name, and arguments made of letters, digits and `. / : _ = -` only, split on single spaces and handed over as separate words: nothing is evaluated or expanded, and a value cannot become a command), signs in with `az login --identity` (three tries, because the first minute of a group can be noisy), runs `python3 /mnt/op/<tool>.py <arguments>` once, hides a string that looks like a token in what the tool prints, and exits with the tool's own exit code. It never runs the tool twice: an event that arrived would start the job twice. The workflow sets `GITHUB_ACTIONS=true` in the container, because the tools refuse to start a job anywhere else (rule 18) and only a run of the Hub workflow makes a group of the Operator.

**It ran, and it passed.** On 2026-11-06 both checks ran through the Hub on the real estate, with the Operator's identity holding Azure Event Hubs Data Sender on the two control hubs: first while the namespace was still public, and again after it was made private. All four runs passed, so the token for `https://eventhubs.azure.net`, the send to the control hub over the private endpoint with the new role, and the telemetry read through Azure Resource Manager with Reader all worked. [What the runs showed](#what-the-runs-showed-on-2026-11-06) has the numbers.

**Why the tools themselves.** The tools use the standard library only, the image has `python3` (3.12) and `az`, and the secret volume takes a file of 400,000 bytes whole (the probe), so the two tools, about 33 KB, travel in the request. The telemetry read has to move into the network as well, because a later step makes Application Insights private. `tools/cases-check.py` loads `tools/recording-check.py` from its own folder, so both files are sent for `cases-run`. The tools have no new option and no new behaviour. CI and the function app use Python 3.13 and the image has 3.12, so a test parses both tools as 3.12 and runs them from a folder that holds only the files that are sent.

**What Reader does here.** The tools query the telemetry through Azure Resource Manager (`POST .../components/<name>/query`), which is a read. Learn lists the operation `Microsoft.Insights/Components/Query/Read` for "Run queries against Application Insights logs" ([Azure permissions for Monitor](https://learn.microsoft.com/azure/role-based-access-control/permissions/monitor#microsoftinsights)), and the built-in Reader role includes `*/read` for the control plane ([built-in roles for General](https://learn.microsoft.com/azure/role-based-access-control/built-in-roles/general#reader)); both were read on 2026-11-06. The Operator holds Reader on the project's resource group already, so the read needs no new role. That the endpoint is authorised by that operation was inferred, and the first `recording-check` in the Operator showed it on 2026-11-06: it read the telemetry with that role and passed.

**What stops working later, and the next step.** A query through Azure Resource Manager "can't use Azure Monitor private links" and works only while the component allows queries from public networks ([Azure Monitor private link design](https://learn.microsoft.com/azure/azure-monitor/fundamentals/private-link-design#control-network-access-to-ampls-resources)). So when Application Insights gets private-only query access, the query of the tools stops working, and they have to query the data plane instead: `https://api.applicationinsights.io/v1/apps/<appId>/query`, with a Microsoft Entra token for that resource (the Operator gets it with `az account get-access-token --resource https://api.applicationinsights.io`) and a read role on the component (the example in [Microsoft Entra authentication for Application Insights](https://learn.microsoft.com/azure/azure-monitor/app/azure-ad-authentication#query-application-insights-by-using-microsoft-entra-authentication) gives Reader on the component, which the Operator's Reader on the group may already be (inferred); a narrower monitoring role is the alternative). The probe showed that `api.applicationinsights.io` is reachable from the subnet. That is the next step, and it is not built here. The list of the functions, `tools/recording-check.py functions` and `tools/cases-check.py functions`, is still made from the runner through Azure Resource Manager before the group is made. It answered for the usage app with its public access Disabled, from outside the network (six functions, on 2026-11-06); for the cases app, which is public, it has not been tried with the app private.

**Time and cost.** The group is given 1,500 seconds for `recording-check` (the tool waits 20 minutes at most for the telemetry) and 2,400 seconds for `cases-run` (30 minutes), and the step is given more than that. The tool deletes the group at the end of every run, and a last step deletes any group named `op-check-<run id>` that a cancelled run left. A stopped container keeps only the last 16 KB of its log, and the tool that polls reads the log every few seconds while the container runs, so the script stays 20 seconds after the tool has ended: the poll then reads the whole log while the container still runs. At most about 4 US cents for a run of `cases-run` ([what it costs](#what-it-costs)).

## What it costs

Container Instances bills the vCPU and the memory of a group for the seconds it exists. The Retail Prices API on 2026-11-06 gives, for Sweden Central and a Linux group, 0.0466 US dollars for a vCPU-hour and 0.00511 for a gigabyte-hour. A group of 1 vCPU and 1.5 GB costs about 0.054 US dollars an hour, so a probe of 10 minutes costs about 0.9 US cents, and 30 such runs a month about 27 cents. The identity, the subnet and its network security group cost nothing. The private endpoints that the later steps add (one for each app, which [phase 1 of publishing code](#publishing-code-to-the-private-apps-phase-1) makes, and one for the Azure Monitor private link scope) cost about 6.57 euros a month each ([the first environment](01-first-environment.md)). Two fallbacks have a standing price, and the probe says whether either is needed:

- A NAT gateway, if the landing zone's route does not work for a container group: 0.045 US dollars an hour, about 33 a month, plus a Standard public IP address at 0.005 an hour, about 3.65, so about 37 a month.
- A private container registry, if MCR cannot be reached from the subnet: Azure Container Registry Premium, which private links need, is 1.67 US dollars a day, about 50 a month, which is the owner's line.

## What the probe checks

[`operator/probe.sh`](../../operator/probe.sh) runs in the container and prints one `ok:` or `FAIL:` line for each check: at most 120 short lines, never a token or a secret, always ending in `probe-done`, and always exiting 0, because the facts are the product. That the image is pulled at all is the first answer, and the tool's events show it when it is not.

| Check | What it shows | What it decides |
|---|---|---|
| The container starts | MCR is reachable from the subnet, and the landing zone's route lets a container group out | Whether the Operator can work at all, and whether a NAT gateway or a private registry is needed |
| `az login --identity`, `az group show` | The identity signs in inside a group in a network, and its Reader role works | Everything else |
| The resolvers, and the names that are passed in | The DNS servers the group got, and whether a private endpoint's name gives a private address | Whether private endpoints can be used from the Operator |
| `management.azure.com`, `login.microsoftonline.com` | The Operator's own calls | Whether it can sign in and call Azure |
| `api.github.com`, `codeload.github.com` | The GitHub API and the repository archive at a commit | Route (a) from the repository |
| `api.github.com` and the host of the workflow artifacts | The download of an artifact that the job uploaded | Route (a) from an artifact |
| `github.com`, the release-asset hosts | A release asset with a public address | Route (b) |
| `pypi.org`, `files.pythonhosted.org` | Installing a package inside the container | Building inside the container |
| `api.applicationinsights.io`, `api.loganalytics.io` | The query endpoints that the read step will use | Whether the telemetry can be read from inside after the private link exists |
| A file of a stated size in the secret volume | How many bytes the request body and the volume carry | Route (c) |

**How the answers choose the package route.** The usage app's package is 7.0 MB zipped and 22.9 MB unpacked (the Azure SDK wheels), so it cannot ride in the request. The cases app's finished package turned out to be too much for a request too: 614,068 bytes zipped, about 200 KB of source and three libraries, and a request with 632,656 bytes of files was refused ([phase 2](#publishing-code-to-the-private-apps-phase-2)). The route that [phase 1 of publishing code](#publishing-code-to-the-private-apps-phase-1) builds on, and that phase 2 runs for both apps, is a build inside the container from sources that do ride in the request, which is why the probe got a second set of checks.

- **(a) The job's own token.** The workflow hands the container its token for the run as a secure value, and the container downloads the package that the job built and uploaded as an artifact, or the repository archive at the commit. The token expires when the job ends, and on a GitHub-hosted runner at the latest after 6 hours ([GitHub docs](https://docs.github.com/en/actions/concepts/security/github_token)). It would need `actions: read` next to `contents: read`. If the API and the artifact host answer, this is the route, and nothing needs to be built in the container. If only the archive host answers, the container would have to build the package itself, which needs the two package hosts and Python 3.13 (the image has 3.12, so the build would have to target 3.13 wheels: inferred): possible, and clumsy.
- **(b) A public repository and a release asset** at a public address. It needs no token, and it also allows the `onedeploy` extension to take that address as its `packageUri`, so that even the publish step would need no Operator (inferred: whether the platform follows the redirect of a release asset is not documented). It needs the owner's decision on visibility, rule 1.
- **(c) A package inside the request**, as a file of the secret volume. It works up to a measured size and no further: a request with 466,104 bytes of files was taken, and one with 632,656 bytes (the cases app's finished package and the container script) was refused with an internal server error ([phase 2](#publishing-code-to-the-private-apps-phase-2)). So it carries sources and scripts, and it does not carry a package of either app.
- **None of them**: if no GitHub host and no size is enough, the usage app has no route until the platform team of the landing zone allows one host, or the owner chooses a private registry.

## Publishing code to the private apps: phase 1

**Why.** The rule ends with both function apps, the usage app on Flex Consumption and the cases app (on a Basic plan when this phase was written, and on Flex Consumption since 2026-11-07), which also serves the console, at public network access Disabled. The workflow publishes their code today from the GitHub-hosted runner, to each app's deployment site, `<app>.scm.azurewebsites.net`. Learn says that with private endpoints and public access disabled that site cannot be reached from outside, and that the machine that deploys needs a network path and DNS to it ([deployment technologies, secured virtual networks](https://learn.microsoft.com/azure/azure-functions/functions-deployment-technologies), read on 2026-11-06). So the code is published from inside the network, by the Operator, in three phases. This is phase 1: it changes nothing about how the code is published and nothing about who can reach the apps.

| Phase | What | State |
|---|---|---|
| 1 | One private endpoint for each app, and a second set of checks in the probe: can the Operator sign in as the deploy identity, build the usage app's libraries and reach the apps' deployment sites. The apps stay public | done on 2026-11-06: the endpoints exist and every check of the probe passed |
| 2 | The two publish steps run in the Operator, as the deploy identity, while the apps are still public, so that the path through the private endpoint is proved with nothing to lose | done on 2026-11-06 for both apps: the usage app at the first attempt, and the cases app at the first attempt after a fix for a request that was too big ([phase 2](#publishing-code-to-the-private-apps-phase-2)) |

**As whom the Operator publishes.** As the deploy identity, which holds the right to write to the apps already, and not as the Operator's own identity. The Operator's identity gets no role that writes, so [rule 29](../../AGENTS.md) stays as it is, and no key, publish profile or personal access token exists ([rule 23](../../AGENTS.md)). Right before it makes the container group, the workflow asks GitHub for a new OpenID Connect token for the audience `api://AzureADTokenExchange`, the one that `azure/login` asks for. The token is valid for five minutes ([GitHub docs](https://docs.github.com/en/actions/reference/security/oidc#methods-for-requesting-the-oidc-token), read on 2026-11-06), which is why it is asked for last and why the probe signs in with it before any other check that uses `az`. The workflow masks it at once and gives it to [`tools/operator-run.py`](../../tools/operator-run.py) in the environment of that one command, as `--secure-env AZURE_FEDERATED_TOKEN`. It is a secure environment variable of the container group, which Azure does not show again, and it is on no command line, in no `--env` value, in no file and in no line that the tool, the probe or the summary prints. In the container, `az login --service-principal --username <client id> --tenant <tenant id> --federated-token <token>` signs in (the option is "Federated token that can be used for OIDC token exchange" in the [Azure CLI reference](https://learn.microsoft.com/cli/azure/reference-index), read on 2026-11-06), with a state folder of its own, so the Operator's own sign-in is left as it is. The two ids are the repository's secrets that the workflow already uses for `azure/login`, and they are not secrets themselves. The Hub job names no `environment`, and its first step, `azure/login`, signs in with a token of the same audience and subject, so the federated credential `github-main` of the [bootstrap](../../environment/BOOTSTRAP.md) accepts this one too, and the probe of 2026-11-06 showed that it does: no hand step was needed (Microsoft Entra's error AADSTS700213 would have meant that the subject did not match). Where the workflow cannot get a token, the probe says why in that one line and goes on with the others.

**The two packages.** Neither package rides in the request: a container group's request takes only a few hundred kilobytes of files ([phase 2](#publishing-code-to-the-private-apps-phase-2) has what was measured), the usage app's package is 7.0 MB zipped, and the cases app's is 614,068 bytes zipped (about 200 KB of source and three libraries; this record first said about 2 MB for it, which was an estimate and was wrong). So each is built inside the container from the hash-locked lock file of its app, with the pip command of [`tools/build-function-app.sh`](../../tools/build-function-app.sh) (wheels for Python 3.13 on Linux, `--only-binary=:all: --require-hashes`), fetched from PyPI, which the probe of 2026-11-06 reached from the subnet. The probe builds the usage app's libraries from the hash-locked `src/usage-functions/requirements.txt` (since 2026-11-07 the probe builds the cases app's libraries from `src/case-functions/requirements.txt`). Only the lock file rides in the request of the probe. The script insists on running under Python 3.13, because pip checks the `Requires-Python` of `azure-functions` 2.x against the interpreter that runs it, and the image has Python 3.12. Whether the build works from 3.12 was the main unknown of this phase, and the probe of 2026-11-06 answered it: it works, and without the flag (what the second probe showed, below). pip is told `--python-version 3.13`, which in its source feeds the resolver's check too (inferred from pip 25.0.1, and the probe confirmed it), so the probe tries that first. If it fails for a reason that `--ignore-requires-python` can change, the probe tries again with the flag and says which of the two it was. The flag is safe only because every version is pinned and every file is checked against its hash. A failure of the network, of a certificate or of a hash is not tried again with the flag.

**What the probe checks now.** One `ok:` or `FAIL:` line each, still at most 120 lines, never a token, always ending in `probe-done`, and still always exiting 0. The checks of [the first probe](#what-the-probe-checks) are all still there.

**Where Learn says something other than the plan assumed.**

- The plan took it that the gateway adds `X-Original-Host` when it overrides the host. Learn says that it inserts the six headers into all requests, so the header is there whether or not the host is overridden. Nothing in this change depends on the difference, and the table follows Learn.
- The plan put the app behind the gateway the way the platform's other apps are put behind it: one backend setting with the host name taken from the backend address. Learn recommends the opposite for a reverse proxy, which is to preserve the host. It calls the override the easiest way, because it needs no custom domain and no certificate on the app, and it gives `forwardProxy` as the workaround for the sign-in. This change follows the platform's pattern and names the other way next, so that the owner can choose it.

**The other way, which Learn recommends, and why it is not chosen.** Preserve the host: attach `<console host name>` to the cases app as a custom domain, validate it with a TXT record, put a certificate for that name on the app (imported from Key Vault, or an App Service certificate: the free managed certificate cannot be used behind a proxy), turn the host override off on the gateway's backend setting and name the host in the probe. The sign-in then needs no `forwardProxy`. What it costs: a certificate and its renewal on the app for a name that is not Meternaut's; the platform's wildcard certificate belongs to the gateway, and moving its private key into the app is the platform owner's decision; a price for an App Service certificate (not read here); and one more thing on the app that the platform's other apps do not have. What it gives: the app sees the real host in every request, so nothing depends on a header. It is not chosen because the platform's other apps use the override and this change follows that. If the first sign-in through the gateway does not work with `forwardProxy`, this is the next thing to try.

**What this does to the security of the console.** The app uses the host in no security decision. The platform's sign-in uses it to build the return addresses that it gives Microsoft Entra, and Entra accepts only return addresses that are registered, so a request with a made-up `X-Original-Host` cannot take a sign-in to another host (inferred from how Entra treats return addresses; not tried). The app trusts that header only because nothing but the gateway is meant to reach it: once the app is closed, its only network path is its private endpoint, which the landing zone's networks reach (inferred). The check of the front door asks what the return address names, so a sign-in that does not read the header is found.

| Backend setting | HTTPS, port 443, the host name picked from the backend address, the probe below, no cookie affinity (the app sets none), and the platform's usual request timeout | App Service routes by the host name that it receives, so the request carries the app's own name, and the original host travels in `X-Original-Host` |
| Custom probe | HTTPS, the host name taken from the backend setting, the path `/healthz`, healthy only when the status is 200 | `/healthz` is the one path that the app serves with no sign-in (`excludedPaths`). The default probe would count the redirect to the sign-in as healthy |
| Routing rule | A basic rule for the listener, with the pool and the setting, and a priority that no other rule has | One rule for each listener |
| DNS record | One CNAME record set for the console's host name in the platform owner's public zone, pointing to the gateway's public name | People resolve the name in public DNS. Meternaut creates no zone ([rule 19](../../AGENTS.md)) |

Two more things are not objects of the gateway: the return addresses in Microsoft Entra (item 4 above), and the repository variable.

**Who adds them, and how.** The objects are outside the project's resource groups, so [rule 15 (b)](../../AGENTS.md) applies: the owner approves each object in plain words first. No workflow of this repository adds them: the deploy identity holds no right at the gateway or in the zone, and gets none. That makes the steps break-glass under [rule 18](../../AGENTS.md). The agent runs them with the owner's own Azure CLI session, on his written word, and reports at once. The owner runs no script. The platform team can add the same objects with its own tools: nothing here needs the agent. The steps read before they write, and every name is a new one (a `create` on a name that exists replaces that object). The DNS write uses `--if-none-match`, so it fails when the record set exists. Nothing is deleted. The same block is in [the bootstrap page](../../environment/BOOTSTRAP.md#changed-on-2026-11-06-the-console-behind-the-platforms-application-gateway), and a test keeps the two equal.


**The order of the steps.**

1. The owner says yes in plain words, to each of the five gateway objects, the DNS record, the return addresses and the variable.
2. The five objects are added (step 2 of the block, after the reads of step 1).
3. The health of the new pool is read (step 3). It has to say Healthy. Anything else is the first answer to the question that is not proven below, whether the gateway reaches the app's private endpoint through the hub, and the work stops here with nothing else changed. What is missing is then a route, a firewall rule or a name resolution of the platform team's. After such a change the gateway may have to drop a cached lookup, and a restart stops every site behind it, so that is the platform team's decision.
4. The DNS record is added (step 4).
5. The name is read from outside, with no sign-in (step 5). Now the whole path has been shown with no change to the app: public DNS, the listener and its certificate, the gateway, the private endpoint and the app's `/healthz`.
6. The return addresses are added in Microsoft Entra (step 6): `check`, and then `apply` with `--apply`.
7. The variable is set (step 7), and `cases` is run. The template writes `CONSOLE_HOST` and the `forwardProxy` setting, the health check runs in the Operator, and the door check knocks at the host name and asks that the return address names it. The agent then runs the browser check of [rule 28](../../AGENTS.md) through the console's host name: it opens a page, posts a form with the same fields to a plan id that does not exist, and requires the console's own "I cannot find this request" page and a POST row in the telemetry, and not an empty 403. It says in the report that this is all that was checked of the approval until the owner has pressed it.
8. Only then, in a change of its own and after the owner's yes: `CASES_APP_PUBLIC_NETWORK_ACCESS` is set to `Disabled`, the test that pins it is changed with it, and `cases` runs once more. After that run Azure shows Disabled, an anonymous request to the app's own public name is refused (as for the usage app), the door check passes through the gateway, and the browser check is made again.

**The way back** is one constant and one run: set `CASES_APP_PUBLIC_NETWORK_ACCESS` back to `Enabled` and run `cases`. The app takes public traffic again, and the console answers on the gateway's host name and on its own. The Operator publishes into the app whichever the value is. To go back further, clear the variable and run `cases`: `CONSOLE_HOST` is then the app's own name and the sign-in has `NoProxy`; the app can stay closed meanwhile, because with no host name the check of its front door runs in the Operator. The platform team removes the five objects by their names. The return addresses of the app's own name were never removed, so the sign-in works on that name at once.

**Cost.** The Retail Prices API (read on 2026-11-06) lists no meter for a listener, a rule, a pool, a setting or a probe of an Application Gateway, so the five objects have no price of their own (inferred from the list of meters). The gateway's own price, 0.26 US dollars an hour for the fixed part of Standard v2 in Sweden Central, is the platform's and is paid already. The capacity units that the console's traffic adds are small for a console that a few people use (inferred, not measured). The DNS record set is within the first 10,000 record sets of a public zone, which the API lists at 0.00. The private endpoint of the app exists already ([phase 1](#publishing-code-to-the-private-apps-phase-1)), and closing the app does not change its price. The health check adds one container group to a `cases` run: at its limit of 1,800 seconds about 2.7 US cents (1 vCPU and 1.5 GB, from the 0.9 cents that ten minutes cost in [what it costs](#what-it-costs)), and a normal run is a tenth of that. Nothing standing is added.

**What is not proven.** None of it has run.

- Whether traffic from the gateway reaches the app's private endpoint. The gateway is in the connectivity network, and the endpoint is in the project's own network, so the traffic crosses the hub. Whether a route, a firewall rule and the landing zone's DNS let it through is not known, and it is the first thing the real set-up shows (step 3 of the order).
- Whether the gateway resolves the app's name to the endpoint's address, which is the central zone's record (inferred), and whether it has to restart to learn it, because the two pages of Learn differ on that: one says a restart may be needed, the other that the gateway refreshes the address after the time to live.
- How the certificate and the host name behave. The listener presents the platform's certificate for the console's host name. The gateway connects to the app on its own name, whose certificate is Microsoft's, and the gateway trusts well-known authorities by default (inferred: no root certificate is set on the backend setting). The runner's check validates the platform's certificate with the Python store, so a certificate from a private authority would make it fail with a certificate error, and it would say so.
- Whether the sign-in redirects as Learn describes when `forwardProxy` is `Custom`: that the redirect to Microsoft Entra carries the console's host name, that the person comes back to it, and that the session cookie is kept for it. Only the first real sign-in shows this. The door check sees the return address in the redirect and nothing after it. The form of the redirect is also not known (straight to Entra, or the sign-in's own address with `post_login_redirect_uri`): the check reads both, and a redirect with no host in it passes and says so. If the return after the sign-in fails, the first thing to try is to add `https://<console host name>/` to `login.allowedExternalRedirectUrls` (inferred: Learn says the current domain is allowed anyway).
- What the gateway does with an `X-Original-Host` that the client sends. Learn says that the gateway inserts the header, and not whether a value that came with the request is replaced. One anonymous request through the gateway with a made-up value shows it: the return address in the redirect must still name the console's host name.
- Whether the sign-in refuses an authenticated POST through the gateway with an empty 403 ([rule 28](../../AGENTS.md)). The sign-in compares `Origin` with something, and which host it compares with is not documented. The browser check after the first deploy with the variable answers it.
- Whether the gateway's request timeout, 20 seconds by default, is enough for every page of the console. The longest request was not measured.
- Whether the list of the app's four functions, which `cases` and `cases-run` make from the runner through Azure Resource Manager, still answers when the app is closed. It did for the usage app.
- WebSockets are not used. The console's content security policy is `default-src 'none'` with styles and form targets only, so a page can run no script and open no connection of its own (read in [`layout.py`](../../src/case-functions/cases/web/layout.py)).

## The web page on the private network (built, not deployed)

**The decision.** On 2026-11-07 the owner decided that the web page does not go behind an Application Gateway: the gateway's health probes keep an app awake, and he wants the app to scale to zero. He reaches the private network himself, so the cases app is closed (public network access `Disabled`) and its private endpoint is its only way in ([rule 15 (c)](../../AGENTS.md): nothing public unless he asks for it). The gateway route of the section above stays built and unused: `CONSOLE_HOST_NAME` stays unset, and nothing of that route is removed.

**What is built.** Nothing is deployed and nothing is closed: no Azure change and no Hub run was made, the cases app is still public, and `CASES_APP_PUBLIC_NETWORK_ACCESS` in [`tools/environment-params.py`](../../tools/environment-params.py) is still `Enabled`. The parameter builder takes `Disabled` with no host name (it refused that), and every other check of `CONSOLE_HOST_NAME` is as it was. A closed app answers nobody outside the network, so the check of the front door cannot knock from the runner. The new output `door_in_operator` of the parameter builder decides where it runs:

| Public network access | `CONSOLE_HOST_NAME` | The check of the front door runs | It knocks at |
|---|---|---|---|
| `Enabled` | not set | on the runner, as before | the app's own name |
| `Enabled` or `Disabled` | set | on the runner, as before | the host name on the gateway, and the sign-in's return address has to name it |
| `Disabled` | not set | in the Operator, in the container group `op-door-<run id>` | the app's own name, which has to resolve to a private address there |

The run in the Operator is the one of the health check: [`operator/run-tool.sh`](../../operator/run-tool.sh) runs [`tools/console-check.py`](../../tools/console-check.py) `door --host <app name>.azurewebsites.net --expect signin|refuse --private`, with that file as the tool in the secret volume and the same limits on the tool's name and arguments as for every other tool that runs there. The answers that it expects do not change: without a sign-in nobody gets a page. The option `--private` is new: a name that resolves to a public address, or not at all, makes no request and fails with a line that says so. The check only reads, sends no credential, and the container gets no token of the deploy identity. It has no second try (each request is tried three times, and `loop-check` repeats the whole check). The group is given 900 seconds and the step 25 minutes, and a step after it deletes any group that is left. It needs the Operator, as the health check does: run `operator` first. Its cost is that of the health check's group at half the limit ([what it costs](#what-it-costs)).

**What closes the web page.** One line, in a change of the owner's own, when he can reach the private address: `CASES_APP_PUBLIC_NETWORK_ACCESS = "Disabled"` in `tools/environment-params.py`, with the one test that pins the value (`tools/tests/test_environment_params.py`). Then the Hub action `cases`: it deploys the app closed, publishes into it from the Operator, waits for its health answer there and knocks at its front door there. Azure then shows `Disabled`, and `loop-check` repeats the check of the front door alone. **The way back** is the constant set to `Enabled` and a run of `cases`.

**What must be true first.** The owner's workstation resolves the app's name to the private address and reaches it on port 443: `nslookup <app name>.azurewebsites.net <the landing zone's DNS server>` has to answer a private address, and a TCP connection to that address on port 443 has to open. **A workstation that is on a corporate VPN can fail to reach the private address although the landing zone's DNS answers it correctly:** the VPN's routes (a broad 10.0.0.0/8) can win over a more specific route, and the VPN's name resolution rules can send the app's domain to another DNS. The two tests tell which of the two it is.

**What is not proven.** None of it has run. Whether the check passes in the Operator against the closed app is shown by the first `loop-check` after the flip (inferred from the usage app, which the Operator reaches over its private endpoint while its public address answers HTTP 403). Whether the owner's workstation reaches the address is his to test, as above. The browser check of [rule 28](../../AGENTS.md) needs the same path from the machine that makes it.

## The web page on Flex Consumption

**The decision (2026-11-08).** The owner ordered on 2026-11-07 that the web page runs on Flex Consumption: an app that serves a page for a few people should scale to zero, and a tool that looks for savings should not carry a cost that it can avoid. The first cases had run there until 2026-11-05, when the platform's front end held some requests to the web page for 15 to 60 seconds and answered some with "The service is unavailable", while the app's own time was 5 to 20 milliseconds ([changelog](../../CHANGELOG.md)). The app was moved to Flex Consumption with a measurement and a way back, and two measurements of 2026-11-08 found the same hold: both fail the rule below. The page was moved to a Basic plan (B1, always on, 13.14 US dollars a month) on the strength of that rule, which was a decision that the owner had not made: **at 09:39 the same morning he ordered the web page back on Flex Consumption, as he had instructed. The constant `CASES_APP_PLAN` is `"Flex"` again, and it goes back to `"Basic"` only on his word:** a measurement that fails the rule is reported to him with its numbers, and he decides. The owner's decision of 2026-11-07 not to put the web page behind an Application Gateway ([the web page on the private network](#the-web-page-on-the-private-network-built-not-deployed)) gave the same reason, an app that scales to zero; this change does not revisit it.

**What was measured on 2026-11-08.** The Flex app had one instance at most, 2048 MB, Python 3.13, the platform's sign-in (Easy Auth), the virtual network integration, and public network access still `Enabled`. Five views of the same hold:

| View | What it showed |
|---|---|
| The action `page-latency`, from the Operator over the app's private endpoint, with no credential: the first run (9 requests) | Median 50.35 s, slowest 60.09 s, 2 requests not 200 (a 503 after exactly 60 s) and 5 slower than 15 s. The times repeat in this order: 0.15 s, 50.35 s, a 503 at 60.09 s, 0.08 s, 50.35 s, a 503 at 60.07 s. After the quiet gap of 4 minutes: 2.13 s, 0.05 s, 50.51 s |
| The same action, the second run (12 minutes, 14 requests) | Median 50.30 s, slowest 60.08 s, 3 requests not 200 (all 503) and 8 slower than 15 s. After the quiet gap of 6 minutes: 2.20 s, 55.4 s, a 503 at 60.08 s |
| A workstation, over the public path: 9 requests to `/healthz`, one after the other | All 200, but 50.6 s each (35.6 s the first) |
| The same workstation, requests at the same time | `/admin/host/ping` 200 in 0.25 s; `/healthz` and a path that does not exist 503 after 60.2 s; `/.auth/me` 401 after 24 s |
| The app's telemetry for the same requests | A duration of 0 s inside the app, and the requests reach the app about 50 s late. No host restart and no worker exit in the traces. The timer `runner-tick` ran on its own instance every minute, in 1.3 s |

The app is healthy, and the hold is in the platform's HTTP path before the app (inferred: nothing inside the app takes 50 seconds). The public path shows it too, so the private endpoint and the Operator are not its cause (inferred).

**The known family.** Two open questions on Microsoft Q&A describe a Python app on Flex Consumption that answers some requests with a 503 after about 60 seconds while it records no failure: [6000597](https://learn.microsoft.com/en-ca/answers/questions/6000597/intermittent-60-second-http-503s-on-azure-function) (a health endpoint that answers in about 100 ms and now and then with a 503 after 60 s, with no failed invocation recorded) and [6052474](https://learn.microsoft.com/en-ca/answers/questions/6052474/azure-functions-flex-consumption-alternating-http) (a 503 after 60.2 s that alternates with a 200 in 0.5 to 1.4 s, and stays when the memory goes from 512 MB to 2048 MB). The replies there, read on 2026-11-08, are suggestions: they name no confirmed cause and no fix. That our hold is the same fault is inferred from the symptom and not shown.

**What explains it, and the setting (2026-11-08, after the owner's order).** The host's own log (Application Insights, the table `requests`) shows that the web page's function was reached at least 60 seconds after the previous request, never sooner (62.3, 69.6, 67.7, 62.4, 62.5, 61.6, 67.6, 63.4, 61.8, 60.8, 60.9 and 121.3 seconds between consecutive requests of one sweep), and the requests that did not reach it were held outside the app for what was left of the 60 seconds and then answered with a 503 or, a little later, with their answer. A sweep from a workstation, with a request a number of seconds after a successful one, got: after 0 s a 503 in 60.8 s; after 10 s a 200 in 52.9 s; after 30 s a 200 in 26.1 s; after 60 s a 200 in 0.7 s; after 120 s a 200 in 1.3 s; after 240 s a 200 in 2.9 s. So one request a minute reaches the app, and the others wait for the next minute. Microsoft's page on concurrency says that a Python app on Flex Consumption has an HTTP trigger concurrency of one by default, whatever the instance size, and the page on scaling says that a maximum instance count that is too low for an HTTP workload can increase latency or cause requests to be rejected ([concurrency](https://learn.microsoft.com/azure/azure-functions/functions-concurrency#http-trigger-concurrency), [limit scale-out](https://learn.microsoft.com/azure/azure-functions/event-driven-scaling#limit-scale-out), both read on 2026-11-08). The app had one instance at most (set on 2026-11-05, when the group had scaled out to four instances for one request every four seconds) and no setting for the HTTP concurrency, so the platform could neither give the group a second request at a time nor a second instance. That this is the whole cause is inferred from the numbers and those two statements: no page says that the wait is a minute. The setting that follows is the HTTP concurrency of the group, `perInstanceConcurrency` under `functionAppConfig.scaleAndConcurrency.triggers.http`, which the template sets to 50 (the one instance takes the requests in its worker; the web page is light). It costs nothing, because Flex Consumption bills for executions and not for a setting, and the app still scales to zero. Whether it removes the hold is measured after the action `cases` has put it in place, and the numbers go to the owner.

**What was not tried.** The cheaper variants of Flex Consumption. An always-ready instance for the group of the web page's functions (the `http` group) would cost about 5 US dollars a month at 512 MB and about 21 at 2048 MB: the meter "Always Ready Baseline" is 0.000004 US dollars per GB-second in Sweden Central in the price snapshot of 2026-10-31 ([`docs/design/cost/prices-snapshot.json`](../design/cost/prices-snapshot.json)), for 730 hours, which is an estimate and not a price read today. It would help only if the hold is the allocation of an instance, and the measurement does not show that: the telemetry says that the 50 seconds pass before the request reaches the app, and not what the platform waits for. At 2048 MB it would cost more than the Basic plan.

**What is built.** One constant, `CASES_APP_PLAN` in [`tools/environment-params.py`](../../tools/environment-params.py), is `"Flex"` (the default) or `"Basic"`, and [`environment/cases/main.bicep`](../../environment/cases/main.bicep) makes the plan and the app of that kind and shares everything else (identities, settings, the private endpoint, the control queue, the roles, the workbook, the sign-in). Basic is the plan `plan-meternaut-cases-basic` (B1) on `snet-cases`, published with a zip deployment. Flex is the plan `plan-meternaut-cases` (FC1), the function subnet `snet-func` (no new subnet: the network is small; the usage recording's app, which was on it, is retired by the action `retire-old`), a package container `app-package-cases` in the storage account that the app reads with its own identity, one instance at most, an HTTP concurrency of 50 (the default of a Python app is one request at a time: [what explains it](#the-web-page-on-flex-consumption)) and no always-ready instance. The Operator publishes the code to a Flex app with `az functionapp deployment source config-zip`, the command that published the usage app's code. For a Flex app the action `cases` reads the subnet before it changes anything, and says which other plan holds it.

**Moving between the two.** An app cannot change from one kind of plan to the other, so the action `cases` clears the ground before it deploys, from the state that Azure shows and not from what an earlier run did: a run that stops half way (the platform answers a delete with a gateway time-out although the delete went through; a deploy is refused) must leave nothing that the next run does not clear. A step before the deploy, [`tools/cases-move.py`](../../tools/cases-move.py), reads each thing as it is now, deletes it when it is in the way, reads it again until it is gone, and prints one line for each: the app, while it runs on the plan of the other kind; the plan of the other kind, by its exact name and while its tier is that kind's (an idle plan bills for nothing, so it does not stay); the private endpoint of the app, when its connection is Disconnected or the app that it points at is not there (a Disconnected endpoint is informative and should be deleted for cleanup, says Microsoft's page on private endpoints, it is billed while it stays, and Azure refuses to change it, which the deploy does every time); and the role assignments that the deploy is about to write, which a preview of the deploy lists (the template names each after the app's id, so Azure refuses to change the identity of one that exists, and a new app has a new identity), when they are not the app's own. Every call that gets a gateway time-out, a bad gateway, an unavailable service or too many requests is made again, up to five times, and a delete that went through anyway is read and counted as gone. A run that stops half way therefore leaves nothing that the next run does not clear, and a move in either direction is the same step. The new app has the same name, so the host name, the sign-in's reply address and the links in the letters stay. **It has a new system-assigned identity**, so what a person gave the old one outside the project's group (Reader and Cost Management Reader, and the right to send letters) is given again, and `foundry` and `aigateway` are run to give it its roles on the Foundry project and on the AI Gateway (the gateway's role is made for the app's principal id, so a new identity has none until `aigateway` has read it from the app; a new role takes up to ten minutes to apply) ([access and onboarding](03-access-and-onboarding.md#the-apps-run-as-system-assigned-identities)). The roles that the Foundry and AI Gateway templates gave the old identity stay as assignments of an identity that is gone (Azure shows them as Identity not found) and harm nothing. The web page is down from the removal until the deploy has finished: a few minutes, and the wait of about ten for the landing zone to register the app's private endpoint. ## Reading telemetry when the component is private

**What changed.** `tools/recording-check.py` (now `tools/check-helpers.py`) and [`tools/cases-check.py`](../../tools/cases-check.py) read the telemetry for their answer: the results of the copy jobs and the History of a Watch. Until now they did that only through Azure Resource Manager, which is the row "Reading telemetry" of the table above. Both tools now take `--query-via arm|data-plane` on `run`, the one subcommand of each that queries. The default is `arm`, so nothing changes while the component accepts queries from public networks. With `data-plane` a tool does four things:

1. It reads the component's Application ID once through Resource Manager (`GET <component id>?api-version=2020-02-02`, the property `AppId`) and keeps it for the rest of the run. It does this before it sends the event that starts a job, so a component that cannot be read stops the run first. The read is on the control plane, which stays reachable while the component is private.
2. It asks the Azure CLI for a token for the resource `https://api.applicationinsights.io`, the way the tools ask for their other tokens. It asks again for each query, keeps no token and prints none.
3. It posts the KQL, as `{"query": "..."}`, to `https://api.applicationinsights.io/v1/apps/<Application ID>/query`.
4. It checks the answer, which has the shape of Resource Manager's (`tables`, each with `columns` and `rows`), and passes the rows on unchanged. A status other than 200, an answer that does not have that shape and a network error each become one short message. The loops that wait for the telemetry keep waiting, as they already do for a query that fails right after a deploy.

A 403 is reported as what it most probably is: the identity has no Reader or Monitoring Reader role on the component or above it (a new role takes minutes to apply), or the component refuses queries from this network. What a service says back is cut to one line, and the token is taken out of it. The tool does not follow a redirect: Python's standard client repeats a POST that was answered with 301, 302 or 303 as a GET at the new address and keeps the `Authorization` header (seen on two local servers), which would hand the token to another host. No API key is used.

The option is for the Operator, inside the network, where `api.applicationinsights.io` resolves to the private endpoint. From the GitHub-hosted runner the name resolves to a public address, and a component that refuses public queries refuses that request. The workflow steps and the Operator script that call the tools with this option are a later change.

## Decisions for the owner

**Phase 1 of [publishing code](#publishing-code-to-the-private-apps-phase-1) changes three of the decisions below.** Its route needs no public repository (the sources ride in the request and the libraries of both apps come from PyPI), no job token in the container (the container gets an OpenID Connect token for the deploy identity instead, which no key replaces and which lives five minutes), and no Website Contributor for the Operator (it publishes as the deploy identity, which holds the right already). The three stay below as they were decided, and matter again only if that route fails.

**A public repository** (rule 1). Needed only for route (b). Cost: none. The way back: none in practice, because published content can be copied. Recommendation: do not decide now. Run the probe first; route (a) needs no change of visibility.

**The job's token inside the container** (rule 23). It is not a key that anyone keeps: it exists for one job. It is a bearer token, though, and whoever holds it can read the whole private repository until the job ends. Whether that counts as "an identity of the run" under rule 23 is the owner's to say (inferred reading of the rule). Way out: route (b) or (c). Recommendation: allow it for the packages of the two apps and nothing else, if the probe shows that route (a) is the only one.

**The Operator's Website Contributor** (rule 29), as above. Recommendation: standing, on the two apps only. The Operator can be used only by a group that the deploy identity makes, and that identity can already do everything the role allows, so a standing role adds no right that the workflow does not hold. Counter-disclosure: it is a standing right to write that a person who may assign that identity could use. The alternative, given just before a run and taken away after it, needs the same entry in the condition and a wait for the role to take effect (inferred).

**The console for people (decided on 2026-11-06).** A private console cannot be opened from the public internet. Two ways were named: a path into the landing zone's network for each approver (a VPN, ExpressRoute, or a machine inside), and a public front end such as Azure Front Door with Private Link in front of it, which is a public endpoint again and costs a standing price. The owner chose neither. His words: "In general, public endpoints are not allowed. You can only connect through gateways (App GW or API Mgmt)." The people reach the console through the landing zone's own Application Gateway, on a host name under the platform owner's domain ([phase 3 for the cases app](#publishing-code-to-the-private-apps-phase-3-for-the-cases-app-the-console-behind-the-platforms-application-gateway-built-not-deployed)). The cases app stays public until the gateway objects exist and the owner has said yes to closing it. **Decided differently on 2026-11-07:** no gateway for the web page; the owner reaches the private network, and the cases app is closed when he says so and his workstation reaches the private address ([the web page on the private network](#the-web-page-on-the-private-network-built-not-deployed)).

**The agents' traces.** Foundry's Basic agent setup cannot send traces to a component whose ingestion is Disabled. Three ways:

| Way | What it gives | What it costs |
|---|---|---|
| No traces from Foundry | The agents run; the History is unchanged | Nothing. The agents' own steps stay in the History that the app writes |
| A separate component for the traces, ingestion public, Microsoft Entra ID only | The traces | One public ingestion point that holds the agents' traces and not the History, and takes no key. A few cents a month. Taken away by removing the connection |
| The Standard agent setup, with a delegated subnet | Traces and agent state inside the network | It needs a Cosmos DB account, a storage account and an AI Search service of the project's own. AI Search Basic alone is 0.101 US dollars an hour, about 74 a month, so the whole is above the owner's line |

Recommendation: no traces from Foundry while the component is private, and a separate component only if the owner wants the traces and accepts one public ingestion point.

**A NAT gateway or a private registry**, if the probe shows that either is needed. Both are named with their prices above. The probe of 2026-11-06 passed without either, so there is nothing to decide now; the paragraph stays for the case that the landing zone changes its route. Recommendation then: the NAT gateway first, because it costs less and the registry also needs an image import.

**The gateway's path to the namespace**, only if the first call through the gateway shows that there is none ([the section](#whether-the-gateway-reaches-the-private-namespace)). A public endpoint is not an option under the rule, so what is asked is a route, a firewall rule or name resolution from the platform team of the landing zone, whose cost and way back are theirs to say. Recommendation then: ask for the narrowest path, from the gateway's network to the namespace's private endpoint and nothing else.

## The order of the work

1. **The identity switch**, in its own change, first. Both steps are merged: both apps run as their system-assigned identities and the grants of the user-assigned ones are retired in the code ([changelog](../../CHANGELOG.md), 2026-11-06). What is left is a person's: deploy it, read it back, and remove the old identities. The roles and the private endpoints below are given to identities, and changing an identity after that repeats them (inferred).
2. **The Operator and the probe** (done). A person registered the resource provider `Microsoft.ContainerInstance` in the project's subscription and added Reader to the deploy identity's condition ([bootstrap](../../environment/BOOTSTRAP.md)). The Hub actions `operator` and `operator-probe` ran, and the probe passed twice ([what it proved](#what-the-probe-proved-on-2026-11-06)). Nothing that was still public had been switched off at that point.
3. **The checks run in the Operator** (done: both passed through it on the real estate on 2026-11-06, before and after step 4). The control event and the telemetry read of `recording-check` and `cases-run` go through the Operator, with Azure Event Hubs Data Sender on the two control hubs ([the section above](#the-checks-of-the-usage-recording-and-the-first-cases-run-in-the-operator)). The order on an estate is `recording`, `cases`, `operator`; then `operator` is run again so that the two roles are assigned, about ten minutes are waited for them to apply, and `recording-check` and `cases-run` are run. Step 4 is not run before both have passed.
4. **Event Hubs private** (done on 2026-11-06). The namespace's public network access is Disabled, read back from Azure, and the deploy identity's right to send to the control hubs is retired by the actions that deployed it. What ran, in this order, and what each run showed is in [the section](#event-hubs-private-only-deployed-and-proven-on-2026-11-06): `recording-check` and `cases-run` through the Operator while the namespace was still public, then `recording`, then `cases`, then `recording-check` and `cases-run` again as the proof. Whether the gateway's loggers still reach the namespace is not known and cannot be tested before a policy of the gateway sends ([the question](#whether-the-gateway-reaches-the-private-namespace)); it is read when the first call goes through the gateway, and it is a change of its own if it asks for one.
5. **The two apps private**, one private endpoint each, with the central zone for App Service sites registered by the landing zone's policy for both records (the app's and the deployment site's: both records of each app were there about 12 minutes after its endpoint was made, on 2026-11-06). It is done in three phases ([above](#publishing-code-to-the-private-apps-phase-1)): the endpoints and a second set of checks in the probe, with the apps still public (done on 2026-11-06: both endpoints exist, and every check of the probe passed); the publish steps through the Operator, still with the apps public (done on 2026-11-06 for both apps: [phase 2](#publishing-code-to-the-private-apps-phase-2)); and then `Disabled` for each app, with the cases app's health check moved inside and its access check made through the gateway's host name. The usage app is done and proven ([the section](#publishing-code-to-the-private-apps-phase-3-for-the-usage-app-deployed-and-proven-on-2026-11-06)); the cases app is built for the gateway and waits for the gateway objects and the owner's yes ([phase 3 for the cases app](#publishing-code-to-the-private-apps-phase-3-for-the-cases-app-the-console-behind-the-platforms-application-gateway-built-not-deployed)). The actions wait for the registration of each app's endpoint before they publish. The console stays public until the gateway objects exist and the owner has said yes. Since 2026-11-07 there is no gateway: the owner closes the app when he can reach its private address, and the check of its front door then runs in the Operator ([the web page on the private network](#the-web-page-on-the-private-network-built-not-deployed)).
6. **Application Insights and the workspace private**, through an Azure Monitor private link scope with one private endpoint. The central zones `privatelink.monitor.azure.com`, `privatelink.oms.opinsights.azure.com`, `privatelink.ods.opinsights.azure.com`, `privatelink.agentsvc.azure-automation.net` and `privatelink.blob.core.windows.net` exist in the hub (the owner's finding), and the built-in policy "Configure Azure Monitor Private Link Scope to use private DNS zones" (`437914ee-c176-4fff-8986-7e05eb971365`, part of the Azure landing zone reference's DNS initiative) has to be assigned in the landing zone: a fact to check, not to assume. The scope starts in Open access mode and moves to Private Only after every resource is in it ([Learn](https://learn.microsoft.com/azure/azure-monitor/fundamentals/private-link-design)). The query of the check tools has to move to the data plane before that ([above](#the-checks-of-the-usage-recording-and-the-first-cases-run-in-the-operator)), and the Foundry decision above comes first. The owner has to decide about the shared Azure Monitor private link scope too (as the session that coordinates the work reported on 2026-11-06): Application Insights and the workspace are still public until then.
