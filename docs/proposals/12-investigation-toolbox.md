# The investigation toolbox — a decision record

**Status, 2026-11-09: ordered by the owner on 2026-11-08 ("build the entire thing"), built the same day with fakes for every call, and deployed with the app. The Investigator used its tools in four real runs on 2026-11-09 (24 to 28 tool calls each); what the tools returned in those runs is not described on this page, and a claim that rests on Microsoft Learn alone says so.** This page records what the Investigator's read-only tools gained, why its reads were slow, and what each tool does not tell. It builds on [the Foundry agents](06-foundry-agents.md) and leaves their rules as they are: the tools only read, give typed values and handles instead of names, and no text from the estate reaches a model.

## The problem

On 2026-11-08 the Investigator found seven things and could analyse none of them: its tools showed no volume, no readers and no deployments. A run also ran out of tool time after about 17 calls: ten subscriptions at 45 seconds a call.

## Faster reads

Measured on 2026-11-08 on the pilot subscription (about 400 resources, read only, with the app's own client code): Resource Graph answers in 0.5 to 1.4 seconds. A Cost Management query for the cost of every resource by service over 30 days takes 6 to 16 seconds cold and 1.6 seconds warm. A second query within seconds gets HTTP 429 with a wait of 2 to 21 seconds, **unless the call carries the header `ClientType`**: with it two queries in a row answered 200 in 2 and 5 seconds. That header is on no Microsoft Learn REST page; it is known from [a Microsoft Q&A answer](https://learn.microsoft.com/answers/a/8268839) and [an issue of the REST API specs](https://github.com/Azure/azure-rest-api-specs/issues/24407), so it is a bet: if Azure ignores it, nothing breaks and the 429 handling stays. The documented limits are 12 query units in 10 seconds, 60 a minute and 600 an hour for a tenant, about one unit for each month of data ([Learn](https://learn.microsoft.com/azure/cost-management-billing/costs/manage-automation)).

| | Before | After |
|---|---|---|
| The count of resources by type, for N subscriptions | N queries of Resource Graph, one after the other | one query for all of them |
| The cost lines of a subscription | read twice a run (the Watch's totals, the tools' lines), each cold | read once, shared by both; the Watch's totals are added up from the same lines |
| Many subscriptions in one call | one after the other, cut at 45 seconds (about 3 to 4 of 10) | four at a time; what is not reached is counted and read by the next call |
| Rows of a listing | cost read for one subscription at a time | the subscriptions that have the type are read together |

Simulated, not measured on ten subscriptions: the real code of both versions against a fake estate with the measured latencies (1 second for Resource Graph, 10 for a cold cost read, all scaled by 1/100). Ten subscriptions: before, the first call read 4 of them (53 s, over the cap of 45) and all ten took three calls and 135 s, with 10 queries of Resource Graph; after, one call read all ten in 47 s (30 s is the ideal, three rounds of four; the rest is thread overhead on a loaded machine), with one query, and in 14 s when the Watch had read the cost lines first. Three subscriptions: 41 s, then 22 s. `test_toolbox_speed.py` proves the call counts and the overlap with fakes. Not done: a read ahead in a second thread (the Foundry client swaps its transport during a call, so a second thread is unsafe) and a cache of whole answers (the data is cached instead).

**When Resource Graph refuses a listing (built 2026-11-11, with fakes, not run in Azure).** `list_resources`, `estate_overview` and the search for one resource of a type ask once for all the subscriptions of the run and for no other: the request names them and no management group. Learn, *Resources - Resources* (2022-10-01) and *Guidance for throttled requests in Azure Resource Graph*, read 2026-11-11: at most 1,000 rows a page, a `$skipToken` that is given back with the same query and the same scopes, and 15 queries in 5 seconds for each user, of which a group costs less than one query for each subscription. When that one question answers an error or a limit (a status from 400), the subscriptions are asked one at a time, in the order of the list. One that is denied or fails is a note and is named in `unavailable` (never counted as having no resource) and is not asked again in the run; when none can be read the answer is `unavailable`, as it was. A limit that still holds for the first subscription stops it, because the quota is the identity's. A row of a subscription that is not on the list is dropped whoever gave it. `test_toolbox_graph.py` holds the pages, a limit, a denied subscription, an outside row and the fallback. What the reads that Resource Graph cannot serve still cost is not changed: the cost lines (Cost Management) and, for each subscription, Advisor and the plans of Defender. Advisor has a table in Resource Graph (`advisorresources`), whose rows were not compared with the answers of the Advisor API, so it is not used.

## The new tools

All are read only, answers are at most 6,000 characters, and every call is on the app's list and a line of [the access file](../../environment/access-requirements.json).

| Tool | Reads | Role |
|---|---|---|
| `data_volume` | what a workspace takes in, by table and day for up to 30 days: its settings and tables (`GET`, 2026-03-01) and its `Usage` records through the query API (`POST https://api.loganalytics.azure.com/v1/workspaces/{id}/query`) | Reader |
| `data_readers` | how many rules (Resource Graph), saved searches, workbooks (2023-06-01) and Sentinel rules (2025-09-01) name each table, and the runs in the query-audit table when it is on | Reader |
| `data_writers` | the data collection rules that send to a workspace (Resource Graph); for one table on the Analytics plan, the resources that wrote most of it on the last day; for any other resource its diagnostic settings (2021-05-01-preview) | Reader |
| `children` | the deployments of an AI services account (2026-09-01; Resource Graph does not list them) as handles with model, version, SKU, capacity, rate limits | Reader |
| `metric_split` | one metric split by one dimension (the metrics read, `$filter=<dimension> eq '*'`, `top`) | Reader |
| `commitments` | cost by pricing model and kind of charge (amortized) and the platform's savings plan (2026-06-01) and reservation (2024-08-01) recommendations | Cost Management Reader |
| `cost_history` | one resource or one type by day for 7 to 90 days, actual or amortized | Cost Management Reader |

`list_resources` and `describe` carry a `reads` field that names the deeper tools of a type, so no description names a kind of resource. A table that the platform made is named; any other is a handle (`t1`), a dimension value that is not a part of the resource is a number or a label, and every text of the estate is counted by code and never shown. Sizes in the properties of gateways and hubs (units, bandwidth, capacity) are shown now: four generic suffixes (`Unit`, `Units`, `Mbps`, `Gbps`) and one exact path were added.

**What the three data tools keep.** Besides the numbers that the Investigator may cite, the record that code checks citations against holds the whole volume of the workspace for the days asked, the kinds of resource of the largest writers of a table on the last closed day (three at most, the largest first), and, for a person's page only, what each table handle stands for. Since [proposal 24](24-priced-findings.md) no code reads the record beyond the citation check: the module that worked out a figure from it for a workspace is gone, and a finding about data that nothing reads is priced from the meters that it names, like any other. The names behind the handles never reach a model.

**Owner hints** are a function, not a tool: `cases/ownership.py`, for the human brief only. The tags of a closed set (owner, contact, team, cost centre, project, environment, created by, manager; at most six, 80 characters each, cleaned) and, from the Activity Log (90 days), who last changed the resource and, when the window shows it, who made it. The orchestrator calls `OwnerReader.hints(resource_id, tags)` once for each case, in `investigate.py::_open_case`; nothing is wired yet. A finding to investigate that covers more than five resources is one case ([the decision brief](09-the-decision-brief.md)), and its hints are those of the dearest of them.

## What each tool does not tell

- **Volume** is what is charged for, hour by hour from the `Usage` table; it says nothing about what the data is for and shows no record. The record keeps the first tables of each read and, apart from them, the whole volume of the last read and the days that it covered; a share is worked out over that whole and from the rows of that read only, never over the rows that an earlier read of other days left.
- **Readers** count a table whose name a text holds. A column that has the name of a table counts too, a text that scans every table names none (counted apart, and added to the number that can be cited), a workbook that takes its workspace from a parameter is not counted, and the audit table holds only what was run while the setting was on (the 300 most run texts are read: when the read returns all 300, a table that none of them names has a null count of runs, and the source says `texts_cut`). Meternaut's own queries carry a marker comment that the count leaves out; whether Azure keeps comments in the audit table is not verified. A kind of data is called unread only when every source was read and every count is zero: a count that could not be made is unknown, so the kind stays in the whole volume and out of the unread.
- **Writers** by table are read only for the Analytics plan: a read of any other plan is charged by what it scans. Diagnostic settings are read one resource at a time, so no tool lists every resource that sends to a workspace.
- **Children** have no cost of their own: Cost Management bills the account.
- **Split** shows at most the number of values asked for and says when it was reached; the platform does not say in which order it cuts.
- **Commitments** do not say how much of a commitment is used: that is read at a billing scope or at the reservation, which no role of this file gives. The lists of reservation orders and savings plan orders are not read: a `200` with an empty list cannot be told from "no right".
- **Cost history** ends on the last closed day; amounts are in US dollars only.

## Access at each level (rule 12)

No new role. Reader already holds `*/read`, which includes reading the data of a workspace ([Learn](https://learn.microsoft.com/azure/azure-monitor/logs/manage-access)): Meternaut asks only for volumes and counts, with queries of fixed text that code made, and a test keeps text of the estate out of them. A workspace set to refuse that read (a protected table or the access mode that needs a data action) answers 403, and the tool says "not visible with this access", never "none". Cost Management Reader holds `Microsoft.CostManagement/*/read` and `Microsoft.Consumption/*/read`; without R2 the cost tools say so. Whether R2 alone shows the recommendations of an enterprise or a customer agreement was not proved: with the owner's rights both lists answered 200 and empty.

## Not verified

The query API of the pilot workspace resolved to a private address that this workstation cannot reach, so its answer shapes come from Learn only. Every call of the table above, with the audit queries, must be run once from the app's network, and the shape of each answer compared with the tests' fakes. What Resource Graph answers when a group holds a subscription that the identity cannot read (an error for the whole group, or only the rows of the others) is not known: the fallback handles both.

## Metrics at the grain that they offer, and the bill by meter (2026-11-17)

**Status: built with fakes; read once against the real estate, read only.**

**The problem.** The Investigator's own notes in eight real runs say that a metric was "unavailable, could not judge use", and its History says that a measurement "hit the budget" before it was made. Two faults sat behind both. `metric_summary` and `measure` asked Azure Monitor for daily buckets with three aggregations for every metric, and Azure answers HTTP 400 for a metric that does not offer that grain or one of those aggregations, or when the metrics of one request have no grain in common; the tool said "unavailable", which an agent cannot tell from a missing measurement. And each metric cost two or three calls, in a run that is limited to about 25 to 40. Read on 2026-11-17, one resource of each of 111 kinds in an estate of ten subscriptions: 65 kinds gave 1,110 metric definitions, of which 3 offer no daily grain and 86 offer the count aggregation alone; 45 kinds answered HTTP 400 that the kind is not a supported platform metric namespace, which the tool took for an error and which says that there is nothing to measure. `cost_lines` showed the cost of a resource but not what it is billed for.

**What changed.**

| Tool | Now |
|---|---|
| `metric_summary`, `measure` | read the definitions of the type once for a run (one resource of the type; `metric_names` shares them) and, for each metric, ask only for the aggregations that it supports and for the grain that it offers: the day, else the largest grain below a day, made into daily buckets by code (`cases/metrics.py`). One call takes up to 8 names (`metrics`); the names that share a grain and aggregations are one request, as the platform asks (at most 20 names; a group that is refused with HTTP 400 is asked again name by name), and a table has a row for each resource and metric. With `grain` set to `hour` a row also has `peak` (the greatest value of any bucket of the finer grain) and `p95` (nearest rank), read at the hour, or at the nearest finer grain that the metric offers, in windows of at most 8,640 points; `read_at` names the grain when it is not a day. |
| `metric_split` | the same choice of grain and aggregations |
| all three | a type that Azure Monitor keeps no platform metrics for answers `no-metrics` (a word of its own, never "unavailable" and never "no data"), asked once for a run; a failed read says `unavailable` with the platform's error code word, never its text, which can carry ids |
| `cost_meters` (new) | what one resource (`handle`) or all resources of one `type` (and one `service`) are billed for in the last 7 to 30 closed days, one line for each meter, dearest first: a meter handle (`m1`, `m2`, ..., the same for the same meter of the same scope for a run), the category, subcategory, name, pricing, charge and unit as the platform words (or `other`), the quantity and cost, the share of the scope, and the daily shape as plain numbers (days with a cost, average, smallest and greatest cost, the spread of the daily cost divided by its mean, how many days ago the first and the last cost were). For a type, how many resources carry each meter, from a second query for the subscription and not one for each resource. The numbers of every meter are in `Toolbox.meters` for the code that prices a change ([proposal 24](24-priced-findings.md): only the meters of a resource itself, read over the full 30 days, count, and the register keeps the longest window that a call read for a meter). |

**What they do not tell.** A metric read at a coarser grain than the question needs says so in `read_at`; the daily buckets of a finer grain are sums, greatest values and means made by code, not what the platform would have averaged. `peak` and `p95` are numbers of the finer buckets that were read, and no verdict: they are not kept in the evidence that code checks citations against, which holds the totals only. `no-metrics` is a fact about the kind, and says nothing about use. A meter line says what is billed, not why; it is Cost Management's actual cost, in US dollars (a scope in another currency is named and never added), and a line that no resource owns has no meter handle. The words of a meter pass the same check as a service name; a few real names do not (20 of 227 meter names in the estate), and are shown as `other`. The summary of a measurement counts it as positive when its total, maximum or average is above 0 (a metric that offers no total has none) and as zero only when none is. The documented limit of the query API is two group by clauses, and `cost_meters` groups by six meter dimensions; the limit is not enforced at subscription scope (a read-only probe on 2026-11-17, api-version 2023-11-01, was answered HTTP 200 for two, three, four, six and seven groupings). If Azure starts to enforce it, the query is refused with HTTP 400 and the tool answers `unavailable` with the platform's code word and never its text, asks again for nothing in that run, and a test pins this (`test_toolbox_meters.py`).

**Access (rule 12).** No new call: the metric definitions and metrics are R1's, and the cost query is R2's, which now also names the read by meter.

**Not verified.** That the platform keeps answering 400 with the text that the tool matches for a kind without metrics (it is a fixed phrase; a different text would make that kind `unavailable` again, which is the safe side). How Azure behaves for a request of 30 days at the grain of one minute for many resources at once: the tool bounds each request and the time of a call, and a real run has not shown the load. Whether the agent uses `grain` and `cost_meters` well: no model was called, and the next run of the actions `foundry` and `cases` makes the new version of the Investigator.

## What a resource is connected to, a picture of a few resources in one call, and how old a resource is (2026-11-17)

**Status: built with fakes, and read once against the real estate, read only and counts only.**

**The problem.** An independent read of the real estate (private, and not copied here) found that most of the waste that could be avoided sits where a quiet resource has to be judged together with what it serves, what serves it and what it was before: the symptom is one resource, and the cause, or the saving, is in the larger thing that it is a part of, or that it serves, or that is attached to it. The Investigator saw one resource at a time, and to judge a whole it needed six to ten calls for each resource, in a run that ends at about 25 calls. A young resource also looked like a forgotten one, because no tool said how old it is.

| Tool | What it gives | Reads |
|---|---|---|
| `neighbors` | what a resource refers to and what refers to it, as tables of handles with the relation (`parent` or `refers`), the cost, the SKU, the kind and the state; for a large set a row for each type and relation, then the handles page by page | one pass of Resource Graph for the run (R1) |
| `profile` | for one to five resources at once: facts, the dearest six meters, every platform metric that has data (the others listed by name), the links, the Advisor items, the history, the parts inside it and where it sends its own data | the reads of the tools that show these, made at the same time |
| `changes` | how old a resource is and what was last written to it, as numbers and the kind of identity as a word | Resource Graph and the Activity Log (R1) |

The function that `profile` is made of, `build_dossier(toolbox, handles, days, grain)` in `cases/dossier.py`, is plain: a later step of the Watch can call it without the protocol of the tools, and a test holds its answer to the tool's.

**`neighbors`.** Resource Graph is read once for the run, for the subscriptions of the run, a page of 1,000 resources at a time with the token of the next page, and each page is walked and dropped: what is kept is the id of each resource and, for every string in its properties that is an id, that string. A string under a key that holds somebody's text (a setting, a tag, a description) is not an id, and such a key is not followed. After the last page each reference is resolved to the longest prefix that is the id of a resource of the run, so that a path into a resource is that resource; a reference to something outside the run is counted and dropped, a reference to itself is ignored, and a part is the `parent` of the resource that holds it. The relation is one of two words of code (`RELATIONS` in `cases/neighbors.py`): `parent` for the structure of an id and `refers` for a reference in a property, and no key of a property is kept or shown (the decision and its reason are at the end of this section). The answer says how many resources and edges were read and how many references pointed outside the run, names the subscriptions that could not be read (never as none), and when a call has no time left says `partial`: the next call goes on from the page where it stopped, and no page is read twice. The quota of Resource Graph is 15 queries in 5 seconds, so a page that leaves one query of it is followed by the wait that the platform's own header gives. Bounds, with what is counted when one is reached: 200 pages, 300,000 resources, 400,000 references, 5,000 values and 10 levels for each resource, and 500 references for each resource (the real estate had one with more than 100, so 100 was too few). The answer holds no name, tag or text, and nothing in it decides: no word says that a resource is idle or an orphan.

**`profile`.** The reads run at the same time, six at most and within the time of one call (`budget_seconds`); a part that did not finish is `unread`, by handle, and a part that failed says `unavailable` or `not visible with this access`. A read that was made and kept is in the answer whatever the time that is left (a bill that was read is never shown as nothing because the call ran long), the links name the subscriptions that could not be read (`unavailable`, as `neighbors` does), and the profile is `partial` for an unread part, for links that are not whole and for a pass that had no time to end. The metrics are batched by the grain and the aggregations that they share, as in the metric reads above; the ones that have data are rows (those with a value above 0 first, then by name) and the others are listed by name. Its answer has a cap of its own, because a picture of five resources does not fit under the 6,000 characters of the other tools: 3,200 characters for each resource and at least 6,000, so at most 16,000 for five (about 4,000 tokens by the usual estimate of four characters for one, not measured), and a longer answer loses its longest list first and counts what it left out. The Foundry client cuts an answer at the cap of its tool (`result_cap`), not at the usual one. Every number that a profile shows is in `Toolbox.evidence` like those of the other tools, so a number that the agent cites verifies.

**`changes`.** Sources: the `systemData` that Resource Graph gives for some kinds (its times and its `createdByType` and `lastModifiedByType`, which are words; its `createdBy` and `lastModifiedBy` are not taken from the answer at all), a creation time among the properties, and the Activity Log that the investigation already reads for the owner record: the tools use a reader that shares what it keeps with that one, so that nothing is read twice, and with a budget of its own (12 reads and 30 seconds), so that an agent that asks for many cannot use up the reads that a case needs for who changed a resource. The kind of identity is `person` (a sign-in name has an `@`), `managed-identity` (the token has the claim `idtyp` with `app` and the claim `xms_mirid`), `application` (`idtyp` alone) or `unknown`; never a name, an address or an id. What no source says is `not-recorded` (unknown, never none), and a log that was read to its end and shows nothing in its 90 days says `over-90`. `written_14d` is true when something was written in the last 14 days, false only when the sources cover them, and `not-recorded` otherwise.

**The Investigator** is told three things in general words (a resource is often a symptom of something larger or a part of it, so follow what it is connected to and judge the whole; one call can show the whole picture of a few resources; say which level you judged and why). They name no kind of resource, no metric and no threshold, and the pin of the length of the instructions is 7,000 characters now (it was 6,500). The lock `agents.lock.json` moved on purpose: the schemas of three new tools, the instructions, the code of the toolbox and the digest of the modules of the tools, which now also holds `dossier.py` and `neighbors.py`. It moved again with the decision on the relation words below: the description of `neighbors` (its schema), the code of the four tools that changed (`neighbors`, `profile`, `changes` and `cost_meters`) and the digest of the modules; the instructions did not change.

**Read once against the real estate (2026-11-17, read only, counts only).** The pass over 10 subscriptions read 1,075 resources in two pages and 2.5 seconds: 1,530 edges, of which 1,374 are `refers` and 156 are `parent`, 79 references that pointed outside the run, 705 resources that refer to something and 576 that something refers to; the largest number of resources that refer to one resource is 168, and the largest number that one resource refers to is 152. (Before the decision below a relation was the key that held the reference: 81 different words and 1,631 edges, because two keys between the same two resources were two edges.) Then, for the first two resources of the kind that the estate has most of, `neighbors` answered in 1 second after the pass, `changes` in 8.5 seconds (the Activity Log is the slow part) and `profile` in 9.4 seconds (3,783 characters; 14 seconds on an earlier run, which also made the first read of the costs): no part was unread, the only words of relation in the answers were `refers` and `parent`, and the metrics, the meters, the links and the history were there. Of 32 resources of 12 kinds, 6 had `systemData` (with the kinds `Application` and `User`), 18 a creation time among the properties (written with 2, 3 or 7 decimals of a second, all read) and 11 neither. In the Activity Log of two days, 521 of 527 events had the claim `idtyp` with `app` and 140 of them also `xms_mirid`; the other 6 had neither a sign-in name nor the claim, so they are `unknown`.

**The relation word is closed (2026-11-17, after an independent review).** The first version showed the key that held a reference as the word of the relation, when the key was a plain name of at most 32 letters and digits. The review put a key of that shape in a map that an owner fills (some resources have maps of custom properties whose keys are the owner's choice), and it reached the model as a relation word: 32 plain letters are enough for an instruction, and rule 26(d) says that no text that somebody wrote reaches a model, never. So no key is kept or shown any more: a relation is `parent` (the structure of an id) or `refers` (a reference in a property), the two words are a constant of code that a test pins, and a test with a 31-character key, in a map of objects and in a plain property, shows that the key is in no answer of `neighbors` or `profile`. What is lost is the platform's word for the kind of link; the types of the two ends already say what is connected to what, and the Investigator does not need more to judge a whole.

**Not proved.** That the Investigator uses the three tools well and that a run needs fewer calls: no model was called, and the next run of the actions `foundry` and `cases` makes the new version. The Activity Log is read in at most three pages, so for a busy subscription the log is often not read to its end and the age of a resource that has neither `systemData` nor a creation time is `not-recorded` (it was for the two resources that a real read tried it on). The parts that Resource Graph does not list as resources of their own (the ones that `children` shows) are not in the pass, so a part has no links. A profile of two resources took 9 to 14 seconds on the owner's machine; one in the run of the Investigator, among its other calls, was not timed. The fixtures of the evaluations (`tools/foundry-evals.py`) answer with no reference, no Advisor item and no age, and a test holds their shape to the real tools; they are not compared for a part of a resource.

**Access (rule 12).** No new call and no new role: Resource Graph, the metrics, the diagnostic settings, the Activity Log and the Advisor items are R1's, the meters are R2's. Without R1 a subscription is named as not read, and with R1 at one subscription only that one is in the pass.

## A property is shown only where the platform lists it (2026-11-17)

**The problem.** A property was shown by the path of its keys. A key was followed when it was a plain name (letters and digits, at most 32 characters) that no list of names for text held, and the last key was shown when it ended in one of 24 generic words (`State`, `Count`, `Enabled` and so on). A map that an owner fills, under a name that is on no list, put his key in front of the model, as a part of a path or as the end of one (`actionProperties.<32 characters of his choice>.enabled`). Rule 26(d) says never, and a list of names is incomplete by nature. The review of the relation word of `neighbors` found the same fault for the relation; this closes it for every property in every tool.

**The decision.** The platform's own list. Azure Policy publishes, for each resource type, the paths of its properties (the *aliases*: `az provider show --namespace <ns> --expand "resourceTypes/aliases"` gives them, and so does one GET of the provider; [Learn](https://learn.microsoft.com/azure/governance/policy/concepts/definition-structure-alias)). A path is shown for a resource only when the list for its type names it, every key of it and the last one too, in lower case and without the marks of an array; a map shows at most as its own name, because the platform lists no key under it, and nothing under it is followed. The list of a namespace is read once in a run (`Arm.provider_paths`), with the subscription of the first resource of it that an answer is about, and several namespaces in one answer are read together. It is kept as sets of tuples of keys, never as the answer, and bounded: an answer of at most 12 million bytes, 120,000 paths for a namespace, three pages, 80 namespaces for a run. When a read fails, or a cap is passed, the answers say `property_list: unavailable`; when the platform lists nothing for a type, `not-offered`. Then only the exact paths of `KNOWN_PATHS` are shown, never the old rule, and no length of a list. The limits of three levels and 32 characters are gone: the list bounds a path. A call that is not a read of the provider itself is refused (`cases/http.py`, one GET, nothing after the namespace). The other ways were weaker: a vocabulary from metric definitions or SKU lists is not a list of property names; a placeholder for the unknown keys would show `actionProperties.*.enabled` and teach the agent nothing; and a longer list of names that hold text is the thing that failed.

**Read on the real estate (2026-11-17, read only, counts only).** 10 subscriptions, 46 namespaces, 111 types, 1,074 resources. All 46 reads answered with the owner's own sign-in (Reader's `*/read` holds `Microsoft.Resources/subscriptions/providers/read`: [Learn](https://learn.microsoft.com/azure/role-based-access-control/permissions/management-and-governance#microsoftresources); the app's own identity was not tried). The largest answer was 5.5 MB (Network: 259 types and 19,370 aliases), then about 0.7 MB (Web, Compute), and most were under 0.5 MB; the time was 0.8 seconds on average and 7.3 for the slowest (Sql), and 37 seconds for all 46 one after the other; none was paged. The path of an alias is in `defaultPath`, and in `paths` for the ones that differ between API versions: both are read. The platform lists 858 types, and every type of the estate was in its namespace's answer.
