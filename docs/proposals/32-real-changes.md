# Real changes: a family that lowers a number of a resource, behind the owner's line — a decision record

**What this document answers.** What Meternaut can now do to a resource that it did not plant (lower a number of it, after a person approves), what stops it, how a change runs, which calls can leave the app, and what is not proved. Written on 2026-11-20. A change is still made by the approver, with the approver's own token and rights ([run as the approver](05-run-as-the-approver.md)).

## Why

On 2026-11-20 the owner read the one request that run 7 made: a finding that was right, and a page that said "Meternaut changes nothing in Azure" and offered no way to act. His words: "I WANT TO BE ABLE TO DO IT!", "You should NOT SPOON FEED how to scale back, Meternaut should learn how to do this as part of its research!" and "Meternaut SHOULD BE ABLE TO DO ALL THIS. Also, it should be able to determine the cost difference." The families of change ([14](14-families-of-change.md)) each know one kind of resource and are held by the planted gate, so none could act on a real resource. This record adds the generic family `change-setting`. The Investigator proposes the setting as data and code checks it (cases/proposals.py); this family makes it. It knows no kind of resource and no setting: [rule 30](../../AGENTS.md) stands whole.

## What the family does, and refuses

It takes the settings that a finding proposes (`proposals.settings`): one to three, each a key path as the tools show it, the value that the tools showed (`from`) and a smaller one (`to`). It lowers numbers only (`0 <= to < from`, finite, a whole number only to a whole number), on one resource, by a path of plain keys with no list in it. **Only a count or a size**: the last key of the path has to pass `proposals.countlike`, the one gate of the AI side as well ([proposal 31](31-proposals.md#which-property-may-be-lowered)): by the toolbox's own ranking of a key a capacity, a count, units, replicas, cores, a size, a throughput or a bandwidth, or a `numberOf…` key, in plain ASCII, and never a period (a retention in days, a `numberOf…` key that ends in days or hours), a version, a state, a flag or the length of a list that the toolbox makes up, and never a setting that decides how much is kept (a path that contains a `retention`, `retain`, `retained`, `keep`, `kept`, `ttl`, `backup`, `snapshot`, `history`, `version`, `restore`, `archive`, `purg`, `recover`, `revision`, `checkpoint`, `softdelete`, `delete` or `logfile` anywhere, in any case and inside another word too: `retentionCount`, `keepcount`, `numberOfDaysToKeep`, `maxHistoryCount`, `recoveryPointCount`; so `maxThrottleCount`, which holds `ttl`, is refused as well, on the safe side; the tuple `KEPT_WORDS` in `proposals.py`, [proposal 31](31-proposals.md#which-property-may-be-lowered)). The list is not complete, as no list of words is: the confirm page, the undo sentence and the approver's own reading of the plan are the other guards. `_countlike` in setting.py is a call of that function and holds no rule of its own; it is asked at the plan and again right before the write. Lowering a retention can destroy what is kept, so it is refused with its own words (`not-a-count`); a lower size or capacity can cut something off too, which is why every change of the family asks once more and its undo says that setting the number back does not bring back what the lower number cut off. A path is relative to `properties`, as the tools show it, except a path whose first key is exactly `sku`, which is at the root of the resource (one test, `words.at_root`, builds the body and the command of the undo). It is matched without case and written with the live spelling. A path that is not in the live resource, runs through a list, or does not hold a plain number equal to `from` is refused. Ids, group names and api-versions are ASCII only (the patterns of the addresses are compiled with `re.ASCII`, and a group is compared on ASCII only): the Kelvin sign U+212A would otherwise be a k.

It cannot change a tier, a flag, a text or a list, and it cannot delete a resource and make it again. A change that is a rebuild is a separate decision, with its own family and its own approval.

When it cannot make a plan, the finding is asked about as before, and the request keeps the reason, one key of `proposals.CANNOT`: `unsupported`, `not-a-count` (new: the setting is not a count of units), `outside`, `switch-off`, `do-not-touch`, `locked`, `busy`, `mismatch`, `unreadable`, `no-version` (new: Azure lists no released version of its interface for the kind), `unsettled` (new: the AI reviewers did not agree, so a person decides first) or `approvers` (new: nobody who may approve is known). A finding that carries settings always gets one of them on the request that asks instead; a test makes each key and holds the table to the keys that it makes. The words of each are in `proposals.py`.

The rules of asking apply to a change as to advice, by the same function (`Approvals._asks`): a finding that no saving was priced for, that cannot say what to look at, that a guard holds back, or about which a person answered within the quiet days (a declined change counts, as a declined advice does; the days count from the answer, and from the day that the request was made when none is on record, so a request that waited forty days and was then declined is quiet for thirty days more) gets no request of either kind. A request of a change about a resource that something that runs by itself changed lately carries the same Heads-up as advice.

## The two lines and the two lists

| | What it is | Who changes it |
| --- | --- | --- |
| `CHANGE_REQUIRES_PLANTED_TAG` (gates.py) | True: every old family changes only what Meternaut planted, with its tag, in a group of `CHANGE_SCOPES`. Untouched. | The owner, in a pull request that he reviews himself |
| `REAL_CHANGES_ALLOWED` (gates.py) | False: no real resource can be changed. It is not a setting and no variable reaches it. A test pins it False and pins its comment. | The owner, in a pull request that he reviews himself |
| `CHANGE_SCOPES` | The groups of Meternaut's own planted waste. The rules of asking leave a case alone there. | The template: the project's own group |
| `REAL_CHANGE_SCOPES` | The groups of the owner's real resources, `<subscription id>/<resource group>` separated by commas, empty by default. A secret of the environment `hub`, because it names subscriptions (rule 18 (b)). | The owner |

A group is in one list and never in both: the settings refuse it, and so does the parameter builder (it also refuses the project's own group, and a repeat). A deploy with nothing set changes nothing: the builder writes `realChangeScopes` only when the secret is set, and the template writes the app setting only then.

## How a change runs

1. **The plan** (the Watch, with the app's reader, reads only): first the settings, with no read (`unsupported` for a number that does not go down, a flag, a text, a list or a path that is not plain words; `not-a-count`), then the gates in the order `outside`, `switch-off`, then the do-not-touch note, then the provider's list of api-versions (`GET /subscriptions/{id}/providers/{namespace}?api-version=2021-04-01`: the newest version of the resource type that is not a preview; none is `no-version`), then the resource at that version and its locks, then `busy` (a provisioning state that is not Succeeded) and `mismatch` (a live value that is not `from`), and `unsupported` again for a path that is not in the resource or is no plain number. The rules of asking come before every read. Code writes every sentence from typed facts. The saving is the case's, computed from the bill by code.
2. **The request** keeps the start of its wait. A request that only asked is taken back in the next Watch, with the reason `upgraded` ("Meternaut took this request back, because it can make this change itself now"), when the change can be made (the line was switched on, the group was listed, the facts changed), and the change takes its place with the same start of waiting ([rule 38](../../AGENTS.md)); the new request is announced like any new request of a change, once. The page of the old request names the new one as a link with its title, and the History shows the old one as a line of its own ([proposal 09](09-the-decision-brief.md)). An open change that no longer holds is taken back the same way (`changed`, or `left-alone` when a person marked the resource do-not-touch) and replaced by the plan that can be made, or by advice made as any other advice (`Approvals.advise`: its rules and the quiet days hold it back too, and then nothing takes its place). A reading of Azure that fails, or a resource that is being changed right now (`busy`), takes nothing back. A change request is taken back only for a reason that is true (a do-not-touch mark, a changed live value, a lock, the line or the group closed, the count gate, which also judges the request's own numbers, so that a request made under an older gate is taken back when today's refuses it), and never because a price is missing; the reasons that need no read (the mark, the line, the group, the count gate) are checked first, so that no other request open for the resource and no missing reader hides them: the rules of asking decide whether a request is made, not whether the one that was made still holds, so a later judgment with no price leaves the open change as it is, with its wait, and the case keeps what the request was asked with (`Approvals.asked_saving` counts the change as it counts advice). A request that is taken back because the numbers changed is replaced only when the rules of asking let a new one through. No clock closes anything.
3. **The approval** is the sign-in of the person, as for every family, and **every change of this family asks once more first** (the flag `confirm` of its words): the page of the request opens a second page, "This changes a real resource. Nothing is changed until you confirm here.", and the card asks twice itself. The sign-in's code builds, for that one request, a client whose list holds reads only and whose one write is the plan's own PUT.
4. **Right before the change**, with the approver's token: the same resource in a real group while the line is on; the settings are still counts of units; no lock on the resource or its group; no do-not-touch note; the last operation worked; every number is as it was; and each cited measurement, read again with the same name over the same number of days, is not above what the plan recorded. A reading that cannot be made counts against the change. Any failure stops it, nothing is written, and the request is open again.
5. **The write:** the resource is read once more as late as it can be, the numbers are set in that body, and it is sent back with a PUT, once, with `If-Match` set to the ETag of that reading (the header, else the `etag` of the body): a resource that changed or was deleted since is refused by Azure (412), and the request is open again with the plain words "the gateway changed while Meternaut was about to change it"; nothing is written and nothing is tried again. A provider that returns no etag has the short window between that reading and the PUT, and no header is sent. A 401 with a claims challenge is handled as for the other families. The status address of the operation is followed with the same token, for half a minute; after that the timer reads the resource with the app's reader and settles it. **What is kept of the body that was sent** (a short hash of each part that holds a number or a boolean, at most 120, in the action) is what the check compares afterwards. A text is neither kept nor compared: six hex digits of an unsalted hash would let a low-entropy text of the approver's reading be confirmed by guessing, and Azure rewrites texts (a timestamp, a state) by itself, which would be no difference to report. A list is compared as a multiset, so that a reorder is no difference and a changed item is. The check is: the live values equal `to` and the provisioning state is Succeeded (done), Updating (pending), Failed or Canceled (failed), anything else unknown; a number that is neither the old one nor the new one when Azure shows the state Succeeded is failed, in words, and with no state shown it stays pending and the timer reads it again. When it is done, every other number and boolean that was sent is compared with what is shown now: a difference is said ("Azure also changed: properties.x.") and the request is **done with a difference**, never "done and checked"; what Azure adds that was not sent is no difference. It never writes. The cost check is the one of a change that leaves the resource billing (the daily rate after against the one before).

## Decisions about the PUT body and the api-version

- **The api-version** is read at plan time and stored in the plan; the PUT uses it and no other. A preview is never used.
- **The body** is the resource as it was read, with the numbers changed and nothing else, without `id`, `name`, `type`, `systemData` and `etag` at the root and without the `provisioningState` that is a direct child of the root `properties` (Azure puts it there; one anywhere else, at the root too, is a value like any other and is sent as it was read). Nothing deeper is touched, whatever its key is called: a part of the resource with its own `etag`, `provisioningState` or `systemData` (a sub-resource), the `tags` and a free-form map (one with a `name` key, a map of headers, a map under a key called `properties`) are sent back as they were read, as `az resource update` sends them, so that no value that somebody set is taken out because its key looks like one of Azure's. The resource provider rules of Azure Resource Manager (the RPC, v1.0, read on 2026-11-20 in a public copy of it) say that `name`, `type` and `id` belong to a GET and that a PUT that carries `provisioningState` is to be treated as one that carries a read-only property, so a state or an etag that is sent back is ignored by the provider. Everything else is sent as it was read, including `location`, `tags`, `sku`, `identity`, `zones` and every list. The provisioning state is found in any case, under `properties` and at the root, and the one that is not Succeeded counts.
- **No PATCH**: many providers allow tags only. **`If-Match`** is the ETag of the reading that the body is made from (the header `ETag`, else the `etag` of the body), so that a change in between is refused by Azure (412) and a resource that was deleted in between is not made again by the PUT; the one-request client allows the same address and method as before, and only a header is added. A provider that returns no etag has the short window of that reading, and no header is sent.
- **The undo** takes the raw numbers (1440, not 1,440; 0.125, not 0.12) and puts a path at the root by the same test as the body (exactly `sku` as the first key), and a card and a letter say a short undo, never cut: the first sentence ("Set scale units to 4 again in the Azure portal."), the caveat ("It does not bring back what the lower number cut off meanwhile.") and where the command is ("The page has the command."): a command is never cut in half. The page has the whole command. It says too that setting a number back does not bring back what the lower number cut off meanwhile.
- **The order of the reasons**: the setting is judged first, with no read (`unsupported`, `not-a-count`), then `outside` and `switch-off`, then the rest as in the first step above. (This record said before that `outside` came first; the code judges the setting first, because that needs no read, and the record was changed to say so.)

## The calls that can leave the app

| What | Calls | Token | Held by |
| --- | --- | --- | --- |
| The named writes (`calls.WRITES`) | Eleven, each on one kind of resource, unchanged: DELETE disk, public IP address, snapshot, network interface, NAT gateway, load balancer and private endpoint; POST deallocate and PATCH of a machine; PATCH of a disk; PUT of the one kind of gateway that proposal 14 names | the approver's | the static client of the console, groups of `CHANGE_SCOPES`, planted gates |
| The one write more (`calls.RESOURCE_PUT`) | PUT of the resource that the approved plan names, at the plan's api-version, compared as a whole address | the approver's | the client of that one request (`calls.one_write`), a group of `REAL_CHANGE_SCOPES`, the line; no address while the line is off |
| Reads of the real groups | GET of a resource of the top level of a real group, its metrics, the locks of the subscription, the group and the resource, the provider's list of resource types of a real subscription; the status of an operation of that resource's provider (the one-request client only) | the reader's, or the approver's | `read_calls(scopes, real)` and `one_write` |

The static client of the console holds nothing of the real groups and no generic write. Everything else that leaves the app (the store's tables, the Foundry project, the AI Gateway, the Teams queue and bot, Microsoft Graph, the Watch's reads) is on its own list and is untouched.

For a finding about a bastion-like resource of an invented provider whose `scaleUnits` goes from 4 to 2, cited measurement `Sessions` at 0 over 30 days: "Scale down the bastion host bas-hub in resource group rg-network: scale units from 4 to 2" (the title that a page, a card and a letter show leaves out the group, which the line under it names); the question: "You are asked whether to let Meternaut scale down the bastion host bas-hub in resource group rg-network by lowering scale units from 4 to 2."; "When you approve, Meternaut sends the bastion host bas-hub in resource group rg-network back to Azure as it was read, with this change, scale units from 4 to 2. It uses your own permissions. A property that Azure does not show when it is read is not sent, so Meternaut cannot promise that nothing else changes. Afterwards it reads the bastion host again and checks the number, and that every other number and flag that it sent is still what it sent. It does not compare texts, such as a tier or a name."; "Right before it acts, Meternaut reads the bastion host again. ## What is not proved

- It has never changed a real resource. It is built and tested against fakes of Azure, with an invented kind, and no call of it has been made to Azure.
- **Whether Azure accepts the PUT body for each provider.** A provider whose GET leaves out a property that only a PUT can set (a password, a key) would receive a body without it, and may refuse it or reset the property. The family cannot know which properties are write-only, and cannot see a property that Azure does not return: the plan says so, and the check afterwards compares only the numbers and booleans that were sent. It compares a short hash of each part of the body that holds one, down to a depth that keeps the record small (at most 120 parts, and a part below that depth as one), so a difference is named by the part that holds it; a text is not compared, so a timestamp or a state that Azure rewrites is no difference, and neither is a text that a PUT silently changes (a limit of this check). The first use on a real resource is a decision of the owner, with the group listed for that one resource first.
- **Whether the re-check of the cited measurement holds.** It reads the metric again over the same number of days, so a steady series that is not zero may be a little above the number that the plan recorded and stop the change (the request is then open again, and nothing changed). A measurement that is not a plain Azure Monitor metric name is not read again, and one that cannot be read counts against the change.
- The operation status addresses of providers that put them elsewhere than under the subscription's locations or under the resource are not followed: the progress is then not read and the timer reads the resource instead.
- That the proposals of the Investigator ([proposal 12](12-investigation-toolbox.md)) name settings that this family can make; that the lower number is safe for what uses the resource (the plan says that Meternaut does not know, and what it checked).

## The text of rule 39 of AGENTS.md (added on 2026-11-20)

> 39. **Meternaut may lower a number of a real resource, after a person approves it, behind two gates that only the owner opens** (2026-11-20, the owner, after he read the request that run 7 made: "I WANT TO BE ABLE TO DO IT!"; "You should NOT SPOON FEED how to scale back, Meternaut should learn how to do this as part of its research!"). The family `change-setting` (proposal 32, `docs/proposals/32-real-changes.md`) lowers one to three counts or sizes (a capacity, a count, replicas, units: never a period, a version, a state, a flag or a setting that decides how much is kept, such as a retention, a backup or a snapshot) of one resource that a finding proposed as data and code checked, by a PUT of the resource as it was read, with the approver's own token (rule 29): no identity of Meternaut gets a right that writes. It asks the person once more before the sign-in, for it never promises that nothing else changes, and it says afterwards when Azure also changed another number or flag that it sent (it does not compare texts). **Gates:** the line `REAL_CHANGES_ALLOWED` in `cases/families/gates.py` is False, and only the owner may change it, in a pull request that he reviews himself; it is not a setting and no variable reaches it, and a test pins it and its comment. The list `REAL_CHANGE_SCOPES` (a secret of the environment `hub`, empty by default) holds the groups of his real resources, and a group is never also in `CHANGE_SCOPES`. With the line False or the list empty no real resource can be changed. Rule 26 (a) and the line `CHANGE_REQUIRES_PLANTED_TAG` stand whole for every other family. **One request, one write:** the change is made by a client that the sign-in's code builds for that one request; its list holds reads only and its one write is the PUT of the plan's own resource at the plan's api-version, compared as a whole address. The static client of the console holds no real group and no generic write. **What stays:** rule 30 (no instruction, tool description or document names a kind of resource, a setting or a limit); the family changes numbers that go down and nothing else (no tier, flag, text, list, delete or rebuild); a plan is written by code; a request that waits is never closed by a clock (rule 38) and keeps its start when a request that only asked becomes the request of the change.
