# Real changes: a family that lowers a number of a resource, behind the owner's line — a decision record

**What this document answers.** What Meternaut can now do to a resource that it did not plant (lower a number of it, after a person approves), what stops it, how a change runs, which calls can leave the app, and what is not proved. Written on 2026-11-20. A change is still made by the approver, with the approver's own token and rights ([run as the approver](05-run-as-the-approver.md)).

## Why

On 2026-11-20 the owner read the one request that run 7 made: a finding that was right, and a page that said "Meternaut changes nothing in Azure" and offered no way to act. His words: "I WANT TO BE ABLE TO DO IT!", "You should NOT SPOON FEED how to scale back, Meternaut should learn how to do this as part of its research!" and "Meternaut SHOULD BE ABLE TO DO ALL THIS. Also, it should be able to determine the cost difference." The families of change ([14](14-families-of-change.md)) each know one kind of resource and are held by the planted gate, so none could act on a real resource. This record adds the generic family `change-setting`. The Investigator proposes the setting as data and code checks it (cases/proposals.py); this family makes it. It knows no kind of resource and no setting: [rule 30](../../AGENTS.md) stands whole.

## What the family does, and refuses

It takes the settings that a finding proposes (`proposals.settings`): one to three, each a key path as the tools show it, the value that the tools showed (`from`) and a smaller one (`to`). It lowers numbers only (`0 <= to < from`, finite, a whole number only to a whole number), on one resource, by a path of plain keys with no list in it. A path is relative to `properties`, as the tools show it, except a path that starts with `sku`, which is at the root of the resource. It is matched without case and written with the live spelling. A path that is not in the live resource, runs through a list, or does not hold a plain number equal to `from` is refused.

It cannot change a tier, a flag, a text or a list, and it cannot delete a resource and make it again. A change that is a rebuild is a separate decision, with its own family and its own approval.

When it cannot make a plan, the finding is asked about as before, and the request keeps the reason, one key of `proposals.CANNOT`: `unsupported`, `outside`, `switch-off`, `do-not-touch`, `locked`, `busy`, `mismatch`, `unreadable` or `no-version` (new: Azure lists no released version of its interface for the kind). The words of each are in `proposals.py`.

## The two lines and the two lists

| | What it is | Who changes it |
| --- | --- | --- |
| `CHANGE_REQUIRES_PLANTED_TAG` (gates.py) | True: every old family changes only what Meternaut planted, with its tag, in a group of `CHANGE_SCOPES`. Untouched. | The owner, in a pull request that he reviews himself |
| `REAL_CHANGES_ALLOWED` (gates.py) | False: no real resource can be changed. It is not a setting and no variable reaches it. A test pins it False and pins its comment. | The owner, in a pull request that he reviews himself |
| `CHANGE_SCOPES` | The groups of Meternaut's own planted waste. The rules of asking leave a case alone there. | The template: the project's own group |
| `REAL_CHANGE_SCOPES` | The groups of the owner's real resources, `<subscription id>/<resource group>` separated by commas, empty by default. A secret of the environment `hub`, because it names subscriptions (rule 18 (b)). | The owner |

A group is in one list and never in both: the settings refuse it, and so does the parameter builder (it also refuses the project's own group, and a repeat). A deploy with nothing set changes nothing: the builder writes `realChangeScopes` only when the secret is set, and the template writes the app setting only then.

## How a change runs

1. **The plan** (the Watch, with the app's reader, reads only): the settings, then the gates in the order `outside`, `switch-off`, then the do-not-touch note, then the provider's list of api-versions (`GET /subscriptions/{id}/providers/{namespace}?api-version=2021-04-01`: the newest version of the resource type that is not a preview; none is `no-version`), then the resource at that version and its locks, then `busy` (a provisioning state that is not Succeeded), `mismatch` (a live value that is not `from`) and `unsupported` for what is not as the plan needs it. Code writes every sentence from typed facts. The saving is the case's, computed from the bill by code.
2. **The request** keeps the start of its wait. A request that only asked is taken back in the next Watch, with the reason `upgraded` ("Meternaut took this request back, because it can make this change itself now"), when the change can be made (the line was switched on, the group was listed, the facts changed), and the change takes its place with the same start of waiting ([rule 38](../../AGENTS.md)). An open change that no longer holds is taken back the same way (`changed`) and replaced by the plan that can be made, or by the request that asks. No clock closes anything.
3. **The approval** is the sign-in of the person, as for every family. The sign-in's code builds, for that one request, a client whose list holds reads only and whose one write is the plan's own PUT.
4. **Right before the change**, with the approver's token: the same resource in a real group while the line is on; no lock on the resource or its group; no do-not-touch note; the last operation worked; every number is as it was; and each cited measurement, read again with the same name over the same number of days, is not above what the plan recorded. A reading that cannot be made counts against the change. Any failure stops it, nothing is written, and the request is open again.
5. **The write:** the resource is read once more as late as it can be, the numbers are set in that body, and it is sent back with a PUT, once. A 401 with a claims challenge is handled as for the other families. The status address of the operation is followed with the same token, for half a minute; after that the timer reads the resource with the app's reader and settles it. The check is: the live values equal `to` and the provisioning state is Succeeded (done), Updating (pending), Failed or Canceled (failed), anything else unknown. It never writes. The cost check is the one of a change that leaves the resource billing (the daily rate after against the one before).

## Decisions about the PUT body and the api-version

- **The api-version** is read at plan time and stored in the plan; the PUT uses it and no other. A preview is never used.
- **The body** is the resource as it was read, with the numbers changed and nothing else, without `id`, `name`, `type` and `systemData` at the root and without `etag` and `provisioningState` at any depth. The resource provider rules of Azure Resource Manager (the RPC, v1.0, read on 2026-11-20 in a public copy of it) say that `name`, `type` and `id` belong to a GET and that a PUT that carries `provisioningState` is to be treated as one that carries a read-only property. Everything else is sent as it was read, including `location`, `tags`, `sku`, `identity`, `zones` and every list.
- **No PATCH**: many providers allow tags only. **No `If-Match`**: not every provider checks it, a PUT without it is 200 on a resource that exists, and the resource is read again just before the PUT.
- **`outside` is said before an unsupported setting** when both hold, because the first needs no read of the finding's own data; the order is the one that the owner takes: list the group, switch the line on.

| What | Calls | Token | Held by |
| --- | --- | --- | --- |
| The named writes (`calls.WRITES`) | Eleven, each on one kind of resource, unchanged: DELETE disk, public IP address, snapshot, network interface, NAT gateway, load balancer and private endpoint; POST deallocate and PATCH of a machine; PATCH of a disk; PUT of the one kind of gateway that proposal 14 names | the approver's | the static client of the console, groups of `CHANGE_SCOPES`, planted gates |
| The one write more (`calls.RESOURCE_PUT`) | PUT of the resource that the approved plan names, at the plan's api-version, compared as a whole address | the approver's | the client of that one request (`calls.one_write`), a group of `REAL_CHANGE_SCOPES`, the line; no address while the line is off |
| Reads of the real groups | GET of a resource of the top level of a real group, its metrics, the locks of the subscription, the group and the resource, the provider's list of resource types of a real subscription; the status of an operation of that resource's provider (the one-request client only) | the reader's, or the approver's | `read_calls(scopes, real)` and `one_write` |
| Reads of the planted groups | The named kinds, the sizes of a machine, the metrics of a gateway, the locks, the quota | the reader's, or the approver's | unchanged |

The static client of the console holds nothing of the real groups and no generic write. Everything else that leaves the app (the store's tables, the Foundry project, the AI Gateway, the Teams queue and bot, Microsoft Graph, the Watch's reads) is on its own list and is untouched.

## An invented example, in the words of the plan

For a finding about a bastion-like resource of an invented provider whose `scaleUnits` goes from 4 to 2, cited measurement `Sessions` at 0 over 30 days: "Scale down the bastion host bas-hub in resource group rg-network: scale units from 4 to 2"; "When you approve, Meternaut sends the bastion host bas-hub in resource group rg-network back to Azure as it was read, with this change: scale units from 4 to 2. It uses your own permissions, and nothing else of the bastion host changes."; "Right before it acts, Meternaut reads the bastion host again. It stops unless the bastion host still shows the old numbers, its last operation worked, it has no lock and no do-not-touch note, and it is in a resource group on the owner's list for real changes. It also reads Sessions again over the same number of days, and stops if the reading is above what this request was made with."; "Meternaut does not know what a lower number takes away from what uses the bastion host. What it checked: Azure Monitor shows Sessions at 0 over 30 days, and that no lock is on the bastion host. Azure carries out the update in the background and may need minutes: Meternaut follows it for half a minute, and a later check reads the bastion host again. If your account may not change the bastion host, Azure refuses and nothing changes."; undo: "Set scale units to 4 again: on the page of the bastion host in the Azure portal, or with az resource update --ids <resource id> --set properties.scaleUnits=4 --api-version 2024-05-01. That update takes minutes too and needs the same right."

## What is not proved

- It has never changed a real resource. It is built and tested against fakes of Azure, with an invented kind, and no call of it has been made to Azure.
- **Whether Azure accepts the PUT body for each provider.** A provider whose GET leaves out a property that only a PUT can set (a password, a key) would receive a body without it, and may refuse it or reset the property. The family cannot know which properties are write-only. The first use on a real resource is a decision of the owner, with the group listed for that one resource first.
- **Whether the re-check of the cited measurement holds.** It reads the metric again over the same number of days, so a steady series that is not zero may be a little above the number that the plan recorded and stop the change (the request is then open again, and nothing changed). A measurement that is not a plain Azure Monitor metric name is not read again, and one that cannot be read counts against the change.
- The operation status addresses of providers that put them elsewhere than under the subscription's locations or under the resource are not followed: the progress is then not read and the timer reads the resource instead.
- That the proposals of the Investigator ([proposal 12](12-investigation-toolbox.md)) name settings that this family can make; that the lower number is safe for what uses the resource (the plan says that Meternaut does not know, and what it checked).
