## 2. Rules that bind every sentence

- **Audience.** A platform team and a FinOps lead at an adopting organisation who will build the system from `docs\design\` (technical design) and `docs\experience\` (what people see), and a contributor who wants to know where to start. A stranger must be able to read it cold, with no memory of any conversation.
- **AGENTS.md binds the plan** (read it): write for the community (no "the operator", nothing about any person's tenant, landing zone, licences or preferences; say "the adopting organisation"); never harden a hedge into a constraint; no conversation residue and no review history in the plan (history lives in `docs\reviews\`); no assumptions section and no form-style risk register (risks appear where they matter, with what is done about each); examples are invented and labelled as such; never the two original findings; no lab, exam, Terrarium, wind tunnel, time machine, learner; "agreement", never "contract", for an Azure agreement (the hub's "contract" is the design's own word and stays); never mention Fabric or Databricks; pictures show loops, hubs, parallel work or state changes, never one linear pipeline (Mermaid, at most 15 nodes).
- **Words.** Use the design's words (Hub, contract, hosted agent, Evaluate and Operate profile, capability profile, cost lake, Estate model, Atlas, Detector, Case, Credential, R1 to R3, proof points P1 to P10, the Unexplained Spend list, the Agenda). Define no new term. Avoid jargon a stranger would not know: do not write "walking skeleton", "spike", "fold", "shift left", "hardening", "dogfooding", "burn-down" or "yak"; say what the thing is. "Drill" is the design's word for a rehearsed failure. Write "written down before the measurement", never "pre-registered".
- **Numbers.** Sizes are **person-weeks, scenario parameters** (starting estimates for a team that knows Azure Functions, Bicep and the Agent Framework), replaced by measurement. Every number the plan gives for a pass condition, a margin, a budget or a time window is labelled **starting value**, and the plan says that each is written into `evaluation/` by a pull request before the measurement, never after. The plan **never types a euro figure of its own**: cloud cost is stated by pointing at `docs\design\10-cost-and-finops.md` (its Pilot, Team and Enterprise columns and its sensitivity table).
- **Facts about Microsoft products** are verified on Microsoft Learn the day you write them. The facts in section 3.9 were verified on 2026-11-02; reuse them with their links and check any other you add.
- **No invention.** Do not assert what an adopting organisation owns, licenses or has. Name the person or team who can grant each request and what to ask for; where a choice has no safe default, say it is required and who makes it.
- **Pictures.** README: one hub-and-spoke picture. `01`: a dependency picture and a state diagram of a slice's life with back-edges. Both Mermaid, quoted labels, at most 15 nodes, no single chain.

## 3. Settled content

### 3.1 The phases and their exits (from `docs\design\13-roadmap.md`; do not change)

- **Phase 0 foundations.** Exit: P1, P2 and P9 pass; a fresh deployment of dev from scratch works; the isolation test (dev cannot reach prod) passes. The plan adds one exit item of its own: a first kill-switch drill in dev (check C12).
- **Phase 1a first value on one estate.** Exit: P4 and P7 (read paths) pass; explained spend is measured on the estate; **zero writes to Azure**; the FinOps lead confirms a number of findings, **written down before work on the Cases starts**, as true and worth acting on, each priced on a named basis; cost per Case and per confirmed finding are read from hub logs, dead ends included, with people's hours recorded beside it. **The exit is reached only when that number is reached.** If it is not reached by the review date the adopting organisation sets, phase 1a stays open and the team decides what to change; a smaller number is a new number written down with its reason, never a pass.
- What a confirmation is, stated once in `01` and `03`: the FinOps lead's judgement ("true and worth acting on"), with the price basis shown. It is not an owner's acceptance (owners are asked from phase 2) and not a verified saving (phase 3).

### 3.4 Where the cost data comes from in 1a.2 (source by access; from `docs\design\14-agreements-and-access.md` §4)

Say, in plain words and in `01`'s notes for 1a.2: exports in FOCUS (EA and MCA, direct or through a partner, at billing, subscription or resource-group scope; roles: Cost Management Contributor, Contributor or Owner on the subscription, or a billing role at billing scope; a firewalled storage account also needs Owner during creation and trusted-service access; if the identity may not create an export, the estate or billing owner creates it once) → else the Cost Details API (EA and MCA; Cost Management Reader; one month per report, up to 13 months back, at most daily) → else the Usage Details API (pay-as-you-go, MSDN, Visual Studio; legacy) → the Query API gives aggregates only (two group-bys, throttled) and is **not** a per-resource bill path. Pay-as-you-go subscriptions cannot export FOCUS; mapped columns fill the lake there. **A first estate must offer a per-resource bill path (an export, the Cost Details API or the Usage Details API) to pass the explained-spend exit.** An estate that offers only the Query API's aggregates, or no cost access at all (list prices only), can still run Cases with labelled fidelity but is a different, non-passing pilot: choose another first estate, or state in writing that the pilot cannot pass the exit.

### 3.7 `README.md` principles table (eight; one line each; the other documents follow them)

1. **Riskiest first, thinnest path first.** Work is ordered by what could change a choice. One synthetic lead is followed all the way to a test e-mail at the end of phase 0, before any depth is added.

4. **Evaluation grows with the code.** No role is deployed before its component suite passes; no tool before its pins and a negative test.
5. **Cost is visible from the first deployment**: budgets and anomaly alerts on the solution's own subscriptions are the first infrastructure; cost per Case is read from hub logs from the first Case.
6. **One repository, one release record**; Bicep with Azure Verified Modules; GitHub Actions with OpenID Connect; zip deployment; no container registry (design 09).
7. **A slice is done when** the checks of 02 hold.
8. **Builders may use AI coding assistants**; the same gates apply to every change.

### 3.9 Microsoft facts verified on 2026-11-02 (reuse with the link)

- Exchange RBAC for Applications grants are independent of unscoped Entra grants and **add** to them; an organisation-wide `Mail.Send` consent in Entra defeats the scope; changes follow a cache of 30 minutes to 2 hours; `Test-ServicePrincipalAuthorization` bypasses it; the role `Application Mail.Send` allows sending as any user within the scope ([Learn](https://learn.microsoft.com/exchange/permissions-exo/application-rbac)).
- Graph `sendMail` returns 202 Accepted when it accepts a message, saves it in Sent Items and gives no delivery guarantee; the steps before delivery are described in [Learn](https://learn.microsoft.com/graph/outlook-things-to-know-about-send-mail) and [sendMail](https://learn.microsoft.com/graph/api/user-sendmail).
- A new subscription can need up to 48 hours before all Cost Management features work ([Learn](https://learn.microsoft.com/azure/cost-management-billing/costs/tutorial-acm-create-budgets)). Budgets only alert and are evaluated every 24 hours (design 07 §4).
- Cost paths, roles and limits: `docs\design\14-agreements-and-access.md` §4, with its Learn sources. Agent playground evaluations are on by default in Foundry and are switched off in this design (design 08 §9).
