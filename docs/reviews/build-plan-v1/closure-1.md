## New defects

**Three new defects: 1 Blocker, 2 Major, 0 Minor.**

### N1 — Blocker — C4 treats asynchronous acceptance as failure of recipient protection

- **Current file:line:** `docs\build-plan\03-first-checks.md:80–81,84–86`.
- **Quote:** “Exchange rejects the direct send; if Graph accepts it, C4 has failed”.
- **Why wrong:** The sender is authorized to send as the shared mailbox. Graph can therefore return 202 before Exchange's transport applies the recipient mail-flow rule and rejects delivery. Microsoft's documented sequence returns 202 at step 1 and evaluates tenant policies at step 5. A correctly protected system can consequently fail C4 every time. This also conflicts with line 86's correct distinction between acceptance and delivery. Owning the off-list mailbox fixed the original safety problem; it did not make 202 proof of an allow-list escape.
- **Fix:** Keep the team-owned off-list mailbox and no-retry rule. Treat 202 as pending. Require evidence of transport rejection, using the administrator's message trace or a rejection report, plus no delivery to that mailbox during a predeclared observation window. Record an unresolved outcome as unresolved, not as proof that the rule failed or passed.
- **Source read:** https://learn.microsoft.com/graph/outlook-things-to-know-about-send-mail — especially steps 1 and 5.

### N2 — Major — GitHub Team does not supply the required private-repository production reviewer

- **Current file:line:** `docs\build-plan\02-before-you-start.md:18,23`; `docs\design\09-delivery-and-operations.md:44`.
- **Quote:** “GitHub Team or Enterprise Cloud (rulesets and environments in a private repository need it)”.
- **Why wrong:** Team supports private-repository environments, but not their required-reviewer protection. The referenced delivery design specifically requires a prod environment reviewer other than the release initiator. GitHub's feature reference says required reviewers on Free, Pro and Team are public-repository-only. The new licence row therefore accepts a plan that cannot enforce the specified production approval.
- **Fix:** Distinguish environment creation/rulesets from environment protection. For the private repository and the specified native reviewer control, request Enterprise Cloud. Alternatively, document and review an equivalent enforceable approval mechanism before accepting a Team-based setup; do not silently omit the reviewer or make the repository public.
- **Sources read:** https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments and https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#required-reviewers.

### N3 — Major — The firewalled-lake instructions omit the same-tenant prerequisite

- **Current file:line:** `docs\build-plan\02-before-you-start.md:21,71–73`; `docs\design\14-agreements-and-access.md:63`.
- **Quote:** “The lake's storage account is behind a firewall” followed by the setup-role, trusted-services and copy-scope instructions.
- **Why wrong:** The new paragraph correctly lists those prerequisites but never checks the tenant boundary. The same Learn page explicitly says firewalled storage is supported for same-tenant exports and not for cross-tenant exports. Agreement/access coverage and managed estates do not establish that the exporting scope and the solution's destination share a tenant. Completing every instruction in this paragraph can therefore still leave an unsupported export path.
- **Fix:** Check and record the export/destination tenant relationship when selecting the first estate and requesting access. State that direct exports to this firewalled lake require the same tenant. For a cross-tenant estate, select and verify a supported detailed API or another explicitly designed ingestion path; do not weaken the lake firewall as an implicit fallback.
- **Source read:** https://learn.microsoft.com/azure/cost-management-billing/costs/tutorial-improved-exports#configure-exports-for-storage-accounts-with-a-firewall.
