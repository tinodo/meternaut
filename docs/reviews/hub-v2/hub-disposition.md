# Hub review 2: disposition

A reviewer on another model family (gpt-6.1-sol) read the rebuilt hub at commit `32399ac`: the workflow, the template, the gateway tool and its policies, the bootstrap, the helper tools, the tests and the documents. The report is [hub-review-1.md](hub-review-1.md): 13 findings (1 Blocker, 8 Majors, 4 Minors). The reviewer's verdict was that the package was not yet safe to hand to the owner as a pull request. All 13 are accepted. Before accepting, the claims that the fix depended on were checked against the code and, where an answer could be reproduced, by running it.

| # | Finding (severity) | Verdict | What was done (where) |
|---|---|---|---|
| H2-01 | The instance id could end in `?api-version=...#`, so the first DELETE of a `meternaut-` object went to the instance itself (Blocker) | Accepted, reproduced | Reproduced first: the old pattern accepted such an id, and the address that urllib puts on the wire (its `selector`) was the instance, not the object. Fixed in three layers: the id must match a strict pattern (letters, digits and the few characters a name may hold), an address is built and read back and must have exactly the instance's path and no fragment, and the one place that sends the token refuses any address with a fragment, a user or another host. A regression test tries thirteen endings on three commands and checks that nothing is sent; run against the old pattern it fails, against the new one it passes (`tools/apim-sync.py`, `tools/tests/test_apim_sync.py`) |
| H2-02 | The manifest chose its own prefix, so it could name another team's objects (Major) | Accepted | `meternaut-` is a constant of the tool, and a manifest that declares any other prefix, well formed or not, is refused. An empty name after the prefix is refused too (`tools/apim-sync.py`; tests for a foreign prefix, for objects under it and for the key of one of its subscriptions) |
| H2-03 | Deleting the product deleted every subscription of it, named in the manifest or not (Major) | Accepted | The cascade is gone: the tool deletes the subscriptions the manifest names, then the product without the cascade. A subscription that someone else made on the product now stops the removal with a message, and is not touched. The stand-in service models the product-subscription relation, so a test proves it (`tools/apim-sync.py`, `tools/tests/test_apim_sync.py`) |
| H2-04 | An update was sent without `If-Match` (Major) | Accepted | `apply` now follows the plan: an object that is already right is not written, a new one is written plain and an update carries `If-Match: *`. The stand-in refuses an update without it, and a second apply is tested against existing objects. I could not confirm from the stand-in that the service insists on it; Microsoft's reference says it does for an update, and sending it costs nothing |
| H2-05 | A write that the service only accepted (202) was taken as done (Major) | Accepted | After a 202 the tool reads the object until the service says it is there (a bounded wait of five minutes), stops if it reports failure, and writes nothing that depends on it before then. Tests: accepted and delayed, failed, and never ready |
| H2-06 | The budget's start date moved with the clock at every deployment (Major) | Accepted | The template no longer takes the date from the clock: it is a parameter. The workflow reads the existing budget's start date and passes it on, or uses the current month for a new budget, and `tools/hub-params.py` checks it is the first of a month. I did not find in the documentation whether Azure refuses a changed start date; the fix removes the question. The shell steps are run in the simulation for an existing budget, a missing one and an error (`hub/main.bicep`, `tools/hub-params.py`, `.github/workflows/deploy-hub.yml`) |
| H2-07 | The smoke test passed without evidence: any 429, and a reply with no token usage (Major) | Accepted | A completion must carry the model's token usage, or the check fails. The limit check passes only on the gateway's own refusal (a body with a top-level `statusCode` of 429; the model's own 429 has an `error` object), and only if the large request's reported usage was at least the minute's allowance, so it cannot pass without having crossed it. Negative tests for a model-side 429, a missing or zero usage and a too-small request (`tools/hub-smoke.py`, `tools/tests/test_hub_smoke.py`) |
| H2-08 | The summary said things were gone or checked when the run had failed; the README overstated atomicity (Major) | Accepted | The summary now depends on the job's result: a failed or cancelled run says that it did not finish, what may exist and what may still cost, and promises nothing; success wording appears only after success. The README no longer says that a failing model leaves nothing in the instance: it says what is and is not added at each point, and that running `deploy` again repeats only what is missing (`.github/workflows/deploy-hub.yml`, `hub/README.md`) |
| H2-09 | The undo instructions prescribed more manual Azure changes as the ordinary way (Major) | Accepted | Taking the hub away is the workflow's `remove` or `pause`. The manual steps are now named as the reversal of the bootstrap, a manual exception of the same kind that needs its own plain-word yes. The purge is not needed (the workflow restores a soft-deleted account) and is described as a separate step that waits for its own yes (`hub/BOOTSTRAP.md`) |
| H2-10 | The preview did not handle a soft-deleted account of the same name (Minor) | Accepted | The preview does what the deploy does: when the platform names the restore flag, it previews again with `restoreAccount=true`. Simulated for success, restore and other failure. The complete sequence under the narrow identity cannot be shown offline and stays on the list of what the first runs must prove (`.github/workflows/deploy-hub.yml`, `hub/README.md`) |
| H2-11 | Streaming is accepted, and the token limiter estimates a stream's tokens (Minor) | Accepted | The contract's policy now reads the request once and refuses, before anything is counted: a model that is not a JSON string on the list (403), and streaming or a body it cannot read (400). The API's policy keeps its own fail-closed check. Tests check the order of the contract's steps, and the README says what is refused (`hub/apim/policies/`, `tools/tests/test_apim_sync.py`, `hub/README.md`) |
| H2-12 | The lint looked for words, not for the guard's meaning (Minor) | Accepted | The deploy workflow must have exactly one job, and that job's own `if:` must be exactly the owner-and-main condition (quotes and a `${{ }}` wrapper are the same condition). Both of the reviewer's mutations (`&&` turned into `\|\|`, a second unguarded job) and a guard moved into a step are tests, and each was also tried on a copy of the real workflow and found (`tools/workflow-lint.py`, `tools/tests/test_workflow_lint.py`) |
| H2-13 | The bootstrap said the identity cannot delete resource groups (Minor) | Accepted | It says now that the identity can delete the whole hub resource group, that the workflow never does, and that a budget alert is the only warning (`hub/BOOTSTRAP.md`) |

## Also changed

- **The identity's role condition** now also limits the one role to service principals, in the form that Microsoft's examples give for constraining roles and principal types. The identity can no longer grant even that role to a person or a group (`hub/BOOTSTRAP.md`).
- **The list of what has not been seen** in the README now carries what the reviewer could not verify offline: the identity's real rights, DNS resolution (the wait sees a zone group, not a resolving name), the exact objects and policy expressions on the instance, token usage in the reply, a whole lifecycle, and the costs the sizing leaves out (`hub/README.md`).
- **The model name** is read by a JSON parser that keeps the last of two duplicate keys. The README says so, and why it cannot reach another deployment: the account holds only one.
- **The shell steps of the workflow** were run under the runner's flags against a fake Azure CLI: sixty checks (restore retry, not-found handling, order of removal, polling, masking of the key, the summaries). The harness stays out of the repository.

## What was kept

The reviewer found these right and they were not changed: the template creating no gateway, DNS zone, link, zone group, peering or route; the Bicep compile and lint; the trigger, guard and identity wiring; the shell constructs; the host fence and the refusal of redirects; no identifier in the diff.
