## (c) Findings

Blocker · `05` :233 · "A person sets it on the settings page or on a card (the bot passes the tapper's own token, as for a tap)" · That write includes delegates (`06` :155), mutes and "Pause messages". It uses the same token as an R1 tap. It is not step-up, and the daily cap does not count it. A stolen Teams session, or the `bot` fetching a signed-in token, names the attacker as delegate and can silence the owner. The delegate then approves that owner's R1 and R2 changes as themselves, after the stolen session is revoked. Section 8 admits the `bot` can approve R1 within the cap. It does not admit this longer grant. · A change that names a delegate, mutes, or sets "Pause messages" is refused on a card. It requires the approval page and the same authentication context as R2. Tell the owner on a channel they cannot mute. A delegate's R2 submit must carry that context. Say that a compromised `bot` can appoint delegates for every signed-in person.

Blocker · `05` :209 · "who restores in one tap inside the undo window: a rollback grant, usable once, held by the approver for a change that can be reversed" · R2 and R3 were approved on the page with an authentication context. Undo is a card verb (`C6`, `C8`) with no such claim and no cap. A stolen Teams session applies the inverse of a production change. For a Credential run there is no approver of the run, so the holder of the grant is unnamed. The consumption item id "derives from the request id" (`05` :60) and the same container records the grant (`05` :37). One id cannot mark both the run and the undo, so "usable once" is not enforceable. · Undo of an R2 or R3 change requires the same sign-in strength as the class, on the page, not a card tap. Give the grant its own consumption id. For a Credential run, name the owner as the only holder, and say a stolen session can still undo within the window.

Major · `14` :116 · "Sends a complete request: stored quote, scope, term, saving, evidence, deadline" · The next paragraph (`14` :123) allows only scope identifiers and "no other spend". A builder who follows the table sends a saving and evidence to a partner mailbox. A builder who follows the paragraph sends a request the partner cannot price. `05` :180 also tells approvers the recipient "is outside the organisation", which is false for an internal billing owner. The recipient is both "the partner contact the organisation names" and "one address on the allow-list", and the text does not say which wins. An estate owner who can name the contact (`09` step 3) can point it at an attacker if the allow-list check is not a hard refuse. · One rule: the body may contain the stored quote's SKU, term, dollar amount and scope identifiers, and nothing else. No evidence, no other spend, no resource names. Refuse to send unless the directory contact equals one allow-list address. Call an internal billing owner internal.

Major · `05` :158 · "it shows the exact plan from the stored plan record and takes the decision" · The only authorisation stated for the page is scope (`05` :160). The approver check is stated for card verbs, not for this submit. A forwarded `/ok/<requestId>` link lets any signed-in person who can see the resource decide. The id is not a secret. · The page refuses a submit unless the sign-in token's object id is the designated approver or a named delegate, and the token carries the class's authentication-context claim. Say that a forwarded link authorises nobody.

Major · `06` :178 · "resuming purchases takes two people with the two roles of an R3 approval" · `approvals` holds replace and delete on `switches` (`05` :48). The page's fresh sign-in and the two-person rule are code in that app. The app identity can clear the purchase switch alone. The runbook is "commands" (`09` :147) and is not said to need two credentials. `07` :68 says a break-glass account cannot release alone. Nothing in the store enforces that. · The purchase switch is two items, each creatable by only one of the two roles, and a release deletes both. The runbook uses the same split. Say that a stolen `approvals` identity can still release every switch.

Major · `05` :128 · "The App holds Pull requests and Checks write and no Contents write on the base repository, so it can neither push there nor merge" · The merge half is right. Checks write lets the App create a check run on the base repository. The text does not pin required checks to another app, and it does not forbid `pull_request_target` on fork pull requests. A stolen App key can make its own proposal look green, and a workflow that checks out the fork head with the base token can push to the base repository. · Pin every required check to the CI app, not to `pr-draft`. Drop Checks write if the App does not need it. Fork pull requests run on `pull_request` only, with no secret and no token that can write to the base.

Major · `05` :184 · "a sign-in asking to grant an app permissions is fraud" · The R1 tap uses user authorization and an on-behalf-of exchange (`05` :146). That flow asks the person to sign in and, unless an admin has already consented, to grant a permission. The warning and the real path can be the same screen, so a consent-phishing page is what people were told to expect. · Admin-consent the delegated permission before first contact. State that the real sign-in never asks for a new grant, and that any consent screen is fraud.
