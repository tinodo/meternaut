# Hub review 1: disposition

A reviewer on another model family (gpt-6.1-sol) read the development hub as built: the files of [`hub/`](../../../hub/README.md), the patch to the accelerator and the working copy it applies to, the access contract, the C14 harness, and the plan and design text that they implement. The report is [hub-review-1.md](hub-review-1.md): 18 findings (1 Blocker, 8 Majors, 9 Minors), and the verdict was that the work must not be released as a completed slice 0.2 and check C1. The reviewer found the allow-list and policy names right for the pinned commit, the conditional Cosmos output and the Event Hubs identity and TLS changes sound, and no credential or identifier in the committed files.

The review was static. Most findings were answered by changing the files or the deployed hub and then checking the result against the deployment; the rest by saying exactly what the hub does and does not do. This record says which.

| # | Finding (severity) | Verdict | What was done (where) |
|---|---|---|---|
| H01 | The hub alone cannot close C1: no solution-side Evaluate account, deny policy, egress limit or pre-flight, and no evidence of a successful and a refused call (Blocker) | Accepted | C1 stays open, and the README says so. What the hub can show was checked and recorded: a call through a contract succeeds; calls with no key, a wrong key, a model the contract does not allow, or a prompt over the limit are refused; the model account refuses callers that bypass the gateway. The Evaluate account, the policy and the egress limit belong to the Evaluate profile and are not built. The direct probe used an empty or malformed request, so no model ran; [AGENTS.md](../../../AGENTS.md) rule 15 (c) says that such a request is not a model call, and the owner may strike that sentence (`hub/README.md`, `AGENTS.md`) |
| H02 | Foundry key access stays enabled (Major) | Accepted | The patch sets `disableKeyAuth` to true. Verified on the deployed account: no credentials and the hub's key are refused, while the gateway still reaches the model with its managed identity (`accelerator-changes.patch`) |
| H03 | The template takes over private-endpoint DNS, which conflicts with the landing zone's policy (Major) | Accepted in part | After deployment the conflict showed as the reviewer expected, and as harmless: the policy's `PolicyDeployment_` fails with "more than one private dns zone group" because each endpoint already has the one the template made. The local zones are linked to the hub's own network only, so they mask nothing elsewhere. Not changed: a central-DNS mode (no local zones, the network's DNS servers set, zone groups left to the policy) is a larger change to the pinned template with nothing broken to fix. The README says what happens and why it is harmless |
| H04 | The token policy keeps the rejected default `estimate-prompt-tokens="false"`, and its comment promises too much (Major) | Accepted | The estimate is on. A prompt of about 40,000 estimated tokens was refused by the gateway with 429 in a fraction of a second and no model call. The comment now says that the minute's limit answers 429 and the quota 403, and that the counters are accounting with some overshoot. Not run: a breach of the monthly quota and concurrent calls across a limit (`contracts/learning-demo-dev/ai-product-policy.xml`) |
| H05 | A monthly token counter is not the stage's daily and total spend limit (Major) | Accepted in part | Right that the words were too strong: the contract's quota is a monthly token ceiling, not a stage ledger. It is a persistent limit at the gateway that survives restarts of the harness, and at this model's list prices it bounds a month's model spend to about one euro, far below both standing limits; the harness's cap protects a run inside it. Spend is the sum of tokens of calls that returned 200 in the workspace, because refused calls log their estimated tokens (`hub/README.md`). Not added: a second ledger in the harness, which would repeat the gateway's quota |
| H06 | Paid foundations have a tag but no wired budget, owner or end (Major) | Accepted | The owner is a required parameter. A budget for one resource group (`infra/budgets/rg-budget.bicep`) was written and deployed to the hub's group, with alerts at 80 % of the cap, at the cap and on the forecast. The README says that a budget only alerts and that deleting the group stops the cost, and AGENTS.md rule 15 (g) says that the agent asks the owner in plain words whether to delete the hub when the demonstration is finished |
| H07 | Unneeded identities and grants survive (Major) | Accepted in part | The usage identity and its role are created only with the add-on. Two switches turn off the Foundry account's access to the vault (read of secrets, write of certificates) and the deploying person's role on the account; the template granted the latter again on every deployment, which gave direct access to the model. The leftovers of earlier deployments were deleted by hand, because an incremental deployment does not delete, and the role list was read back. Not adopted: narrowing the gateway's roles from the resource group to the accounts. The group holds only the hub, so the group scope grants nothing the account scope would not, and narrowing needs a larger patch (`accelerator-changes.patch`) |
| H08 | "Private PaaS" is not true for telemetry and the gateway's platform endpoint (Major) | Accepted | The README lists what is private (gateway, model account, event hub, vault) and what is not (Log Analytics and Application Insights ingestion and queries, authenticated; the management endpoint of the classic tier). Private connectivity for the workspace is an option of the template that this profile leaves off: no policy of the landing zone required it, and it adds endpoints and zones to a development hub |
| H09 | A clone cannot reproduce the path: no bootstrap, no README, no CI for the new files (Major) | Accepted | `hub/README.md` is the runbook: fetch the pin, apply the patch, set the environment, check, deploy, name the gateway in DNS, add the contract, put a budget on the group, try it. A new CI step runs the first two on every change (fetch by commit, apply the patch, compile the template and the parameter files), so a patch that no longer applies fails the build |
| H10 | The one-name zone is sound, but resolution from callers is assumed (Minor) | Accepted | The narrow zone is kept. The README says that the zone is linked to the hub's own network and the network whose resolver the landing zone uses, and that a machine that does not forward to it can use the gateway's address with the name kept for TLS. That path was used for every check, and by the harness's new option |
| H11 | The DNS template has no lifecycle or input safeguards (Minor) | Accepted | The address is read from the API Management instance, the list of networks must not be empty and duplicates are dropped. The order of removal (links to networks outside the group first) and the five-minute record lifetime are written in the template and the README (`dns-gateway.bicep`) |
| H12 | A bearer token makes the client drop the key, which the API always requires; the key-only exception has an upgrade trap (Minor) | Accepted | The client always sends the key header and sends a bearer token in addition when one is set, and it can connect to a given address while TLS and the Host header keep the URL's host name. A `hub-check` command makes one small call. Tests grew from 101 to 107. The README says that callers are identified by a subscription key until an app registration exists (`evaluation/c14`) |
| H13 | Optional-module warnings remain; no coverage for both flag values (Minor) | Accepted in part | CI compiles the whole patched template, which compiles both branches of every conditional whatever the flag's value. The remaining warnings are the accelerator's own, unrelated to the patch; suppressing them wholesale was not done |
| H14 | "Off" is not a complete lifecycle for `azd` and for earlier deployments (Minor) | Accepted | The README says to deploy with `az deployment`, not `azd up`, and that a switch suppresses creation, not deletion. The only thing an earlier deployment had made was the usage identity, which was deleted |
| H15 | An unused event hub still bills and can inflate (Minor) | Not adopted | The accelerator's logging fragments write to it, and removing it means making the event hub, the loggers and the fragments optional together: a larger patch to a pinned upstream. Its cost is in the price of the development hub (`python tools/cost-model.py --dev-hub`), and the README says what it is for |
| H16 | The repository does not price this profile (Minor) | Accepted | `tools/cost-model.py --dev-hub` prices the gateway, the event hub, the endpoints, the DNS zones, the vault and the log ingestion from the price snapshot, run by CI. The workspace has a daily cap on ingestion, priced as an upper bound. Not changed: diagnostic categories and sampling, because the whole workspace took in about 0.2 MB in the hub's first hours, with some thirty calls, and the cap allows 100 MB a day |
| H17 | The alias and the headers are not what the design promises (Minor) | Accepted | The README says that the contract allows the model's own name, that aliases are not onboarded and that the debugging headers are for development. A call with the alias is refused, which was checked |
| H18 | "Only token counts" overstates the minimisation (Minor) | Accepted | The parameter file and the README now say: token counts and request metadata are logged, prompts and answers are not (the message columns of the workspace were read and are empty), and the client address and the caller are logged |

One finding came from the deployment, not from the review: the template grants the deploying person the Foundry Project Manager role on the account again at every deployment. It was removed by hand twice and is now a switch, which the hub's parameter file turns off.
