# Design 14 — Next phases

> **What this answers:** *What do we prove first, in what order, and which assumptions are checked by building the smallest thing that can show them wrong?* The design of phase 1 ends with this plan; the build begins with its first spikes. Part of the [design](README.md). Decisions the plan tests are in [13](13-decisions.md); costs in [12](12-cost-and-finops.md).

---

## 1. Principle: evidence before breadth

The riskiest parts of this design are not the agents. They are the **platform seams**: whether an agent identity passes the hub's per-tool checks, whether the hub can carry a hosted agent's invocation and a leaf that returns at once survives its idle timeout, whether the broker and the runner can each verify a permit, a signed record and a person's Entra-signed token for themselves while a constrained role-assignment delegation behaves as described, whether a Durable Functions spine survives a restart without a lost or double effect, whether a private Foundry spoke really fills its own stores, whether a Teams card can hand a bound approval to the web page. Each is a small experiment. **Every phase starts with the spikes that could invalidate its decisions and ends with evidence against a named exit criterion** — evidence the pipeline produces, not a status report.

## 3. Spike register

A spike has a question, a method, an exit criterion and a fallback. Timeboxes are in working days of effort and are *limits*, not estimates; a spike that needs elapsed time (S-ORCH-1's 30-day wait) starts early and is read when it ends, and elapsed time is not effort. **The size of the register, honestly:** 34 spikes, 32 of them boxed at 109 working days of limits in all, and two that wait for a trigger (S-GW-2 and S-SEC-3). It is a menu, not a queue: §4 sets in **bold** the 14 spikes (65 days) whose failure would change what a phase builds first, and only those start before their phase's build (S-ID-3, the chain's first build under faults and forged proofs, is the largest at 14 days); the other 18 (44 days) run beside it, because their fallback is already the default or only a claim waits on them ([the minimum viable profile](#phase-and-capability-profiles)).

### Phase and capability profiles

A **profile** says what exists in a phase. **A release deploys to the next environment that exists in the current profile**, and the pipeline's gates and the `pr-spoke` workflow read the profile (the file `governance/phase-profile.yaml`, [11 §3](11-delivery-and-operations.md#3-pipelines)), so no TEST hub, TEST account or Lab is required before its phase. Accounts and environments are created in the phase that needs them, and a deferred private account saves its idle meters ([12 §4](12-cost-and-finops.md#4-what-still-costs-money-when-nothing-is-happening)). **The one exception is the AI Search services**: they are created on day zero because their region may refuse a new service (assumption 8), a deliberate idle meter that buys certainty and is priced apart in 12 §4.

|---|---|---|---|---|
| 0 | DEV | DEV | none | `study`: one hosted agent |
| 1 | DEV | DEV | none | + `curate`, `examine-pub`: Scholar, Cartographer, Librarian (Atlas), Examiner |
| 2 | DEV, PROD (shadow: read-only on one real estate, every Move a dry run) | DEV, then PROD | none; the DEV rehearsal uses a dry-run runner | + `survey`, `investigate`, `forge`, `conduct`: Surveyor, Detective, Skeptic, Economist, Forger, Conductor |

| 4 | + the Lab account (Team and Enterprise scale) | as phase 3; the Lab is where experiments run, never a release target | as phase 3 | + `experiment`, `engineer`: Experimenter, Engineer |

DEV and TEST carry synthetic data only, so their products use the public pools ([04 §4.3](04-landing-zone-and-citadel.md#43-the-access-contracts)); until TEST exists, DEV carries the exams and the gate runs. At Pilot scale there are only DEV and PROD accounts ([12](12-cost-and-finops.md)), and the first Moves are rehearsed in DEV by the dry-run runner. A spike that needs real resources uses a **scratch subscription**, vended by hand and deleted afterwards: it is not an environment, not the Lab and not in the profile. The gates apply as far as the profile has something to gate: G1 from phase 0, G2 to G6 for the leaves that exist, the drills of G7 from phase 3 (they need the chain) and G9 from phase 5.

**The minimum viable profile.** Until a spike or the exam gives a reason, a phase takes the simplest generally available option and activates only its own leaves and contracts: direct hybrid retrieval (the semantic ranker is an option the exam must justify), typed query tools before sandboxed code, the framework-agnostic hosting container, a plain agent loop, our own deterministic gate, structured output for triage and Sol for investigation. A spike in plain type in the table above may start beside the build, because its fallback is already this default or only a claim waits on it (G2, for example, counts the hub's response screening only after S-GW-4); the spikes that can only *add* to the default (S-DATA-3's ranker, S-SBX-1, S-HOST-1's package, S-AGT-1, S-SEC-1, S-MOD-2, S-MOD-3) never block a phase. The operating budget in hours is in [11 §7](11-delivery-and-operations.md#7-operating-the-platform). Two spikes wait for a trigger instead of a phase: S-GW-2 (the first A2A asset) and S-SEC-3 (egress *enforce* mode reaching general availability).

## 5. Pre-flight checklist (day zero)

1. **Quota requests** for the GPT-6 family and the hosted-agent session limits in Sweden Central.
2. **AI Search**: create the Search services on day zero, before anything depends on them. Learn flags Sweden Central as "in high demand, which prevents the creation of new search services" (assumption 8); if it refuses, create the service in another EU region and cost the cross-region traffic.
3. **Resource providers** registered in the new subscriptions (the research lists about 25 for the hub and the spoke).
4. **Entra**: the hub's app registration with the `Model.Invoke`, `MCP.Invoke`, `Agent.Invoke` roles, and the per-tool app roles to be assigned directly to the agent identities (S-GW-3); a person able to assign app roles; the approval page's app registration (a confidential client) with a federated identity credential that trusts the page's user-assigned managed identity, requesting the optional claims `auth_time` and `amr`, and a Conditional Access policy on it that requires the multifactor authentication strength (S-ID-3; assumption 5).
5. **Networking**: address space (a `/24` per agent subnet, a `/26` for endpoints (`snet-pe`: every private endpoint lives there, because a delegated subnet cannot hold one), and a separate subnet for the execution plane, `snet-exec`, sized in [04 §6](04-landing-zone-and-citadel.md#6-network)), peering both ways, firewall rules for the Entra hosts, `*.identity.azure.net`, Application Insights and the hub; private DNS zones linked.
6. **GitHub**: the repository's protected environments and rulesets, workload identity federation, the self-hosted runner job; the plan checked for required reviewers and status checks on a private repository (S-DEL-2); the agents' GitHub App, limited to the data paths, with its private key in the secrets vault; a pull request that touches `moves/**` needing two approvers who are not its author; `pr-spoke` running after the merge, inside `deploy`; bot pull-request workflows on GitHub-hosted runners with no secrets and no federation.
7. **Teams and mail**: custom app allowed for pilot users; shared mailbox; Exchange role-based access scoping for the application.
8. **Billing**: Cost Management export destination; reader access on the first estate.
9. **Policy**: the initiative in *audit* mode in the first week, then *deny* in production.
10. **Budgets** as alarms on every subscription; the cost report workflow.
