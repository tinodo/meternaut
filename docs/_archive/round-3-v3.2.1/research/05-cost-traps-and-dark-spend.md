# Azure Cost Traps & Dark Spend — Sourced Catalog

**Project:** Azure Cost in Action (ideation) · **Author:** desk research for Tino Donderwinkel
**Retrieval date for all live sources:** 2026-10-30 (noted again where a source carries its own effective date)
**Round-2 note:** the catalog was spot-checked in rubber-duck round 2 (17 rows; see the addendum at the end). The pre-correction text is archived [here](../_archive/round-2-v2/research/05-cost-traps-and-dark-spend.md).
**Method:** Microsoft Learn / official pricing docs read directly this session (`Verified`), AI-assisted search summaries citing an official page I did not re-fetch in full, or credible community corroboration of an official mechanism (`Partial`), or well-established mechanisms drawn from general Azure knowledge with a best-known canonical doc URL not re-checked this session (`Unverified`). No Azure subscription, `az`/PowerShell, or portal access was used — everything below is reading, not probing a live tenant.

**Why this catalog exists:** Azure Cost Management shows *what* was billed. Azure Advisor shows a narrow, conservative slice of *idle* resources (unattached disks, idle public IPs/load balancers/ExpressRoute circuits, empty App Service plans, Cosmos DB autoscale candidates — see [Advisor cost recommendations](https://learn.microsoft.com/azure/advisor/advisor-reference-cost-recommendations), `Partial`). Everything else — platform-managed resource groups, pricing-model mechanics, ratchet effects, silently-failing idle-shutdown settings, "pause doesn't stop storage" nuances — is invisible unless someone reads the fine print of each service's billing page. That fine print is this document.

**Legend:** Status = `Verified` / `Partial` / `Unverified` (see Method above). 🔻 = flagged retired/renamed/preview/legacy in SCOPE instructions.

## Where to start — ten verified traps that are safe to test first *(added after round 2)*

*Selection by the orchestrator, by judgement — **not** a ranking by dollar value (no spend was measured). Rule: the row is **Verified** in this catalog, the signal is readable from configuration and metrics alone, and the first action is advice or a restorable property patch — no hidden-consumer risk and no data loss. Read the full row before using any of them.*

| # | Trap | Why it is a good first test | First action |
|---|---|---|---|
| 1 | **TRAP-STOR-001** — SFTP enabled on a storage account bills hourly | Round-2 confirmed; a flat charge that only config + connection metrics can explain | Advise; disable when no SFTP use is observed (restorable) |
| 2 | **TRAP-DATA-004** — Databricks all-purpose clusters without auto-termination | A silent "left running" mechanism | Advise; enforce auto-termination through compute policy |
| 3 | **TRAP-AI-006** — Azure ML compute cluster `min_nodes` above 0 | A property patch, no data involved | Advise; set `min_nodes` to 0 |
| 4 | **TRAP-AI-007** — ML compute-instance idle shutdown silently fails without a role grant | A *mechanism that is not working*, invisible to billing views | **Advise only** — the fix is a permission grant, so it needs security co-sign |
| 5 | **TRAP-APP-001** — Functions Premium plan bills at least one instance per plan | A concrete floor price per idle plan | Advise; move truly idle apps to a consumption-based plan |
| 6 | **TRAP-APP-005** — Container Apps replicas bill an idle rate when min replicas is above 0 | A property patch with a clear tolerance question for the owner | Advise; set min replicas to 0 where start-up latency is acceptable |
| 7 | **TRAP-PLAT-008 / NET-006** — a Virtual WAN Standard hub bills a fixed hourly fee | Same family as seed example 2 (hidden capacity) | **Advise only** — re-architecting connectivity is high risk |
| 8 | **TRAP-AI-001 / AI-002** — provisioned throughput cannot be paused; do not scale it with traffic | Maps to the Release-1 utilisation play | Advise; right-size, or consider a reservation *deliberately* — a reservation is a signed transaction, never automatic |

| 10 | **TRAP-SEC-005** — Sentinel analyses and bills *all* data in the workspace | Pairs with the log-usefulness play and Sentinel's own "used only by Azure Monitor" observation | **Advise only** — security-scoped; move non-security data to a separate workspace |

## 1. Orphaned / Unattached Resources (TRAP-ORPH)

| TRAP-ORPH-001 | Unattached managed disk keeps billing after its VM is deleted | Disk outlives the VM; no owner left once the compute resource is gone | `ManagedBy` = null; zero attach/detach events in Activity Log for 30+ days | Snapshot if needed, then delete disk | Low risk once snapshotted | [Advisor cost recommendations](https://learn.microsoft.com/azure/advisor/advisor-reference-cost-recommendations) | Partial |
| TRAP-ORPH-002 | Standard-SKU public IP billed hourly whether attached or idle; orphaned NIC keeps it alive | IP/NIC pair survives VM deletion if deleted out of order | IP `IpConfiguration` = null; NIC not attached to any NIC-attachable resource | Dissociate and delete IP + NIC | Low risk | [Public IP addresses](https://learn.microsoft.com/azure/virtual-network/ip-services/public-ip-addresses) | Partial |

| TRAP-ORPH-004 | NAT Gateway has no "stopped" state — only deletion stops the hourly + data-processing meter, and it silently takes over all subnet egress once attached | Looks like a one-time network setup task, not an ongoing cost item | Near-zero `SNAT Connection Count`/bytes metric over weeks; subnet has no active egress workload | Delete NAT Gateway (+ its public IP/prefix) when egress not required | Low risk; recreate via IaC when needed | [What is Azure NAT Gateway?](https://learn.microsoft.com/azure/nat-gateway/nat-overview) | Verified by the agent; **round-2 spot-check inconclusive** (the cited page returned no matching billing statement; StandardV2 NAT Gateway is priced the same as Standard) |

| TRAP-ORPH-006 | Application Gateway/WAF v2 provisioned at minimum scale bills a fixed per-instance/capacity-unit hourly rate even at zero traffic | Provisioned for a launch, never decommissioned after traffic moved elsewhere | Near-zero `Estimated Billed Capacity Units` and request count sustained for weeks | Delete the gateway (*corrected after round 2:* setting the autoscale **minimum to 0 does not remove the fixed charge** — Microsoft's pricing page says there is an associated cost even if zero instances are reserved by specifying 0 as the minimum instance count; only deleting does) | Low–medium risk (check DNS/dependents first) | [Understanding Pricing for Application Gateway and WAF](https://learn.microsoft.com/azure/application-gateway/understanding-pricing) | Verified |

| TRAP-ORPH-009 | On-demand VM Capacity Reservation group bills for reserved capacity whether or not any VM is actually deployed into it | Reservation is a capacity guarantee, not a running resource — easy to forget it's a standing charge | Reservation `VM instance count assigned` = 0 for an extended period | Remove reservation or reduce quantity to match actual deployments | Low–medium risk (may lose capacity guarantee) | [Capacity Reservation overview](https://learn.microsoft.com/azure/virtual-machines/capacity-reservation-overview) | Unverified |
| TRAP-ORPH-010 | A backup item moved to "stop protection, retain data" keeps billing standard rates indefinitely — policy retention no longer governs it, only a manual delete does | Looks "stopped," reads as inactive, but the retained recovery points keep accruing at full backup rate forever | Protection state = "Protection Stopped" with data retained, no scheduled jobs, age > original retention | Confirm recovery point no longer needed, then permanently delete | Medium risk — deletes recovery capability | [Soft delete for Azure Backup](https://learn.microsoft.com/azure/backup/secure-by-default) | Verified |
| TRAP-ORPH-011 | VPN/ExpressRoute gateways provisioned "for the project" are billed hourly regardless of whether any tunnel/circuit is actively passing traffic | Gateway deployment is a one-off infra task; nobody revisits after the project pivots | Zero/near-zero `Gateway Bandwidth` or active tunnel count over weeks | Downsize SKU or delete gateway if connectivity no longer required | Medium risk — reconnecting on-prem may need a maintenance window | [About VPN Gateway](https://learn.microsoft.com/azure/vpn-gateway/vpn-gateway-about-vpngateways) | Partial |

## 2. Stopped-but-Billed (TRAP-STOP)

| ID | Trap | Why Invisible to Owners | Usage-Truth Signal | Typical Fix | Reversibility / Risk | Source | Status |
|---|---|---|---|---|---|---|---|
| TRAP-STOP-001 | A VM "Stopped" (not "Stopped (deallocated)") keeps billing full compute — only deallocation releases the compute meter | Portal "Stop" button looks final; the deallocated state requires a distinct action/wait | Power state = `stopped` not `deallocated` in VM instance view | Deallocate instead of just stopping | Low risk | [States and billing status of Azure VMs](https://learn.microsoft.com/azure/virtual-machines/states-billing) | Partial; **round-2 spot-check inconclusive** |
| TRAP-STOP-002 | Premium SSD/Ultra Disks keep billing storage cost even while their VM is fully deallocated | Only compute stops on deallocation; attached disks are billed independently of VM power state | VM deallocated > 30 days, disk still `Premium_LRS`/`UltraSSD_LRS` | Downgrade to Standard SSD or delete if VM is permanently retired | Low–medium risk (IOPS drop if downgraded) | [Managed Disks pricing](https://azure.microsoft.com/pricing/details/managed-disks/) | Unverified |
| TRAP-STOP-003 | A Standard-SKU public IP reserved on a deallocated VM keeps billing hourly even though nothing is reachable | "We might start it again" keeps the IP attached indefinitely | VM deallocated, IP still associated, zero inbound connections | Dissociate IP if a new one is acceptable on restart | Low risk (IP address will change) | [Public IP addresses](https://learn.microsoft.com/azure/virtual-network/ip-services/public-ip-addresses) | Partial |
| TRAP-STOP-004 | AKS "Stop cluster" is the only supported way to pause — but node resource group objects (disks, LB, public IP) are governed by the cluster, not by VM power state, so some keep billing | Team assumes "stopping the cluster" is equivalent to deleting its infrastructure | Cluster `powerState` = Stopped, node resource group still contains LB/disks/public IP | Use [start/stop cluster feature](https://learn.microsoft.com/azure/aks/start-stop-cluster) deliberately; delete cluster if truly done | Medium risk — full delete removes node resource group permanently | [AKS FAQ](https://learn.microsoft.com/azure/aks/faq) | Partial; **round-2 spot-check inconclusive** |
| TRAP-STOP-005 | A Databricks workspace with all clusters terminated still bills for residual managed disks and DBFS root storage — there is no workspace-level "pause" | Teams expect "no running clusters" to mean "no cost" | Zero active clusters/SQL warehouses for 10+ days, workspace storage account still present | Terminate clusters immediately after use; archive/export then delete workspace if abandoned | Medium risk — deleting workspace loses notebooks unless exported first | [Azure Databricks cost optimization best practices](https://learn.microsoft.com/azure/well-architected/service-guides/azure-databricks) | Partial |
| TRAP-STOP-006 | Azure OpenAI Provisioned Throughput (PTU) deployments cannot be paused — only deleting the deployment stops the hourly PTU meter | "We'll just scale it to zero between tests" is not an option for PTU, unlike Consumption deployments | Deployment exists with PTUs > 0 and near-zero token throughput over days | Delete deployment between use windows; re-create when needed | Low risk if IaC-defined; takes capacity-availability risk on re-create | [Provisioned throughput billing](https://learn.microsoft.com/azure/foundry/openai/concepts/provisioned-throughput-billing) | Verified |
| TRAP-STOP-007 | Provisioned (non-serverless) SQL Database / Managed Instance compute tiers bill 24/7 regardless of query activity — only the Serverless tier can auto-pause | Dev/test databases provisioned on a standard vCore tier "because that's the template" never stop billing compute | Query/connection count near zero for days on a non-serverless tier | Migrate low-use dev/test DBs to Serverless with auto-pause | Medium risk — serverless adds resume latency on first connection | [Serverless compute tier overview](https://learn.microsoft.com/azure/azure-sql/database/serverless-tier-overview) | Partial |

## 3. Platform-Managed / Hidden Resources & Managed Resource Groups (TRAP-PLAT)

| ID | Trap | Why Invisible to Owners | Usage-Truth Signal | Typical Fix | Reversibility / Risk | Source | Status |
|---|---|---|---|---|---|---|---|
| TRAP-PLAT-001 | AKS creates a second "node resource group" (`MC_*`) holding the Load Balancer, public IP, NSG, VMSS nodes and PV disks — it persists for the cluster's entire life and is invisible unless you know to look | Teams review only the resource group they created; the `MC_*` group is auto-created and easy to overlook in cost views | A second `MC_<rg>_<cluster>_<region>` resource group exists per AKS cluster | Budget/alert at the `MC_*` RG scope too; delete cluster (not just workloads) when retiring | High risk — deleting the node RG directly is unsupported and breaks the cluster | [AKS frequently asked questions](https://learn.microsoft.com/azure/aks/faq) | Verified |
| TRAP-PLAT-002 | The Load Balancer inside an AKS or Container Apps-managed resource group is protected by a system "deny assignment" — you can't delete it directly even if you have Owner rights | Admins try to clean up an "orphaned-looking" LB and get a confusing permission-denied error, then give up and leave it | `az network lb show` + deny-assignment lookup shows `Microsoft.ContainerService`/`Microsoft.App` as caller | Delete via the owning AKS cluster or Container Apps environment, not the LB directly | N/A — must go through the parent resource | [Troubleshoot a Load Balancer that can't be deleted](https://learn.microsoft.com/troubleshoot/azure/load-balancer/troubleshoot-cannot-delete-load-balancer) | Verified |
| TRAP-PLAT-003 | Kubernetes-reclaimed PersistentVolume disks in the AKS node resource group can outlive the namespace/PVC that created them, depending on the storage class reclaim policy | Deleting a namespace feels like a full cleanup; the underlying Azure Disk may be left `Retain`-ed | Managed disks in `MC_*` RG with no matching live PVC in the cluster | Set reclaim policy to `Delete` for ephemeral workloads; audit orphaned disks periodically | Medium risk — deleting a Retain-policy disk may destroy data intentionally kept | [AKS disk CSI driver](https://learn.microsoft.com/azure/aks/azure-disk-csi) | Partial |
| TRAP-PLAT-004 | Azure Databricks' managed resource group (cluster VMs, NICs, DBFS root storage account) lives in a separate, Azure-locked resource group most billing reviewers never open | Named `databricks-rg-*`, created automatically, outside the team's normal RG review | Managed RG size/resource count growing without matching increase in reviewed workspace activity | Review the managed RG alongside the workspace in cost reviews | N/A — not directly deletable | [Azure Databricks concepts](https://learn.microsoft.com/azure/databricks/getting-started/concepts) | Partial |
| TRAP-PLAT-005 | Databricks cluster pools keep a configured number of "Min Idle" instances warm and billed as cloud infrastructure even when no cluster is using them | Pools exist to cut cluster start time; the idle-instance cost trade-off is easy to forget once set | Pool `Min Idle` > 0 with low cluster-attach frequency | Set Min Idle to 0 unless fast-start is a hard requirement | Low risk — slightly slower cluster starts | [Databricks pool best practices](https://learn.microsoft.com/azure/databricks/compute/pool-best-practices) | Verified |
| TRAP-PLAT-006 | Azure Managed Applications place resources in a customer-hidden managed resource group locked by a deny assignment — the consuming team often can't even see what's running, let alone its cost drivers | Managed app publishers intentionally hide implementation details; the managed RG rarely gets tagged or reviewed like normal RGs | A `managed by` resource group exists with a deny assignment tied to a Managed Application resource | Review publisher's cost documentation; decommission the managed application if the capability is unused | Varies — governed by the publisher's deletion path | [Azure Managed Applications overview](https://learn.microsoft.com/azure/azure-resource-manager/managed-applications/overview) | Partial |
| TRAP-PLAT-007 | Synapse workspaces with a managed VNet provision managed private endpoints and integration runtime compute inside a Microsoft-managed scope, separate from the customer's reviewed resources | "Managed VNet" is enabled for security, not cost, so its resource footprint is rarely checked | Managed VNet enabled with multiple managed private endpoints, low associated pipeline activity | Audit managed private endpoints against active linked services | Low–medium risk | [Synapse workspace managed VNet](https://learn.microsoft.com/azure/synapse-analytics/security/synapse-workspace-managed-vnet) | Partial |
| TRAP-PLAT-008 | A Virtual WAN Standard hub bills a fixed hourly router charge regardless of how much (or how little) traffic transits it | Hub is provisioned once as core network plumbing and then forgotten as a line item | Hub exists with near-zero inter-VNet/branch traffic over weeks | Consolidate hubs or downgrade topology if traffic never materialized | High risk — re-architecting core connectivity | [About Virtual WAN pricing](https://learn.microsoft.com/azure/virtual-wan/pricing-concepts) | Verified |
| TRAP-PLAT-009 | Agentless disk scanning can be enabled redundantly by more than one Defender for Cloud plan (e.g., CSPM and Defender for Servers) on the same subscription, duplicating scan coverage and cost | Each plan is toggled independently in the portal; nobody cross-checks for overlap | Multiple Defender plans with agentless scanning both enabled on the same subscription | Confirm which single plan should own agentless scanning; disable the duplicate | Low risk | [Agentless machine scanning](https://learn.microsoft.com/azure/defender-for-cloud/concept-agentless-data-collection) | Partial |
| TRAP-PLAT-010 | Azure Backup recovery points accumulate inside a Recovery Services vault's backend storage, which doesn't appear as a normal, ownable storage resource in the resource list | The storage backing a vault is platform-managed, not a customer-visible Storage Account | Vault backup-storage cost trending up with no corresponding change in protected-item count | Review retention/LTR policy against actual recovery needs | Medium risk — reduces recovery window | [Back up Azure Backup recovery points](https://learn.microsoft.com/azure/backup/backup-azure-delete-recovery-points) | Partial |

## 4. Storage Traps (TRAP-STOR)

| ID | Trap | Why Invisible to Owners | Usage-Truth Signal | Typical Fix | Reversibility / Risk | Source | Status |
|---|---|---|---|---|---|---|---|
| TRAP-STOR-001 | Enabling SFTP support on a Storage Account adds a flat hourly charge that applies the entire time it is enabled, whether or not anyone connects | It's a one-time portal toggle; nobody treats "feature flags" as standing meters | SFTP enabled flag = true, zero SFTP-protocol transactions in Storage Analytics for weeks | Disable SFTP when not actively needed; re-enable on demand (config, not data, is lost) | Low risk | [SFTP support in Azure Blob Storage](https://learn.microsoft.com/azure/storage/blobs/secure-file-transfer-protocol-support) | Verified |
| TRAP-STOR-002 | Blob versioning, soft delete, and snapshots each retain full-priced copies of changed data — enabling all three compounds storage growth invisibly in the background | Each is enabled independently "for safety" with no combined-growth alert | Container size growing faster than live (non-version, non-snapshot) blob count | Add lifecycle rules to expire old versions/snapshots; right-size retention days | Low–medium risk — shortens recovery window | [Blob soft delete overview](https://learn.microsoft.com/azure/storage/blobs/soft-delete-blob-overview) | Verified |
| TRAP-STOR-003 | Container soft delete is free to enable but silently bills the full data rate for every soft-deleted container during its retention window | "No extra charge to enable" is read as "no extra charge," full stop | Soft-deleted containers visible via `include=deleted` holding non-trivial data volume | Shorten retention to the minimum useful window (Microsoft suggests 7 days) | Low risk | [Soft delete for containers](https://learn.microsoft.com/azure/storage/blobs/soft-delete-container-overview) | Verified |
| TRAP-STOR-004 | New storage accounts default to Geo-Redundant Storage, silently paying for cross-region replication many dev/test or cache workloads never need | GRS is the path-of-least-resistance default in the portal's quick-create flow | Non-production tag or workload pattern with GRS/RA-GRS redundancy configured | Switch to LRS/ZRS where regional durability is sufficient | Medium risk — changing redundancy has workflow/approval implications | [Azure Storage redundancy](https://learn.microsoft.com/azure/storage/common/storage-redundancy) | Partial |
| TRAP-STOR-005 | Premium file shares are billed on **provisioned** capacity, not actual data stored — an oversized share keeps costing the provisioned amount even if mostly empty | Provisioning is a one-time sizing decision rarely revisited as usage patterns change | Provisioned GiB far exceeds used GiB (Storage metrics) for a sustained period | Shrink provisioned size to match actual + headroom | Low risk (shares can usually be resized down without data loss if within used capacity) | [Understand Azure Files billing](https://learn.microsoft.com/azure/storage/files/understanding-billing) | Partial |
| TRAP-STOR-006 | Blob containers without a lifecycle management policy leave data in Hot tier indefinitely, even when access patterns show it's gone cold | Lifecycle policies are an opt-in feature, not a default | Blob last-access-time much older than its tier's intended access frequency | Add age- or access-based lifecycle rules to auto-tier to Cool/Cold/Archive | Low risk | [Lifecycle management overview](https://learn.microsoft.com/azure/storage/blobs/lifecycle-management-overview) | Partial |
| TRAP-STOR-007 | Archive-tier objects deleted or re-tiered before the tier's minimum retention duration incur an early-deletion charge on top of the rehydration cost | Teams tier-to-archive reflexively without checking the minimum-duration commitment | Archive blobs deleted/rehydrated well inside the minimum retention period | Model minimum retention into lifecycle policy design before archiving | Low risk if planned up front | [Access tiers overview](https://learn.microsoft.com/azure/storage/blobs/access-tiers-overview) | Partial |
| TRAP-STOR-008 | High-transaction-rate small-object workloads (many small reads/lists/writes) can make transaction cost exceed capacity cost, a cost shape most reviewers don't expect | Dashboards default to showing capacity (GB) cost prominently; transaction cost is a separate, less-watched meter | Transaction-meter spend rising disproportionately to capacity-meter spend | Batch small objects, cache metadata, reduce list-operation frequency | Low risk | [Blob storage pricing](https://azure.microsoft.com/pricing/details/storage/blobs/) | Unverified |
| TRAP-STOR-009 | Defender for Storage malware scanning defaults to a 10,000 GB/month per-account cap; once exceeded, scanning **silently stops** for the rest of the month — a security gap hiding behind what looks like a cost control | The cap is a cost-control feature, so nobody expects it to create a protection gap | Scanned-GB metric flatlines mid-month while uploads continue | Raise the cap deliberately or split hot accounts, and alert on cap-reached events | Low risk to fix; high risk if left unnoticed (unscanned uploads) | [What is Microsoft Defender for Storage](https://learn.microsoft.com/azure/defender-for-cloud/defender-for-storage-introduction) | Verified |
| TRAP-STOR-010 | Blob change feed or blob inventory left switched on writes continuous log/report data to a container nobody downstream actually consumes | Enabled for a one-time analytics or migration project, never disabled afterward | Change-feed/inventory container growing with zero recent reads | Disable the feature if no consumer exists; otherwise lifecycle-expire its output | Low risk | [Change feed support in Blob Storage](https://learn.microsoft.com/azure/storage/blobs/storage-blob-change-feed) | Partial |
| TRAP-STOR-011 | Pre-managed-disk ("classic") unmanaged VHD page blobs can be left behind in a storage account after a VM was migrated to managed disks, billed as ordinary blob capacity indefinitely | Migration tooling moves the VM, not always the leftover VHD; the blob looks like generic data | Page blobs named like OS/data disk VHDs with no corresponding managed disk or running VM | Confirm no running classic VM references the VHD, then delete | Medium risk — verify no cold-start/DR dependency first | [Azure Storage overview](https://learn.microsoft.com/azure/storage/common/storage-introduction) | Unverified |

## 5. Network Traps (TRAP-NET)

| TRAP-NET-005 | 🔻 Private Link Service **Direct Connect** (preview) introduced a new $0.675/hour per-resource charge effective October 15, 2026 — brand-new line item easy to miss on bills that previously had none | Feature is in preview and newly priced; teams piloting it won't expect a standing hourly fee | Direct Connect resource present with low/no production traffic | Delete preview Direct Connect resources once evaluation ends | Low risk (preview feature) | [Configure Private Link service Direct Connect](https://learn.microsoft.com/azure/private-link/configure-private-link-service-direct-connect) (read 2026-10-30) | Verified |
| TRAP-NET-006 | A Standard Virtual WAN hub bills a fixed router fee per hour regardless of how much inter-VNet/branch traffic it carries | Core connectivity plumbing, provisioned once, rarely revisited for right-sizing | Hub exists with minimal VNet-to-VNet transit traffic sustained over weeks | Consolidate hubs/topology if traffic never materialized | High risk — core network re-architecture | [About Virtual WAN pricing](https://learn.microsoft.com/azure/virtual-wan/pricing-concepts) | Verified |

## Implications for our idea

- Azure Advisor/Cost Management natively surface only a narrow slice of this catalog (unattached disks, idle public IPs/LBs/ExpressRoute circuits, empty App Service plans, Cosmos DB autoscale candidates, reservation purchase suggestions) — roughly 10 of the 145 items here. The other 90%+ is genuine, defensible whitespace for an agent-driven catalog.
- A large share of the highest-value traps are **silent mechanism failures**, not simple idle-resource waste: AML idle-shutdown blocked by a missing RBAC grant, Defender for Storage malware-scanning cap silently halting coverage, Sentinel's 31-day commitment-lowering ratchet. Detection needs service-specific "is this mechanism actually working?" checks, not a generic low-utilization heuristic.
- "Usage truth" must combine control-plane state with data-plane telemetry per resource type (e.g., NAT Gateway byte/connection metrics + subnet association; AML compute instance Jupyter/VS Code/custom-app session state; Container Apps idle-replica criteria). Billing data alone cannot prove non-use.
- Ownership is hardest to establish exactly where cost hides best: platform-managed/hidden resource groups (AKS `MC_*`, Databricks, Managed Applications, Synapse managed VNet) have no natural human owner. The agent needs an escalation path that walks up to the owning parent resource (cluster, workspace, subscription) and its tags/RBAC, not the orphaned child object itself.
- Several traps are **one-way ratchets**: ExpressRoute Unlimited→Metered, ExpressRoute Premium downgrade blocked past VNet/route thresholds, Sentinel commitment step-down cadence, Container Apps zone-redundancy disablement, Hyperscale backup-redundancy lock-in. The human-approval workflow must explicitly warn "this cannot be undone" before executing these, distinct from safely-reversible fixes.
- Reversibility varies enormously and should drive the Teams-card risk framing: orphaned-resource deletions are low-risk with a snapshot-first step; config toggles (TTL, min_nodes, auto-termination, lifecycle policy, idle-shutdown minutes) are low-risk and reversible; redundancy/SKU/commitment changes are often irreversible or slow to reverse and need a higher approval bar.
- Several items are explicitly **retiring or legacy** (Defender for Storage classic per-transaction plan, Azure OpenAI legacy Commitment model, multi-step Application Insights web tests, Power BI Premium P-SKU→Fabric F-SKU behavior change, Basic-SKU Public IP/LB). The opportunity catalog needs an ongoing freshness/retirement-watch job, not a one-time load, since these mechanisms change on Microsoft's schedule, not ours.
- Network and AI/data-platform categories produced the richest "nobody notices" mechanisms (NAT Gateway/Firewall/Private Link processing fees and take-over-the-subnet behavior; PTU-cannot-pause; Fabric pause-stops-compute-not-storage; AI Search's multiplicative Replica×Partition cost). These two verticals look like strong candidates for the MVP opportunity catalog given both novelty and dollar magnitude.
- Most fixes here are **property patches**, not resource deletions: idle-shutdown minutes, `min_nodes`/min-replica counts, TTL values, auto-termination settings, lifecycle-management policies, redundancy flags. This favors an "execute approved fix" action set built mostly on ARM/REST property updates — a smaller, more auditable blast radius than a fleet of delete operations.
- A non-trivial number of entries here are `Partial` or `Unverified` because they rest on stable, well-documented but not freshly-refetched mechanisms, or on community corroboration rather than a primary doc page read this session. The opportunity-catalog schema should carry source quality/verification status as a first-class field, so the agent can calibrate auto-approval thresholds (e.g., require human sign-off more readily on `Unverified` items).
- FinOps-governance traps (tagging, subscription sprawl, unreviewed Advisor recommendations) are the connective tissue behind almost every other category: they are why orphaned/platform-managed/pricing-mechanism waste survives undetected for so long. A governance layer (enforced tagging, budget alerts, Advisor-to-ticket routing) is a multiplier on every other opportunity in this catalog, not a category to treat as lower priority.
