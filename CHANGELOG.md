## The Watch reads every subscription that its identity can read (built, not deployed) — 2026-11-07

**What the owner ordered.** In writing: "Watch is what checks for cost savings? That must be on the root management group; watch the entire estate."

**What changed.** The Watch no longer reads only the subscription that its setting names. At the start of every run it asks Azure which subscriptions its own identity can read (the enabled ones, at most 1,000) and reads those, so a person widens or narrows it with the read roles that they give the identity. The setting is `SCOPE_ALL_SUBSCRIPTIONS` (Bicep default false; the Hub's builder passes true, one constant in `tools/environment-params.py`). `SCOPE_SUBSCRIPTIONS` stays as the fallback; with neither, the run says why and stops. The limits are as they were: three cases, the same tokens and calls. A large estate gets 60% of the run's deadline for reading, and the subscriptions that were not read are named in a note. `run.started` carries the count and the first five ids. A change can still be made only in the one resource group of the loop.

**What a person does.** On the owner's word, give the cases app's identity *Reader* and *Cost Management Reader* at the tenant root management group: `python tools/access-requirements.py grant --estate <the group's id> --only R1,R2` (a dry run; `--apply` makes it), then run the Hub actions `cases` and `cases-run` ([the bootstrap page](environment/BOOTSTRAP.md#changed-on-2026-11-07-the-watch-reads-every-subscription-that-its-identity-can-read)). **Not checked.** Nothing ran against Azure: not the list call, not the throttling of Resource Graph and Cost Management on many subscriptions, not a grant at a management group. ## The AI Gateway's subnet is made first, and the gateway after the landing zone's route table: built, not deployed — 2026-11-07

**What was found.** The action `aigateway` made the subnet `snet-aigw` and the gateway in one deployment, and its wait for the landing zone's route table came after the gateway was made. Three things make that order wrong. (1) The landing zone's network manager puts one managed route table on a new subnet some 70 seconds to five minutes after the subnet is made: 70 seconds the first time and four minutes and 36 seconds the second, for the subnet of the first cases (the entry of 2026-11-05 below). (2) The service takes the gateway's backend subnet when the gateway is made and treats it as read-only afterwards ([the decision record](docs/proposals/08-ai-gateway.md#the-subnet-cannot-be-changed): the sources disagree, so it is treated as fixed). (3) A creation of the gateway that fails may keep the subnet for a long time (a risk that was named and is not verified here), and a small virtual network has little room for another range. So the first creation of the gateway must not race with the network manager's write to the subnet, and it must see the subnet as the landing zone leaves it. [Rule 27](AGENTS.md) is the precedent: a template makes a subnet once and never undoes what the landing zone added to it. Nothing here was found by a run: the action has not been run.

**What changed.**
- **Two templates and two parameter files.** [`environment/aigateway/subnet.bicep`](environment/aigateway/subnet.bicep) is new. It makes the network security group and the subnet exactly as `main.bicep` did (delegated to `Microsoft.App/environments`, no default outbound access, made only while it is not there) and gives the name of the subnet. [`environment/aigateway/main.bicep`](environment/aigateway/main.bicep) no longer makes or reads a network resource and no longer takes the two parameters of the subnet; it names the subnet by its id, so the subnet has to be there when it is deployed. Everything else in it is as it was. [`tools/environment-params.py`](tools/environment-params.py) writes `aigateway-subnet.parameters.json` (location, owner, range, whether the subnet is there) and leaves those two parameters out of `aigateway.parameters.json`. Its printed outputs are as they were.
- **The order in `aigateway`.** The early checks as before. Then **make the subnet**, when the network step found it missing (when it is there, the step says so and leaves it alone). Then **wait** for the route table: the same wait, 40 checks half a minute apart with the endpoint subnet as the yardstick, and its texts now say that the gateway is not made yet and, on a timeout, that it was not made. Then a **new sign-in**, because the first credential is old after the subnet's deploy and the wait, which can take about 25 minutes. Then **make the gateway**. Then the second sign-in, the limits, the built-in key and the read-back, as before. `what-if` previews the subnet's template and then the gateway's. The description of the action, the summaries of a stop and of a success, the compile and lint of both workflows and the check of the parameter files know the new template and file. Every other action is as it was.
- **The comment on the subnet's network security group** says what Microsoft's own private networking sample does (`infra/private-network.bicep`, read on 2026-11-07): it adds two allow rules, outbound 443 to `Storage` and to `AzureKeyVault`, and no deny rule, so beside the default rules they change nothing, and none is made here. The comment that `main.bicep` had since step 1 said that those rules belong to the older API Management gateway. That was wrong, and the new comment and the row of [the decision record](docs/proposals/08-ai-gateway.md#what-is-verified-what-is-inferred-what-is-not-known) about the network security group now agree with the sample.
- **Documents.** [The decision record](docs/proposals/08-ai-gateway.md#the-subnet-is-made-first-and-the-gateway-after-the-landing-zones-route-table) has a section with the order and a table of what each stop means, [the bootstrap page](environment/BOOTSTRAP.md#added-on-2026-11-07-for-the-ai-gateway) has the order and the way back, and the README lists both templates. [Rule 15 (c)](AGENTS.md) and [rule 27](AGENTS.md) are unchanged, because nothing in them became untrue.

**What was checked.** The whole suite of the tools passes on the CI runner (1,545 tests, against 1,500 on main before this change; the 45 new ones are all in the new test module). The usage app's 159 tests and the cases app's 2,046 are unchanged and pass. **The open question, and why this step exists.** Can a Foundry project's connection call this gateway with the project's own managed identity and no key? [Rule 23](AGENTS.md) says no key. Microsoft's only sample of a connection to this service uses an API key (category `ModelGateway`). Microsoft's sample of the category `ApiManagement` with the project's managed identity has an audience and no key, but every example of it points at `*.azure-api.net`. Nobody has tried it for this service, and neither has this change. So the connection is built in that second shape, and a failure is made easy to read and easy to undo, so that the real run answers the question. If the connection needs a key, the owner decides, and no path for a key is built.

**What is built.** Code, tests and documents. Nothing is deployed: no Azure change, no Hub run and no workflow run was made, and the agents were not touched.
- **The switch.** While it is False every parameter file is the same byte for byte (a test pins the files that exist against the hashes of what the builder wrote before this change) and every new parameter is empty or false. ## Meternaut holds no right to change Azure any more: a change runs as the person who approves it — 2026-11-05

**What changed in the design** (the decision is [AGENTS.md](AGENTS.md) rule 29; the record is [run as the approver](docs/proposals/05-run-as-the-approver.md)). The console redeems the code with the federated credential of a managed identity (no secret), checks that the ID token names the same person, the same tenant, this client and this request, records the approval, and makes the one delete with the person's own access token. The token lives in memory for that request. Azure checks the person's own rights, and its Activity Log names the person. Nothing is recorded before the person returns, so the 120-second delay and the cancel button are gone (a cancel would need a stored token). ## design-v1 (record) — 2026-11-01 — design phase 1: architecture, decisions, cost model and test strategy

**Why.** With the ideation frozen (tag `ideation-v4`), the design was requested: completely AI-driven; Microsoft Foundry and the Microsoft Agent Framework; every AI part deployed through the Citadel framework in the adopting organisation's landing zone; every safeguard and drift control; security, compliance, test and governance; every technology decision put to two review rounds on different models; and as cost-efficient as possible.

**What.** [`docs/_archive/design-v1/design/`](docs/_archive/design-v1/design/README.md) — an index and fourteen documents (about 157,000 words): requirements and principles · technology landscape · logical architecture · landing zone and Citadel · agents and orchestration · data and knowledge · security architecture · governance and compliance · safeguards and drift controls · test and evaluation · delivery and operations · cost and FinOps · 37 decisions · next phases. Evidence is in [`docs/_archive/design-v1/design/research/`](docs/_archive/design-v1/design/research/) and in a snapshot of 2,468 Azure price meters. Still no code.

<details>
<summary>The detailed record of the withdrawn design (long; kept for the record, not needed to read the current design)</summary>

### The design in six lines
- **A deterministic spine with agentic leaves**: Durable Functions workflows call fourteen hosted-agent roles (fifteen Entra agent identities, eleven contract groups, twelve contracts) one step at a time through the Citadel hub; agents can only read; the Agent Framework runs only inside the leaves.
- **One small execution plane can change an estate**, and *no single credential completes a change that needs a person's web-page approval*: a Policy permit, a person's Entra-signed approval bound to the target and the decision, an Approval service that signs and starts nothing, a broker that verifies and leases, an event-driven runner that verifies again and acts as an identity that exists only for that Move, write-ahead entries in an append-only ledger. What remains is stated in one place and repeated verbatim.
- **Nineteen drift layers** (each with prevent, detect and correct) and **twenty detections**; a preview register in which every preview feature sits behind a switch with a generally available fallback.
- **A statistical test protocol** with signed gate evidence and an exam the system cannot see.
- **A cost model in code** — about €1.2k a month at Pilot, €4.3k at Team and €27k at Enterprise scale (shared hub, list prices) — and a budget that is the spine's atomic reservation of the worst case of every metered part of a call, with the hub's limits as a second layer.
- **34 spikes** that could invalidate a decision, in seven build phases; nothing that changes an estate is switched on before S-ID-1, S-ID-3 and S-ACT-1 pass.

### How it was reviewed
Three passes and a closure check, nine models, every lens on a different model each time. **Round 1** (five lenses: architecture · security, safety and compliance · cost and operability · AI engineering, evaluation and drift · platform fact-check) found 77 issues; **Round 2** reviewed the revision with other models and found 55 (about 45 distinct); a **targeted third pass** by two further models on the parts Round 2 had *redesigned* found 33 more. Those two reviewers then **checked closure** on the fixes (each finding CLOSED with a quote, CLOSED-WITH-RESIDUAL or OPEN) and found that the fixes had reopened 8 findings and introduced 14 new defects, four of them Critical and all in the authority chain; every platform claim was read on Learn before it was acted on; a bounded re-check then found 5 more (one Critical: the lock and the kill switches rested on a measured replica lag that Session consistency does not bound) and a last confirmation found 2, in the observer of the sweeper's removals; the loop stopped there. Raw reports are kept verbatim in [`docs/_archive/design-v1/reviews/`](docs/_archive/design-v1/reviews/design-v1-third-pass/disposition.md) with the orchestrator's own spot-checks and a disposition for every finding.

### What review changed
- **The spine** moved from a custom checkpoint-and-jobs design to Durable Functions on Flex Consumption (Round 1).
- **The execution chain** was reversed twice and hardened a third time: the broker no longer grants *and* dispatches (Round 1); the signer no longer starts the runner, which is event-driven (Round 2, after Learn confirmed that starting a Container Apps job can override its template); the third pass bound the decision into the sign-in nonce, made control items and markers verifiable by signature ("only narrowing is unsigned"), put write-ahead entries before every effect, required the broker to read the approval's own ledger block, and found two things that could not have been deployed — a private endpoint in a delegated subnet and cross-environment calls over internal ingress.
- **The leaf-call rule**: a hosted agent that returns at once is deprovisioned at its idle timeout, so each role's timeout now covers its active time, and completion is a persisted, identity-bound `run-result` record with the event only as a doorbell.
- **The budget**: the hub's token limits are not euros; the spine's reservation now covers tokens, session compute, screening and tools, and the hub refuses any caller-supplied service tier (a request-level priority tier would have been billed at a rate nothing priced).
- **The cost model was rebuilt** and the estimate more than doubled for Team (draft €657 / €1,818 / €17.5k a month for Pilot / Team / Enterprise → €1,244 / €4,278 / €27.0k): it now counts one product per contract and environment, hosted-agent compute including the idle tail, prompt-cache write prices, Content Safety windows, always-ready Flex capacity (which has no free grants), the gate plan and the evaluation work that carries the design's claims (evaluation costs 9.3 / 3.6 / 0.6 times the production cases).
- **The closure check** showed that the fixes had made new holes, so the authority chain changed most late: the approve sign-in starts only from a click (a decline yields no approve token, and the residual that a page can still induce a sign-in is stated); a queue's consumer can put to it, so every sender set is exact and a queue is a doorbell; the deployment lock became a two-sided protocol with fresh reads and a heartbeat; the ledger position is a separate marker because an approval record is never amended; a marker conflict fails closed; the sweeper writes nothing and the Verifier records what it removed; a saving counts only once the Auditor has corroborated it from the cost export; the run registry has its own container, arbitration is first write wins and a crash between the facade's two writes is repaired by the next call; a Move's step checks read the kill switches fresh; every Move class needs a harmless probe; freshness is anchored on the ledger's append time; and, after the re-check, the control state is read at Strong consistency (a documented guarantee instead of a measured lag), a per-run token that only the wrapper holds keeps two runs of one role apart, the wait counter is signed, and a scheduled observer records the sweeper's removals from a stateless 24-hour window.
- **Foundry layout**: two projects per account, not nine; environments and private accounts are created in the phase that needs them.
