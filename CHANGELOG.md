## The first environment is partly deployed; the gateway step failed twice and is fixed — 2026-11-03

**What is in Azure now** (read back from the services after each run, not taken from the logs). The model side: a small network, the private model account (no public access, no keys) with two models, one private endpoint that the landing zone's policy registered in the central DNS by itself, a budget, and the role that lets the gateway's identity call the models. In the owner's API Management instance: the new identity attached (its own identity kept; its host names, TLS settings and network compared before and after, and unchanged), one logger on the Application Insights that it already uses, and what the two failed `gateway` runs left: the module's backends, named values and 22 policy fragments, and the Azure OpenAI API without a policy, a diagnostic or a backend (nothing can be reached through it). **Cost:** about 6.6 euros a month for the private endpoint, plus tokens.

**What failed, first.** The first `gateway` run (Citadel's module) stopped at two of its policy fragments, `ai-usage` and `pii-state-saving`. They send usage records to an Event Hub through two loggers, and the service refuses to save a fragment whose logger does not exist ("Logger not found"). The module does not make those loggers: the kit's own deployment does, together with the Event Hub. The run left the module's backends, named values and the other policy fragments in the instance, and no API; the instance's service-level logging setting was not touched.

**A first fix that did not work.** Two empty placeholder loggers, naming an address that cannot exist, were tried through `gateway-prepare`. The service refused them too: it checks that a logger's address resolves ("No such host is known"). Nothing was left half-made by that run, and the placeholders are gone from the repository again.

**The fix.** The two fragments are left out. A small patch to the kit's checkout, [`environment/kit-patches/no-usage-recording-fragments.patch`](environment/kit-patches/no-usage-recording-fragments.patch), makes the module create them only when a new parameter says so, and the parameter is off. Nothing is lost, because neither of the two APIs, nor the first contract's policy, includes those two fragments (a test holds that for the policy; the kit uses the fragments only in its own access-contract policy templates), and the tokens of a call are counted by another fragment and go to Application Insights. The usage recording itself (Event Hub, Logic App, Cosmos DB, about 265 euros a month) stays out, as decided; a real Event Hub alone, which would have let the placeholders work, would have cost about 26 euros a month for nothing that reads it. When the usage recording is added, the patch goes. The deploy workflow and the checks both apply the patches to the kit (`git apply --check` first, so a patch that no longer fits stops the run), and the checks compile the patched module.

**What failed, second.** The next `gateway` run got as far as the APIs and stopped at three more things that only the real service says (the what-if shows none of them, because it does not check policies): the policies of both inference APIs include a fragment, `set-response-headers`, that the module creates only when its Unified AI flag is on, so the service refused them; the service refuses the value `none` for the LLM log settings of an API; and the two APIs are imported at the same moment and both create the same tags, so one import found a tag that the other had just made (the tags exist now). Fixed: the Unified AI flag is on while the API itself stays off (its fragments are four small, unused policy fragments); a third patch, [`environment/kit-patches/llm-log-messages-none.patch`](environment/kit-patches/llm-log-messages-none.patch), leaves the request and response log settings out when the parameter says `none`, which is how the service wants "no prompts, no answers" said; and the tag race needed nothing, because the tags existed by the next run, which went through.

**In this change too, and not yet run.** The workflow's `contract` action (a product that grants the two inference APIs, with its policy and one key, then a test of the gateway with that key), its template, its test tool and their tests. A review found four things to fix before it is run. Fixed: a self-service request in the developer portal could take the key's one slot (a request now needs approval); the check of the policy read only its top level (it now allows only the template's rules, at any depth, in the template's order); and the test could not be repeated (a new key that the gateway does not know yet, and a key still over its allowance from an earlier run, are waited for; the model's own refusals are not). The fourth finding, that the instance's own all-access key (and any key that is not tied to a product) is not held back by a contract, is closed by a fourth patch, [`environment/kit-patches/contract-required.patch`](environment/kit-patches/contract-required.patch): the policies of the two inference APIs now refuse any call that is not made with the key of a contract (403, `contract_required`), after the kit's own key check, so there is no unlimited way to the models, and the gateway run reads the rule back from the instance. The all-access key still works for the instance's other APIs; it no longer works on these two. The `contract` action has not been run yet.

**Rules.** [AGENTS.md](AGENTS.md) rule 21 records the approval; rules 15, 18 and 19 apply.

## The first runs of the workflow, and what the real services said — 2026-11-03

**What.** The owner said that he merges and clicks nothing himself and that the agent runs it all, so the agent merged the pull request for the hub and started the workflow with `what-if`. Three things the real services said, each an item on the README's list of what had not been seen, stopped the first runs; each is fixed, and each has a test that fails on the previous code.

- **The first run stopped at the sign-in** (AADSTS700213). GitHub presents this repository to Azure with the numeric ids of its owner and of itself in the subject (the repository's own setting says so), and the credential had been made with the plain `repo:<owner>/<repository>` form that the bootstrap page gave. The credential's subject was corrected in place, a step of the bootstrap that the owner had approved, with the same meaning (this repository, the `main` branch) and now bound to the ids, so that a repository that later gets the same name cannot use it. The page reads the prefix from the repository's setting.
- **The second run signed in and read the instance, and stopped at the budget.** The Budgets API answers a missing budget with `Not Found(...)`, and the step recognised other words, so it took a missing budget for an error. The budgets of the group are now listed and filtered by name (a missing budget is an empty list and no error text is read), in the deploy and in the removal. The shell simulation, which had made up another not-found text, now uses the real one.
- **A read-only dry run against the real instance** (`tools/apim-sync.py plan`, with the owner's account, which the rules allow) found, before it cost a third run, that the instance answers a GET on the link between a product and an API with `405`: Microsoft's reference defines only HEAD, PUT and DELETE for it, and no `If-Match`. The tool now looks for the link with HEAD and sends no `If-Match` for it. Reading the reference for every kind of object also showed that deleting an API answers `202` or `204`, so a `202` is now waited for until the API is gone (it would have broken `pause` and `remove`). The stand-in for the instance in the tests behaves in each of these ways, and 36 of the tests fail on the previous tool.
- **An ARM preflight validation** of the real template against the hub's group (`az deployment group validate`, read-only) passed: no policy of the landing zone denies it.
- **The first deploy stopped at the private endpoint** (`IfMatchPreconditionFailed` on the model account). The endpoint's connection is written to the account with an If-Match, and the role assignment that the template makes on the same account had finished two seconds before and had changed it. Nothing was lost: the network, the account, the model deployment, the budget and the role assignment were made, and the endpoint stayed in a failed state. The template now makes the role assignment after the endpoint, so that nothing else writes to the account while the endpoint does, and the deploy step tries again, up to three times, on this one answer. A new test locks that order and the list of resource types that the template may declare, which also keeps a private DNS zone, a peering and a second API Management instance out. The simulation, which could not have shown it, has the service's own text for it now.
- **The endpoint stayed failed, and a second deploy could not repair it** (`InvalidResponseFromPrivateLinkService`: the account still held the connection of the first attempt). The workflow's `pause` action deleted it (the first `pause` run met a crash of the Azure CLI on the runner, an import deadlock, before any delete was sent; the second did it), and the next `deploy` made it fresh. The landing zone's policy registered its name in the three central zones within minutes, the gateway objects were added to the instance, and the smoke test passed its first five checks on the real route: a completion with token usage, 401 without a key and with a wrong one, 403 for another model and for none. The deploy step now also tries again when the CLI stops on that deadlock.
- **The token-rate check failed on the model, not on the gateway.** Its large request asked for a reply of one token, and the model reasons before it answers, so the service refused with a 400. The request now asks for room (256 tokens) and ends with the short instruction of the first check. The stand-in for the model refuses a cap of one token in the same way, so the old check fails the tests.
- **A DELETE of an object that is not there answers 204**, which the tool reported as "deleted": the first `pause` showed four objects "deleted" that had never been added. Each object is now read before it is deleted, and what was not there is "absent", with no DELETE sent.

**The rules.** That the owner does nothing himself changes how a run is approved. [AGENTS.md](AGENTS.md) rule 18 and [`hub/BOOTSTRAP.md`](https://github.com/tinodo/meternaut/blob/implementation-v0/hub/BOOTSTRAP.md) now say what is true: on the Free plan the workflow's guard cannot tell the owner's click from a run that an agent starts with his token, so the approval is his plain words in the conversation, a rule of process and not a technical barrier. The agent starts `what-if` on its own; `deploy`, `pause` and `remove` each need his words.

**Checks.** The tools' tests are 191 (from 177), the shell simulation 69 checks, and the rest as before. A narrow independent review of the first fixes (gpt-6.1-sol) found no Blocker or Major and one Minor: in the removal, a budget list that could not be read was taken for "the budget exists" (it could only ever have reached the one budget the template makes). The list is now read by a plain assignment, so a failure stops the step, and a count other than 0 or 1 stops it too.

## The hub, rebuilt as a workflow in the owner's API Management instance — 2026-11-03

**What.** [`hub/`](https://github.com/tinodo/meternaut/blob/implementation-v0/hub/README.md) now builds the development hub the way the rules say. A Bicep template makes a Foundry account with one model behind one private endpoint, a small network on the landing zone's DNS server and a budget, in a resource group of its own. A set of objects whose names start with `meternaut-` goes into the owner's existing API Management instance (an API with its operation, a product that is the contract, the contract's key, two policies and a diagnostic), and nothing else on it is touched. One GitHub Actions workflow, [`deploy-hub.yml`](https://github.com/tinodo/meternaut/blob/implementation-v0/.github/workflows/deploy-hub.yml), does all of it (`what-if`, `deploy`, `pause`, `remove`): it starts only by hand, runs only on `main` and only for the owner, and writes to the instance only after the landing zone has registered the endpoint's name. **Nothing is deployed, and nothing in Azure was changed to build it.**

- **The one manual step** is creating the deployment identity ([`hub/BOOTSTRAP.md`](https://github.com/tinodo/meternaut/blob/implementation-v0/hub/BOOTSTRAP.md)): its rights, what they cannot do (it can delete its own resource group), and the exact commands. It waits for the owner's yes.
- **Tools.** `tools/apim-sync.py` (the gateway objects; it refuses anything but `meternaut-` objects and refuses to write outside GitHub Actions), `tools/hub-params.py` (checks every setting, works out the account's name), `tools/hub-smoke.py` (checks the hub with real calls; a check passes only with evidence) and `tools/workflow-lint.py` (pinned actions, no expression inside a script, the owner-and-main guard on the one job). The tools' tests grew from 47 to 177.
- **Removed.** The accelerator, its patch and parameter files, the DNS template and the old contract's files. The CI step that fetched the accelerator is replaced by the workflow lint, a YAML check and the compile of the new template.
- **Corrected.** Design documents 02, 09 and 11 said that `hub/` deploys the accelerator; they now say that it adds a development contract to an existing instance. The cost model prices one private endpoint (about 6.4 euros a month) and the contract's token quota (about 1 euro if used in full); the old hub's gateway, event hub, vault, DNS zones and log ingestion are gone from it.

**Why.** [AGENTS.md](AGENTS.md) rules 18 and 19: every change to Azure goes through a workflow, and the landing zone's services (the gateway, the DNS, the network) are reused, never built again.

**How it was reviewed.** One reviewer on another model family (gpt-6.1-sol) read the package: 13 findings (1 Blocker, 8 Majors, 4 Minors), each answered ([the record](docs/reviews/README.md#the-rebuilt-hub)). The Blocker: the instance's id could end in `?api-version=...#`, and everything after the `#` is not sent, so removing a `meternaut-` object would have removed the instance. It was reproduced, then fixed in three layers, and the new test fails on the old code. A closure round closed 10, closed 3 in part and found 3 new defects, among them a Major: the service answers a write with `200` or `201` and `InProgress`, so the tool now waits after every write, not only after a `202`. The workflow's shell steps were also run against a fake Azure CLI (sixty checks). A final, narrow check found the package safe to hand to the owner as a pull request and one Minor: the workflow lint could be fooled by an `if:` line inside a quoted value, because it reads one line at a time. It was reproduced and fixed at the root (a value that goes on over several lines is refused), and CI now also reads `deploy-hub.yml` with a real YAML parser and checks the owner-and-main guard from the parsed structure; that check was seen to fail on a throwaway branch with the guard removed.

**What it does not show.** The first deploy has not run. The record of what is not yet seen is in [the README](https://github.com/tinodo/meternaut/blob/implementation-v0/hub/README.md#what-has-been-checked-and-what-has-not): the identity's real rights, that the landing zone's policy registers the endpoint and the name then resolves from the instance, that the instance accepts the objects and policy expressions, that the token limit refuses as designed, and a whole lifecycle. Check C1 stays open.

## ideation-v5 and design-v3 — 2026-11-01 (tags `ideation-v5`, `design-v3`)

## design-v1 (record) — 2026-11-01 — design phase 1: architecture, decisions, cost model and test strategy

**Why.** With the ideation frozen (tag `ideation-v4`), the design was requested: completely AI-driven; Microsoft Foundry and the Microsoft Agent Framework; every AI part deployed through the Citadel framework in the adopting organisation's landing zone; every safeguard and drift control; security, compliance, test and governance; every technology decision put to two review rounds on different models; and as cost-efficient as possible.

<details>
<summary>The detailed record of the withdrawn design (long; kept for the record, not needed to read the current design)</summary>

### The design in six lines
- **A deterministic spine with agentic leaves**: Durable Functions workflows call fourteen hosted-agent roles (fifteen Entra agent identities, eleven contract groups, twelve contracts) one step at a time through the Citadel hub; agents can only read; the Agent Framework runs only inside the leaves.
- **One small execution plane can change an estate**, and *no single credential completes a change that needs a person's web-page approval*: a Policy permit, a person's Entra-signed approval bound to the target and the decision, an Approval service that signs and starts nothing, a broker that verifies and leases, an event-driven runner that verifies again and acts as an identity that exists only for that Move, write-ahead entries in an append-only ledger. What remains is stated in one place and repeated verbatim.
- **Nineteen drift layers** (each with prevent, detect and correct) and **twenty detections**; a preview register in which every preview feature sits behind a switch with a generally available fallback.
- **A statistical test protocol** with signed gate evidence and an exam the system cannot see.
- **A cost model in code** — about €1.2k a month at Pilot, €4.3k at Team and €27k at Enterprise scale (shared hub, list prices) — and a budget that is the spine's atomic reservation of the worst case of every metered part of a call, with the hub's limits as a second layer.
- **34 spikes** that could invalidate a decision, in seven build phases; nothing that changes an estate is switched on before S-ID-1, S-ID-3 and S-ACT-1 pass.

### How it was reviewed
Three passes and a closure check, nine models, every lens on a different model each time. **Round 1** (five lenses: architecture · security, safety and compliance · cost and operability · AI engineering, evaluation and drift · platform fact-check) found 77 issues; **Round 2** reviewed the revision with other models and found 55 (about 45 distinct); a **targeted third pass** by two further models on the parts Round 2 had *redesigned* found 33 more. Those two reviewers then **checked closure** on the fixes (each finding CLOSED with a quote, CLOSED-WITH-RESIDUAL or OPEN) and found that the fixes had reopened 8 findings and introduced 14 new defects, four of them Critical and all in the authority chain; every platform claim was read on Learn before it was acted on; a bounded re-check then found 5 more (one Critical: the lock and the kill switches rested on a measured replica lag that Session consistency does not bound) and a last confirmation found 2, in the observer of the sweeper's removals; the loop stopped there. Raw reports are kept verbatim in [`docs/_archive/design-v1/reviews/`](docs/_archive/design-v1/reviews/design-v1-third-pass/disposition.md) with the orchestrator's own spot-checks and a disposition for every finding.

### What review changed
- **The spine** moved from a custom checkpoint-and-jobs design to Durable Functions on Flex Consumption (Round 1).
- **The execution chain** was reversed twice and hardened a third time: the broker no longer grants *and* dispatches (Round 1); the signer no longer starts the runner, which is event-driven (Round 2, after Learn confirmed that starting a Container Apps job can override its template); the third pass bound the decision into the sign-in nonce, made control items and markers verifiable by signature ("only narrowing is unsigned"), put write-ahead entries before every effect, required the broker to read the approval's own ledger block, and found two things that could not have been deployed — a private endpoint in a delegated subnet and cross-environment calls over internal ingress.
- **The leaf-call rule**: a hosted agent that returns at once is deprovisioned at its idle timeout, so each role's timeout now covers its active time, and completion is a persisted, identity-bound `run-result` record with the event only as a doorbell.
- **The budget**: the hub's token limits are not euros; the spine's reservation now covers tokens, session compute, screening and tools, and the hub refuses any caller-supplied service tier (a request-level priority tier would have been billed at a rate nothing priced).
- **The cost model was rebuilt** and the estimate more than doubled for Team (draft €657 / €1,818 / €17.5k a month for Pilot / Team / Enterprise → €1,244 / €4,278 / €27.0k): it now counts one product per contract and environment, hosted-agent compute including the idle tail, prompt-cache write prices, Content Safety windows, always-ready Flex capacity (which has no free grants), the gate plan and the evaluation work that carries the design's claims (evaluation costs 9.3 / 3.6 / 0.6 times the production cases).
- **The closure check** showed that the fixes had made new holes, so the authority chain changed most late: the approve sign-in starts only from a click (a decline yields no approve token, and the residual that a page can still induce a sign-in is stated); a queue's consumer can put to it, so every sender set is exact and a queue is a doorbell; the deployment lock became a two-sided protocol with fresh reads and a heartbeat; the ledger position is a separate marker because an approval record is never amended; a marker conflict fails closed; the sweeper writes nothing and the Verifier records what it removed; a saving counts only once the Auditor has corroborated it from the cost export; the run registry has its own container, arbitration is first write wins and a crash between the facade's two writes is repaired by the next call; a Move's step checks read the kill switches fresh; every Move class needs a harmless probe; freshness is anchored on the ledger's append time; and, after the re-check, the control state is read at Strong consistency (a documented guarantee instead of a measured lag), a per-run token that only the wrapper holds keeps two runs of one role apart, the wait counter is signed, and a scheduled observer records the sweeper's removals from a stateless 24-hour window.
- **Foundry layout**: two projects per account, not nine; environments and private accounts are created in the phase that needs them.
