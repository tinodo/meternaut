## The name — 2026-11-02

**What.** The product, called "Azure Cost in Action" until now, is called **Meternaut**: an explorer of billing meters. The documents, the tools, the card templates with their sample data and the pictures use the new name, and the card pictures were drawn again (`tools/render-cards/screenshot-cards.cjs` does that). The repository is `tinodo/meternaut`; the old address redirects.

**Why.** Microsoft's [trademark guidelines](https://www.microsoft.com/en-us/legal/intellectualproperty/trademarks) do not allow a Microsoft brand, such as Azure, in the name of a product, a service, a domain name or an account. Saying what the product is built on is allowed, and the README now does.

**Not changed.** The entries below and the review records keep the old name, because they say what was true when they were written. The name is a working name; an organisation that adopts the product may rename it, and the design already says so.

**What.**

**How it was reviewed.** Two reviewers on different model families read the specification before any plan document was written (25 findings, each checked and answered). Five cold readers on five more model families then read the written plan and filed 84 findings (14 Blockers). Each was checked against the files, and each claim about a Microsoft product was re-read on Learn first. One reader's claim, that hosted agents need a container registry, was wrong, and another's was right: Learn marks the default region as in high demand for new search services. A third reader showed that a Learn page was cited for more than it says, and the sentence was corrected. Two closure checkers on other models then verified every finding against the fixed plan: 58 closed, 20 closed only in part or open and 9 new defects, one of them a Blocker in the mail check (Graph answers `202` before a mail-flow rule runs, so a `202` cannot show that the recipient protection failed). **Not adopted.** A check for slice 0.1; a dependency from the cost lake to Atlas v0; moving the approval page's sign-in test to later phases; hosted agents in a container registry.

**Not claimed.** Nothing is built, and no size, duration or cost in the plan is a result: sizes are scenario parameters until the first slices are measured. None of the checks has been run. Which region works on the day depends on Azure's capacity then.

## design-v4 — 2026-11-01 (tag `design-v4`)

**Why.** An independent AI reviewer read `design-v3` and filed 26 findings. Each was checked against the files first: 10 were confirmed and fixed, 6 were partly right (the gap was fixed), 5 were already covered or stale, 2 were not adopted, 3 were judgements that the changes reflect ([disposition](docs/reviews/validation-1/disposition.md)).

**What changed.**

- **The roadmap now starts with value on one estate.** Phase 1 is split in two. Phase 1a runs the Operate profile with read roles only on a first estate, sends the Diplomat's Monday digest by e-mail, and ends when the FinOps lead has confirmed a pre-set number of findings as true and worth acting on, with cost per confirmed finding read from hub logs. Phase 1b proves that the system learns. Before, the first phase needed a real estate and a digest while the profile that could read one arrived a phase later. A failed learning test (P6) no longer falls back to "more Detectors": it withdraws the learning claim and reopens the goals. The Auditor settles changes that owners make themselves in phase 2, so the first verified saving no longer waits for the action stack.
- **Rules that were implied are now written.** A trial is offered only where the change is R1 (non-production), the guard metric must report faster than the change could do harm, and no credential covers a trial. Evidence labelled `bill-observed` never rests on usage taken from the bill. An outcome with a coinciding change, price change or load shift is *undetermined*, counted as unscored: it never counts as a hit, never narrows a range and may only widen one. A Detector is promoted against numbers written beforehand, shadows every scope and becomes active only where it passes. A new estate gets no expected saving until onboarding thresholds are met. The learning test gains an audit of every gain and, when a real launch falls after the snapshot, predictions recorded with the snapshot's hash before its first invoice. The ideation documents now say a trial runs only in non-production.
- **Goals and cost.** A goal and a report-card measure for effort and time to value. Requirement F11 states its exception (scopes with no Cost Management data). The cost model prices investigations that end without reaching an owner (a seed of one per case): about €332 a month at Pilot (was €311), €1,002 at Team (€795) and €6,831 at Enterprise (€4,760), still at list prices. Break-even is labelled as cloud cost alone; platform, FinOps and security time is stated as not modelled.
- **Size limit.** The design limit moved from 48,000 to 49,000 words ([why](AGENTS.md)).

**Not adopted.** Replacing break-even with a yield threshold (nobody has measured a yield); fixing one reference access level for the first estate (it is the adopter's own, and the capability probe covers every level); hour estimates for platform work (nothing could seed them, so the report card measures them).

**Not claimed.** Nothing is built. Cost figures are model outputs, not measurements.

## ideation-v5 and design-v3 — 2026-11-01 (tags `ideation-v5`, `design-v3`)

**Why.** Readers who had never seen the repository (the [stranger test](docs/reviews/stranger-test-v5/disposition.md)) found three kinds of problem in the previous editions (`ideation-v4`, `design-v2`).

1. The documents still carried the vocabulary and the argument of an idea that had been dropped: learning in purpose-built test environments, with an examiner, a laboratory and exam questions. That approach spends money to learn how money is spent. The system learns from what already exists: documentation and price lists, the bills it can read, replays of past usage, owners' answers, and small trials that an owner approves on resources that already run.
2. The commercial reality of Azure was missing. What a system can see, price and buy depends on the agreement (Enterprise Agreement, Microsoft Customer Agreement, sold through a partner, pay-as-you-go) and on the access it has (billing roles, or one subscription).
3. Many sentences answered a conversation nobody could see (denials, defences, hedges), many terms were used before they were defined, and some figures and examples read as measurements of a system that is not built.

**What.**

- **How the AI finds out without building anything.** [`docs/04-finding-out-without-spending.md`](docs/04-finding-out-without-spending.md) replaces the document on experiments in a test environment: six routes (ask, look, replay, follow, pool and, rarely, a small owner-approved trial) ordered by cost, each with what it costs and what it leaves unproven. Every claim carries one of four evidence levels (documented, price-confirmed, bill-observed, outcome-confirmed); without a readable bill a figure is a labelled scenario at list prices.
- **Every agreement, every level of access.** [North star section 5](docs/01-north-star.md#5-every-agreement-every-level-of-access), the capability probe in the estate document, purchases under each agreement in the recommendation document, and a new design document, [agreements and access](docs/design/14-agreements-and-access.md): the cost data path, the price source and the purchase path for each agreement and each level of access, with the facts read on Microsoft Learn.
- **The ideation documents were rewritten** (north star, 02 to 10 and the research): consent before a meeting is captured, every invented example labelled, what may leave an estate stated with its mechanism (a privacy-reviewed scope and aggregate from several organisations, nothing else), the learning contract rebuilt on the evidence levels, the autonomy ladder named once.
- **The cost-trap bank** (145 sourced traps) was re-read against Microsoft Learn: 83 rows are Verified (source-verified: found on the cited page, no bill has confirmed them), 36 Partial and 26 Unverified; wrong rows were corrected (for example stopping an Application Gateway, Backup soft delete, ExpressRoute link limits) and dead links replaced.
- **The design** has fourteen documents instead of thirteen, terms defined where they first appear, the volumes behind the cost figures published (a Pilot still models at about €311 a month, Team €795 and Enterprise €4,760 at list prices), the exact model-retirement call, the purchase paths under a partner agreement, and the safeguards' writers named. The size limit moved from 42,500 to 48,000 words ([why](AGENTS.md)).

**How it was reviewed.** [The stranger test](docs/reviews/stranger-test-v5/disposition.md): 13 cold readers on 11 models, each with only its assigned files, filed 221 findings (38 blockers). Every finding was fixed or answered, and claims about Microsoft products were read on Learn before they were acted on (two reviewer claims did not hold up). ## design-v1 (record) — 2026-11-01 — design phase 1: architecture, decisions, cost model and test strategy

**Why.** With the ideation frozen (tag `ideation-v4`), the design was requested: completely AI-driven; Microsoft Foundry and the Microsoft Agent Framework; every AI part deployed through the Citadel framework in the adopting organisation's landing zone; every safeguard and drift control; security, compliance, test and governance; every technology decision put to two review rounds on different models; and as cost-efficient as possible.

**What.** [`docs/_archive/design-v1/design/`](docs/_archive/design-v1/design/README.md) — an index and fourteen documents (about 157,000 words): requirements and principles · technology landscape · logical architecture · landing zone and Citadel · agents and orchestration · data and knowledge · security architecture · governance and compliance · safeguards and drift controls · test and evaluation · delivery and operations · cost and FinOps · 37 decisions · next phases. Evidence is in [`docs/_archive/design-v1/design/research/`](docs/_archive/design-v1/design/research/) and in a snapshot of 2,468 Azure price meters. Still no code.

<details>
<summary>The detailed record of the withdrawn design (long; kept for the record, not needed to read the current design)</summary>

### The design in six lines
- **A deterministic spine with agentic leaves**: Durable Functions workflows call fourteen hosted-agent roles (fifteen Entra agent identities, eleven contract groups, twelve contracts) one step at a time through the Citadel hub; agents can only read; the Agent Framework runs only inside the leaves.
- **One small execution plane can change an estate**, and *no single credential completes a change that needs a person's web-page approval*: a Policy permit, a person's Entra-signed approval bound to the target and the decision, an Approval service that signs and starts nothing, a broker that verifies and leases, an event-driven runner that verifies again and acts as an identity that exists only for that Move, write-ahead entries in an append-only ledger. What remains is stated in one place and repeated verbatim.
- **Nineteen drift layers** (each with prevent, detect and correct) and **twenty detections**; a preview register in which every preview feature sits behind a switch with a generally available fallback.
- **A statistical test protocol** with signed gate evidence and an exam the system cannot see.
- **A cost model in code** — about €1.2k a month at Pilot, €4.3k at Team and €27k at Enterprise scale (shared hub, list prices) — and a budget that is the spine's atomic reservation of the worst case of every metered part of a call, with the hub's limits as a second layer.
- **34 spikes** that could invalidate a decision, in seven build phases; nothing that changes an estate is switched on before S-ID-1, S-ID-3 and S-ACT-1 pass.

### How it was reviewed
Three passes and a closure check, nine models, every lens on a different model each time. **Round 1** (five lenses: architecture · security, safety and compliance · cost and operability · AI engineering, evaluation and drift · platform fact-check) found 77 issues; **Round 2** reviewed the revision with other models and found 55 (about 45 distinct); a **targeted third pass** by two further models on the parts Round 2 had *redesigned* found 33 more. Those two reviewers then **checked closure** on the fixes (each finding CLOSED with a quote, CLOSED-WITH-RESIDUAL or OPEN) and found that the fixes had reopened 8 findings and introduced 14 new defects, four of them Critical and all in the authority chain; every platform claim was read on Learn before it was acted on; a bounded re-check then found 5 more (one Critical: the lock and the kill switches rested on a measured replica lag that Session consistency does not bound) and a last confirmation found 2, in the observer of the sweeper's removals; the loop stopped there. Raw reports are kept verbatim in [`docs/_archive/design-v1/reviews/`](docs/_archive/design-v1/reviews/design-v1-third-pass/disposition.md) with the orchestrator's own spot-checks and a disposition for every finding.

### What review changed
- **The spine** moved from a custom checkpoint-and-jobs design to Durable Functions on Flex Consumption (Round 1).
- **The execution chain** was reversed twice and hardened a third time: the broker no longer grants *and* dispatches (Round 1); the signer no longer starts the runner, which is event-driven (Round 2, after Learn confirmed that starting a Container Apps job can override its template); the third pass bound the decision into the sign-in nonce, made control items and markers verifiable by signature ("only narrowing is unsigned"), put write-ahead entries before every effect, required the broker to read the approval's own ledger block, and found two things that could not have been deployed — a private endpoint in a delegated subnet and cross-environment calls over internal ingress.
- **The leaf-call rule**: a hosted agent that returns at once is deprovisioned at its idle timeout, so each role's timeout now covers its active time, and completion is a persisted, identity-bound `run-result` record with the event only as a doorbell.
- **The budget**: the hub's token limits are not euros; the spine's reservation now covers tokens, session compute, screening and tools, and the hub refuses any caller-supplied service tier (a request-level priority tier would have been billed at a rate nothing priced).
- **The cost model was rebuilt** and the estimate more than doubled for Team (draft €657 / €1,818 / €17.5k a month for Pilot / Team / Enterprise → €1,244 / €4,278 / €27.0k): it now counts one product per contract and environment, hosted-agent compute including the idle tail, prompt-cache write prices, Content Safety windows, always-ready Flex capacity (which has no free grants), the gate plan and the evaluation work that carries the design's claims (evaluation costs 9.3 / 3.6 / 0.6 times the production cases).
- **The closure check** showed that the fixes had made new holes, so the authority chain changed most late: the approve sign-in starts only from a click (a decline yields no approve token, and the residual that a page can still induce a sign-in is stated); a queue's consumer can put to it, so every sender set is exact and a queue is a doorbell; the deployment lock became a two-sided protocol with fresh reads and a heartbeat; the ledger position is a separate marker because an approval record is never amended; a marker conflict fails closed; the sweeper writes nothing and the Verifier records what it removed; a saving counts only once the Auditor has corroborated it from the cost export; the run registry has its own container, arbitration is first write wins and a crash between the facade's two writes is repaired by the next call; a Move's step checks read the kill switches fresh; every Move class needs a harmless probe; freshness is anchored on the ledger's append time; and, after the re-check, the control state is read at Strong consistency (a documented guarantee instead of a measured lag), a per-run token that only the wrapper holds keeps two runs of one role apart, the wait counter is signed, and a scheduled observer records the sweeper's removals from a stateless 24-hour window.
- **Foundry layout**: two projects per account, not nine; environments and private accounts are created in the phase that needs them.

### Tools and rules
