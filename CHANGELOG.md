## The approve button answered an empty 403: a header of my own made the browser send `Origin: null` — 2026-11-05

**What the owner saw.** He opened the plan page from the letter, was not asked to sign in, pressed **Approve this exact change**, and got the browser's own page "Access to func-meternaut-cases-… was denied. You don't have the user rights to view this page. HTTP ERROR 403". He said that when he presses agree, it fails. The page was not open to everybody: the app serves a page only for a person whom the platform's sign-in has named (its page says "Signed in as Tino. Roles: owner, approver, ops"), and the Hub's front-door check shows that a request with no session is sent to Microsoft Entra. So his page loads were signed in, and the sign-in passed without a prompt, because his browser held a session or signs in by itself; that part is inferred, not measured.

**What was measured** (UTC; the app's request telemetry, Azure Resource Manager and the signed-in browser panel; nothing was approved or changed).
- 18:22:31 and 18:23:14: his two page loads (GET, 200). **No POST of his is in the telemetry at all**, and both disks are still `Unattached`: nothing was recorded and nothing was deleted. The app's code answers every refusal with a page that has text, so an empty 403 did not come from the app: it came from in front of it.
- 18:28:25: a POST with the same fields to a plan id that does not exist (it can change nothing), sent from the signed-in browser panel, gave the same browser page, and again no request in the telemetry.
- 18:29:39: the same POST, with the only difference that the page's referrer policy was set to `same-origin` first, **reached the app**, which answered 404 "I cannot find this request" (telemetry: `POST /ok/zz00000000`, 404, 138 ms).
- No session: a POST with no sign-in is answered by the sign-in's own redirect (302 for a browser's User-Agent, 401 otherwise) whatever `Origin` it carries (the console's address, `null` or none). So the platform refuses the `Origin: null` only for a signed-in person, and no workflow check can see it.

**Cause.** The console sent `Referrer-Policy: no-referrer` from its first build the same day. Under that policy a browser sends `Origin: null` on every form POST (the Fetch standard's "append a request Origin header" does that for a request that is not CORS), and the App Service sign-in answers an authenticated POST with that header with an empty 403 before the app is reached. **Every form POST of the console was refused**: approve, decline, ask, not mine, withdraw, the notes, the settings and the kill switch. The unit tests drive the handler from a Python harness, and the Hub's front-door check sends GETs with no sign-in, so neither could see it. I had only ever opened pages with GET in a browser and wrote that the console worked and that the click was the one thing left; the form POST had never been tried.

**Fixed** (this change): `Referrer-Policy: same-origin`, which sends the console's own origin on a POST and still sends no referrer to another site. A test pins the policy and fails with the old one (checked), and the same test refuses a form or a page that sets a policy of its own. [Rule 28](AGENTS.md) makes the browser check part of every deploy that changes the console, and the [loop proposal](docs/proposals/04-the-loop.md) lists it under "What proves it". A page that was open before the deploy keeps the old header, so it has to be reloaded before a button is pressed.

**Checked after the deploy** (Hub run 42086362549, published 18:42:46 UTC; the same POST to a plan id that does not exist, from the signed-in browser panel, with no change to the page).
- 18:43:58, the first try: the page had been loaded at 18:43:33, and the POST was refused with the empty 403 again (no request in the telemetry). The platform's own warm-up request of a new container (`/robots933456.txt`) is in the telemetry at 18:43:47, so that page came from the old container, with the old header, 14 seconds before the new one took over. This is inferred from the two timestamps, not measured.
- 18:46:37, 18:47:07 and 18:48:19, with pages loaded after the swap (a start page and the plan page twice, 9, 9 and 36 seconds before the POST): all three **reached the app**, which answered 404 "I cannot find this request" (telemetry: `POST /ok/zz00000004`, `…05`, `…06`, 130, 84 and 88 ms). So the delay between loading a page and sending its form does not matter, and the page does not either.
- Both plans are still waiting and both disks are `Unattached`: no button that decides was pressed.

The lesson for the browser check ([rule 28](AGENTS.md)): a page loaded in the first minute after a publish can still come from the old container; the check loads its page again after the warm-up request shows in the telemetry.

**Not checked yet.** The approve button itself (it needs the owner's press, after he reloads the plan page), the delete and the letter after it, and a form sent after the sign-in has expired (the platform answers with a redirect to Entra, which the page's `form-action 'self'` may block in a Chromium browser).

## The console went down after the second deploy: the subnet lost the landing zone's route table and was replaced — 2026-11-05

**What happened** (UTC; each line is read from the Activity Log, the platform's start log or the app's telemetry).

At 15:08:42, 72 seconds later, another principal wrote to it: the landing zone's network manager, which puts its managed route table on a new subnet (the Microsoft Learn page on user-defined route management says that new subnets are updated with eventual consistency, and that manual changes are not tracked).
- 15:39:57 the second deploy of the action `cases` (the one that removed the container and role of the Flex version) wrote the subnet again. The template names no route table, so the write took the table away. `snet-web` has had no route table since, while `snet-pe` and `snet-func` still carry the managed one.
- 15:40:00 the running container's timer started and never ended, and no telemetry came after it; the container kept answering the health address until the platform replaced it at 15:45:50. The new package was started in a new container at 15:41:31 and again at 15:46:14: neither answered the platform's start probe within 230 seconds, and each time the platform stopped the site ("Container did not respond to startup probe"). From about 15:45 UTC the console answered 503.
- The cause was found from the site's own network (read through its deployment site, with no change): a name lookup for the storage account, for the Event Hubs namespace and even for `login.microsoftonline.com` did not answer within 60 seconds, and the resolver of that network is the landing zone's DNS server. A host that has to look up a dozen names while it starts, at 30 seconds a lookup, cannot answer a probe within 230 seconds.

**Not the cause**, each read back: the package (the two packages have the same size), the app's settings (the same as at the first start), the code (none changed) and the roles (the identity still holds *Storage Blob Data Owner* on `azure-webjobs-hosts`, `azure-webjobs-secrets` and `azure-webjobs-eventhub`; the cleanup removed only the role on the old package container).

**Why the checks did not see it.** The deploy said Succeeded. The front-door check passed because the old container was still answering. The first deploy had worked because the subnet was new. The hazard (a template that makes a subnet again takes away what the landing zone added) was known for the baseline template and was not looked for in the cases template, which makes the same subnet. It is now [rule 27](AGENTS.md).

**What it cost.** The console and the runner's timer were down from about 15:41 until the repair below. No plan was touched (the store was not involved) and nothing was waiting for the runner: neither of the two plans, 428DB995 and 91093E96, had been approved.

**What changed** (this change; the repair run has not happened when this is written). (The wait for the route table below became a statement, and the baseline was fixed too: see the entry above.)
- The Basic plan's subnet is now `snet-cases`, the last free /27 of the virtual network (10.53.0.224/27), a range that `snet-web` never held. The template makes it only while it is not there: the workflow reads that from Azure and passes it (`webSubnetExists`), and the app names the subnet by its id. The landing zone's network manager puts its route table on it a minute after it is made, and nothing writes the subnet again.
- The action `cases` takes the app off the integration with `snet-web` first, deploys, waits up to two minutes for the route table on `snet-cases` (when `snet-pe` has one; the run stops with the reason if it does not come), publishes, waits until the app answers on `/healthz` with no credential (up to 25 minutes), signs in again, lists the four functions, and removes `snet-web` when the platform has let go of its link to the plan (it says so, and the next run tries again, when it has not).
- The app gets `WEBSITES_CONTAINER_START_TIME_LIMIT` = 600 seconds, so that a slow start can finish instead of being stopped at 230.
- The baseline template lists `snet-cases` instead of `snet-web`.
- **Open, and said:** `environment/main.bicep` still makes the whole virtual network and would take the route tables from all three subnets. The action `model-side` is not run again until that is changed, which is the next change.

**Not checked yet.** The repair run, the console's answer afterwards, the removal of `snet-web`, and everything that was listed as not checked in the entry below.

**Why.** With the ideation frozen (tag `ideation-v4`), the design was requested: completely AI-driven; Microsoft Foundry and the Microsoft Agent Framework; every AI part deployed through the Citadel framework in the adopting organisation's landing zone; every safeguard and drift control; security, compliance, test and governance; every technology decision put to two review rounds on different models; and as cost-efficient as possible.

<details>
<summary>The detailed record of the withdrawn design (long; kept for the record, not needed to read the current design)</summary>

### The design in six lines
- **A deterministic spine with agentic leaves**: Durable Functions workflows call fourteen hosted-agent roles (fifteen Entra agent identities, eleven contract groups, twelve contracts) one step at a time through the Citadel hub; agents can only read; the Agent Framework runs only inside the leaves.
- **One small execution plane can change an estate**, and *no single credential completes a change that needs a person's web-page approval*: a Policy permit, a person's Entra-signed approval bound to the target and the decision, an Approval service that signs and starts nothing, a broker that verifies and leases, an event-driven runner that verifies again and acts as an identity that exists only for that Move, write-ahead entries in an append-only ledger. What remains is stated in one place and repeated verbatim.
- **Nineteen drift layers** (each with prevent, detect and correct) and **twenty detections**; a preview register in which every preview feature sits behind a switch with a generally available fallback.
- **A statistical test protocol** with signed gate evidence and an exam the system cannot see.
- **A cost model in code** — about €1.2k a month at Pilot, €4.3k at Team and €27k at Enterprise scale (shared hub, list prices) — and a budget that is the spine's atomic reservation of the worst case of every metered part of a call, with the hub's limits as a second layer.
- **34 spikes** that could invalidate a decision, in seven build phases; nothing that changes an estate is switched on before S-ID-1, S-ID-3 and S-ACT-1 pass.

### How it was reviewed
Three passes and a closure check, nine models, every lens on a different model each time. **Round 1** (five lenses: architecture · security, safety and compliance · cost and operability · AI engineering, evaluation and drift · platform fact-check) found 77 issues; **Round 2** reviewed the revision with other models and found 55 (about 45 distinct); a **targeted third pass** by two further models on the parts Round 2 had *redesigned* found 33 more. Those two reviewers then **checked closure** on the fixes (each finding CLOSED with a quote, CLOSED-WITH-RESIDUAL or OPEN) and found that the fixes had reopened 8 findings and introduced 14 new defects, four of them Critical and all in the authority chain; every platform claim was read on Learn before it was acted on; a bounded re-check then found 5 more (one Critical: the lock and the kill switches rested on a measured replica lag that Session consistency does not bound) and a last confirmation found 2, in the observer of the sweeper's removals; the loop stopped there. Raw reports are kept verbatim in [`docs/_archive/design-v1/reviews/`](docs/_archive/design-v1/reviews/design-v1-third-pass/disposition.md) with the orchestrator's own spot-checks and a disposition for every finding.

### What review changed
- **The spine** moved from a custom checkpoint-and-jobs design to Durable Functions on Flex Consumption (Round 1).
- **The execution chain** was reversed twice and hardened a third time: the broker no longer grants *and* dispatches (Round 1); the signer no longer starts the runner, which is event-driven (Round 2, after Learn confirmed that starting a Container Apps job can override its template); the third pass bound the decision into the sign-in nonce, made control items and markers verifiable by signature ("only narrowing is unsigned"), put write-ahead entries before every effect, required the broker to read the approval's own ledger block, and found two things that could not have been deployed — a private endpoint in a delegated subnet and cross-environment calls over internal ingress.
- **The leaf-call rule**: a hosted agent that returns at once is deprovisioned at its idle timeout, so each role's timeout now covers its active time, and completion is a persisted, identity-bound `run-result` record with the event only as a doorbell.
- **The budget**: the hub's token limits are not euros; the spine's reservation now covers tokens, session compute, screening and tools, and the hub refuses any caller-supplied service tier (a request-level priority tier would have been billed at a rate nothing priced).
- **The cost model was rebuilt** and the estimate more than doubled for Team (draft €657 / €1,818 / €17.5k a month for Pilot / Team / Enterprise → €1,244 / €4,278 / €27.0k): it now counts one product per contract and environment, hosted-agent compute including the idle tail, prompt-cache write prices, Content Safety windows, always-ready Flex capacity (which has no free grants), the gate plan and the evaluation work that carries the design's claims (evaluation costs 9.3 / 3.6 / 0.6 times the production cases).
- **The closure check** showed that the fixes had made new holes, so the authority chain changed most late: the approve sign-in starts only from a click (a decline yields no approve token, and the residual that a page can still induce a sign-in is stated); a queue's consumer can put to it, so every sender set is exact and a queue is a doorbell; the deployment lock became a two-sided protocol with fresh reads and a heartbeat; the ledger position is a separate marker because an approval record is never amended; a marker conflict fails closed; the sweeper writes nothing and the Verifier records what it removed; a saving counts only once the Auditor has corroborated it from the cost export; the run registry has its own container, arbitration is first write wins and a crash between the facade's two writes is repaired by the next call; a Move's step checks read the kill switches fresh; every Move class needs a harmless probe; freshness is anchored on the ledger's append time; and, after the re-check, the control state is read at Strong consistency (a documented guarantee instead of a measured lag), a per-run token that only the wrapper holds keeps two runs of one role apart, the wait counter is signed, and a scheduled observer records the sweeper's removals from a stateless 24-hour window.
- **Foundry layout**: two projects per account, not nine; environments and private accounts are created in the phase that needs them.
