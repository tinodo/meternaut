# Rules for agents working in this repository

Short, durable and binding for every session and every sub-agent. Each rule comes from the project owner; the date is when it was given. Pass them on to any sub-agent you start.

1. **The repository stays PRIVATE until the project owner says to switch it** (2026-10-31: "Keep the repo private until I say to switch it."). Never change its visibility, and never publish any of its content elsewhere — no public fork, GitHub Pages site, release, gist, package, or text posted to another repository. Anything that says "publish" waits for that word. Going public is a one-way door and is the project owner's click.
2. **Ideation first; assume, don't ask** (2026-10-31: "Dont frustrate the ideation processes with questions that have no purpose here"). Take the sensible option and say so; do not stop to ask the project owner questions that have no purpose in ideation. **In the ideation documents (docs 01–10) do not create decision registers, assumption lists, risk registers, kill criteria or gates** — the project owner rejected them as bloat and as technical worry that does not belong in ideation. The questions that matter are *design* questions about the idea itself. (The design phase, rule 11, is different: there decisions, security, governance and tests are wanted.) **Assuming is for your own working; it never goes into a document as a fact about the project owner or his environment.**
3. **Licence: MIT** (2026-10-31) — [`LICENSE`](LICENSE).
4. **Keep history.** Never edit `docs/_archive/` (the frozen earlier versions), and keep the raw reports in `docs/reviews/` verbatim apart from their headers and the appended spot-checks. A substantive change is a new version — a git tag and a [CHANGELOG](CHANGELOG.md) entry — never an overwrite.
5. **Before every commit** run `python tools/check-docs.py --strict` (standard library only; install nothing). It checks links, anchors, diagrams and orphans, and enforces rules 2, 6, 7 and 10, the vocabulary of rule 11 (c) and (j) in every document, rule 12's word (an agreement, never a "contract") in the ideation documents — and, for the design documents, rule 11 (a)–(d) and (g): vocabulary guards plus the size budget; for the experience documents the same guards with their own budget (rule 13 (e)) and the Adaptive Card checks of `tools/cardlint.py` (rule 13 (d)) — with pattern guards (a guard is a safety net, not a substitute for judgement; rule 8 and rule 11 (e), (f), (h), (i) are not mechanically enforced).
6. **This is a learning system — not a rulebook, and not a product built around two examples** (2026-10-31: "Do NOT live from stuff that I fed; build an app that learns how to do the cost optimization, resulting in the findings and tips I provided."). The design must serve *study · survey · test · act · grow*: how the AI learns about new Azure services, gathers knowledge, investigates cost implications, tests its beliefs against evidence, and recommends. The project owner's two original findings may appear **only** as ordinary rows in [`docs/research/cost-trap-bank.md`](docs/research/cost-trap-bank.md) — never as the foundation, a "seed", a founding test or a release plan, and **never in the design documents**. The lint enforces this.
7. **Pictures show loops, hubs, parallel work and state changes** — never a single linear pipeline (2026-10-31: the project owner rejected "a linear process"). Prefer state diagrams with back-edges, hub-and-spoke maps and feedback loops.
8. **Ideation ≠ technology or feasibility.** In the ideation documents (01–10), do not let feasibility, governance or platform detail shape the north star; guardrails and technology are chosen in the design phase (rule 11). Constraints that do apply throughout: Microsoft technology for the product (open standards and repository tooling are the exceptions); Cloud Adoption Framework and Well-Architected alignment; open source (MIT); fully AI-infused; human-in-the-loop.
9. **Replies:** concise, with full absolute file paths; deliverables are never overwritten — a substantive change is a new version.
10. **One wording for purchases** (the brief: "click OK and the machine will be resized. Or purchasing reserved instances"; the wording below is the design's answer, agreed in review). A commitment purchase is **prepared by the AI, approved by two named humans with different hats, and then executed by the AI** on their say-so — never on its own judgement (since 2026-11-05 with the approving human's own sign-in and rights, never with a right of its own: rule 29). Nothing irreversible runs without a human's OK or a rule a human wrote. The lint guards against the older "executed by humans" wording.
11. **The design phase** (2026-10-31: "I want you to start designing … use Foundry and potentially Microsoft Agent Framework … the latest and greatest new features in the Microsoft AI ecosystem … the AI parts should all be deployed using the CITADEL framework in my landing zone … all possible latest and greatest safeguards and drift controls … security and compliance and test and governance … rubber duck all decisions on technology … twice with different models … as cost efficient as possible"). The ideation (tag `ideation-v5`) stays the north star; the design lives in [`docs/design/`](docs/design/README.md) and may name technologies and contain security, governance, test and decision content. The first design was withdrawn on 2026-11-01 (the project owner: "Do not just fix what I said … try again"); [why](docs/_archive/design-v1/README.md). These rules are what it taught:
    - **(a) Write for the community.** The documents will be public. No "the operator", no personal context, and no statement about the project owner's landing zone, tenant, location, licences or preferences. Say "the adopting organisation". Where the brief says "my landing zone", the design says: *the solution onboards to the Citadel governance hub of the adopting organisation's Azure landing zone*.
    - **(b) Never harden a hedge, never invent.** "I don't think you will use X" is not "no X": decide on merit and give the reason. Do not invent constraints, assumptions, licence positions or sources. A design has no "Assumptions" section and no "constraints" table with a "source" column; sizing numbers are labelled *scenario parameters*.
    - **(c) Learning costs no Azure resources** (2026-11-01: "Drop the lab … you are going to spend money to see how much is spent … find an alternative"). The system never deploys resources in order to learn: it learns from documentation, price lists, schemas, the bills it reads, replays of history, owners' answers and small reversible trials that an owner approves. The documents state this as a property of the system, never as a contrast with something rejected. The words *lab*, *Terrarium*, *wind tunnel*, *time machine*, *exam* and *learner* do not appear in any live document; the lint enforces it.
    - **(d) Proportion and plain words.** A design is short enough to be read. The lint enforces a size budget (README ≤ 1,800 words, every other document ≤ 6,000, the whole design ≤ 52,500) and no wall of text (no paragraph over 1,100 characters, no table row over 800). The total was 42,500 until design-v3 added the agreements-and-access document (about 2,800 words), the edits that connect it to the other documents, and what the stranger test required (terms defined where they first appear, the seeded volumes behind the cost figures, the purchase paths a partner agreement allows, the exact model-retirement call); it was 47,500 before the closure checks of that test found contradictions that each needed a sentence, 48,000 until design-v4 added what an independent validation confirmed (the phase 1a slice, the rules for trials, undetermined outcomes, Detector promotion and a new estate, and the dead-end investigations in the cost model), and 49,000 until design-v5 added what the experience design needs of the system (the approval record's rules, the channels' delivery contract, preferences and report data, the owner's pause, the kill-switch page, first contact and approver readiness, and the tests of what people receive). Raise it again only with a reason in the changelog. Generated appendices live in `docs/design/cost/`, outside the budget. Define each term once, in the README's glossary; do not coin jargon (no "spine", "leaf", "authority chain"). Pictures follow rule 7.
    - **(e) Decisions are rubber-ducked twice, by different model families.** Each technology decision records the alternatives, cost, security impact and reversibility. Every statement about a Microsoft product is verified on the vendor's page **today** (preview or generally available, regions, price) — nothing from memory.
    - **(f) Cost is a design constraint.** Every component has an idle cost and a scale-to-zero story, and a line in the cost model; numbers in the cost document come from `tools/cost-model.py` (`--update-doc`, then `--check`), never typed by hand.
    - **(g) Review history stays out of the design.** Round numbers, finding ids and dispositions live in [`docs/reviews/`](docs/reviews/README.md); the design says what the system is, not how it was argued.
    - **(h) Feedback names symptoms.** When the project owner lists defects, audit the whole work for the same class of mistake and fix the cause; patching only the named items repeats the failure.
    - **(i) Be honest about what is unproven.** Say what a safeguard does *not* stop. A preview feature is used only behind a switch with a generally available fallback, and the document says which is which.
    - **(j) No conversation in the documents** (2026-11-01: "You think an independent reader, or later, when this is open sourced, has any clue what that text exists?"). A document answers a stranger's question, never the project owner's remark. Do not write a sentence that exists because of something said in the conversation — "not ruled out", "judged on merit", "without a lab", "unlike the earlier draft", "as asked". A sentence that only makes sense to someone who saw the conversation is deleted. History belongs in the changelog and in `docs/reviews/`. The lint guards the known phrases.
    - **(k) The stranger test.** Before a release, give every live document, cold, to reviewers who have not seen the repository. For each sentence they ask why it exists, and flag what reads as internal reasoning, a hedge, or jargon nobody defined. Fix the findings in the same release.

12. **Agreements and access are part of every question about cost** (2026-11-01: "Can the solution adapt to all of that?" — enterprise, customer-agreement, partner, pay-as-you-go and managed-environment customers, some with billing access and some with subscription access only). What an organisation can see about its bill, which prices apply, and who may buy a commitment all depend on the agreement and on the access the system was given. Every feature that reads cost, prices an option or buys something says what it does at each level of access; facts come from the vendor's pages ([design 14](docs/design/14-agreements-and-access.md), [north star §5](docs/01-north-star.md)). Never assume one agreement type or full billing access.

13. **The experience design** (2026-11-02: "start design phase 2"). What each person sees, receives and decides lives in [`docs/experience/`](docs/experience/README.md), on top of the design and the idea. What it taught so far:
    - **(a)** Rule 11 (a)–(k) binds these documents too: write for the community, never harden a hedge, no conversation residue, a stranger test before a release.
    - **(b) People never see internal names.** The screen words (Recommendation, Note, your OK, standing permission, change, history, the three pauses) are defined once, in the folder's README; the design's words (Lesson, Credential, Approval, Runner, Detective, Atlas and the rest) stay in running text about the system and never in quoted screen text.
    - **(c) Examples are invented and labelled** ("An invented example."), and never built on the two findings of rule 6. Every saving shown to a person carries its price basis and one of Scenario, Expected or Verified.
    - **(d) Messages are honest by construction.** A sender name ending "(AI)", an AI line and footer, why the person got the message, "Talk to a person" as the last button of every card, Explain (and Challenge and Teach where there is a claim or a decision about spend), an action that takes no input says so, one link only on a card (the page of its request), no urgency, guilt or countdown, no dash between figures, plain words. `tools/cardlint.py` (run by `check-docs.py`) enforces what a machine can on the card templates in `docs/experience/cards/`; it is a floor, not the standard.
    - **(e) Size.** The folder's README at most 1,800 words, every document at most 6,000, the folder at most 38,500; no paragraph over 1,100 characters, no table row over 800. Raise a budget only with a reason in the changelog.
    - **(f) Channel facts are verified the day they are written** (Teams, Outlook, Graph, Workbooks, Voice Live, GitHub): the platform register says preview or generally available and names the fallback; a feature that cannot be verified is not claimed.

14. **The build plan** (2026-11-02: "Building a PLAN... But just the PLAN"; "No... wait for the other things"). The plan for phase 0 and phase 1a lives in [`docs/build-plan/`](docs/build-plan/README.md), on top of the design and the experience design. It is a plan only:
    - **(a) A plan builds nothing.** No resource, pipeline or code is created because of this folder. The plan says what would be built, in what order, what is shown to whom, how each step is checked and what the adopting organisation must provide. Building follows only for what the project owner has authorised (rule 15).
    - **(b) Rules 11 (a)–(k) and 12 bind it:** write for the community, never harden a hedge, no conversation residue and no review history, never assert what an adopting organisation owns, licenses or has (name who can grant each request and mark a choice with no safe default as required), and say what each step does at each level of access.
    - **(c) Numbers.** Sizes are person-weeks and scenario parameters. Every number behind a pass condition, a margin, a budget or a time window is a starting value, written down in the repository before the measurement. The plan never types a euro figure of its own: it points at the cost document. The lint enforces the euro rule.
    - **(d) Words.** The design's words, no new terms, no jargon a stranger would not know ("the thin path end to end", not "walking skeleton").
    - **(e) Size.** The folder's README at most 1,200 words, every other document at most 3,900, the folder at most 15,200; no paragraph over 1,100 characters, no table row over 800. Raise a budget only with a reason in the changelog.
    - **(f) Facts about Microsoft products are verified the day they are written.**
    - **(g) Revision.** The plan is re-issued as a new version at each phase exit, with the measured sizes and the results of the checks; an earlier version is never overwritten.

15. **Building** (2026-11-02, the project owner: "Start building to answer the remaining uncertainties — not to mechanically implement every page"; authorised: the repository foundations, the minimal agent, hub and model path, spend and stop controls, pilot-data feasibility and the small learning demonstration, "with named owners, a spending cap and a review date"). Only that is built; the plan says what comes next.
    - **(a) Answer an uncertainty, not a page.** Build what settles a question that the plan names (a check or a review), in the plan's order. Nothing from a later slice is built early.
    - **(b) Nothing touches Azure without the owner's word, given in plain words in the conversation, and nothing changes in Azure except through a workflow (rule 18).** The owner names the subscription. It is read only as far as a check needs, read-only and with the owner's own access; its id is never committed (a record that names it goes in `local/`, rule 17), and the Azure CLI's default subscription is never taken as the pilot's scope. In a subscription that the owner does not own, only resource groups created for this project are created or changed (2026-11-02, the owner: the subscription is not his, so only the project's own resource groups are touched). In a landing-zone subscription the same holds (2026-11-02, the owner: "You can deploy citadel … there since you need it"), and the landing zone's policies are never bypassed: no exemption, and no tag or parameter that turns a control off. Nothing outside the project's own resource groups is changed unless the owner has approved that object in plain words first: the owner's own API Management instance, for example, is not touched at all since 2026-11-07 (rule 15 (c)), and no private DNS zone, link or zone group is ever created (rule 19). Before anything that bills is deployed, the agent says what it is, what it costs a month and where it stops. A review comes from an event (the work is finished, the budget's warning alert fires, a check fails), never from a calendar date. Code is written and tested without Azure first.
    - **(c) Every model call of Meternaut goes through the AI Gateway, the governance hub of the Citadel design, with no direct path, not even for a test, unless the owner makes a written exception** (2026-11-07, the owner, in capitals: "IT NEEDS TO ADHERE TO THE CITADEL DESIGN PRINCIPLES"). The AI Gateway is Azure's separate service ([the decision record](docs/proposals/08-ai-gateway.md), which also says how it meets the Citadel principles and what is still missing); it has been deployed since 2026-11-07, because the owner asked for it in writing ("Create the AI Gateway with public network access and private routing."). The Detective and the Skeptic call it with the cases app's own identity and a Microsoft Entra token for its audience, and no key, and the app's list of allowed calls holds no chat completion to the Foundry resource or to its project. *History:* through API Management until the owner ordered its removal on 2026-11-07, then direct to the Foundry project for a few hours the same day, now through the AI Gateway. **The agents' route through the gateway is on in code and ran once in Azure** (2026-11-07, the owner: "Route [the agents] to the AI gateway ... IT NEEDS TO ADHERE TO THE CITADEL DESIGN PRINCIPLES"): the two agents of the investigation (rule 30) go through the gateway by step 2, the connection of the Foundry project to the gateway, which one line switches on (`AGENTS_VIA_AI_GATEWAY` in `tools/environment-params.py`, True). The order of the real run is `aigateway`, about ten minutes, `foundry`, `cases`, `cases-run`; it was made on 2026-11-08, and the Investigator was refused at its first call, because its model does not take function tools together with a reasoning effort. Its definition now asks for the effort `none`, and that fix has not been run, so no investigation has completed through the gateway yet ([the decision record](docs/proposals/08-ai-gateway.md#what-the-first-real-run-showed)). The way back is the line set to False and a run of `foundry` and `cases`; it is a direct route, so it needs the owner's written exception. **Nothing of Meternaut touches the owner's API Management instance any more, and nothing public is made without the owner's written request** (2026-11-07, the owner's rule: "NO PUBLIC ENDPOINTS UNLESS SPECIFICALLY REQUESTED"; the AI Gateway's front door is public and cannot be made private): the Hub actions that made objects on the instance are gone, and the action `aigateway`, the only one that deploys the AI Gateway, stops at its first step unless the workflow input `public_ai_gateway_requested` is set, which is done only when the owner has asked in writing for a public AI Gateway, so a new deployment of it needs his written request again ([the decision record](docs/proposals/08-ai-gateway.md)). The owner's own, existing AI Gateway in another subscription is not touched (it is only read, as before). A request that carries no prompt, or that the model service refuses before it runs a model, is not a model call (the agent's clarification: check C1 asks for a direct call that fails, and it is made that way, with an empty or malformed request; the owner may strike this sentence). Cases and fixtures are synthetic, and a record that names an estate is never committed: it goes in `local/` or outside the repository.
    - **(d) The standard library first.** A dependency needs a reason, comes from an approved package feed and is pinned. A workflow pins each action to a commit and runs with read-only permissions.
    - **(e) Every tool is tested without a network or a subscription,** and the tests run in CI. A tool refuses what it must not do (a month that has not closed, a record where git would track it, a run with no spending cap) instead of warning.

What would cost about 50 EUR a month or more, or cannot be undone in minutes, is the owner's decision, put to him in plain words with its cost, the way back and a recommendation. A hub that costs money while it stands is described to the owner before it is built, and when the learning demonstration is finished the agent asks him in plain words whether to delete it.

16. **Plain words, in the conversation, never a file to read** (2026-11-02: "I am not going to read a json file."). A decision that only the owner can take goes to him in the conversation, in plain words, with its cost, the way back and a recommendation: never as a file, a table of parameters, a configuration or a pull request to open. The agent decides what is small and says so. A control is an event (spend reached, work finished, a check failed), never a calendar date (2026-11-02: "Dates have no meaning for AI"). Limits that the agent needs are written in this file, not in a file that the owner would have to confirm. This holds for every reply, not only for decisions (2026-11-03: "I am not going to read any MD file again"): a reply says in the conversation what a document says, and a path is only where the record is kept. Never end a reply with "read this".

17. **Working files live in `local/`, never in the Copilot session folder** (2026-11-02: "Use a dedicated folder in the repo folder."). `local/` is in the repository folder and git ignores it (`.gitignore`; a test checks it). It holds what stays on one machine: `local/records/` the records that name an estate, `local/working-files/` briefs, specs, scripts and notes that are not part of the product. Nothing of the project is kept in an agent's session folder, in the system's temp folder or anywhere else outside the repository folder. Scratch that can be made again (browser profiles, `node_modules`, renders) is deleted when its work is done, because the owner's disk is small, and tests and tools clean up after themselves.

18. **Every change to Azure goes through a GitHub Actions workflow** (2026-11-03, the owner: all of it goes through workflows and actions; [design 09](docs/design/09-delivery-and-operations.md#3-pipelines-and-releases) says the same). An agent never deploys, creates, updates, deletes, purges or assigns a role in Azure from a machine: not to build, not to clean up, not to test. It may read Azure (show, list, query, what-if) to understand it. A change is a commit. A workflow run signs in with OpenID Connect (no secret), shows its what-if, deploys only when the owner has approved that run (an environment reviewer where the GitHub plan offers one; on the Free plan, which has none, the owner's plain words in the conversation, after which the agent starts the run: a `what-if` needs none, `deploy`, `pause` and `remove` each need his words. The workflow's guard cannot tell the owner's click from a run that an agent starts with his token, so on the Free plan this is a rule of process and not a technical barrier. 2026-11-03, the owner: he merges and clicks nothing himself, the agent runs it all), checks the result, and its page is the record. The deployment identities (a managed identity with a federated credential bound to this repository) must exist before the first run: the owner approves them in plain words first, with what each may change, and that bootstrap is the only step taken outside a workflow. Anything else outside a workflow is break-glass: only on the owner's written word, and reported at once.

19. **Study the environment before building in it, and reuse what is there** (2026-11-03, the owner: work out how the landing zone works first; "I already have an APIM instance and DO NOT WANT another"). Before a design or a template touches a landing zone, read and write down what it already provides: the shared services (API Management, Foundry, Log Analytics, DNS servers), the policies that apply, what the network manager does to a new virtual network, and where a private endpoint's DNS record comes from. Reuse what exists and never create a second one. In a landing zone never create a private DNS zone, a link to one or a private endpoint's DNS zone group: central zones and a policy register the record, and a new virtual network takes the landing zone's DNS server. Check the soft-deleted names before choosing a name: a key vault with purge protection keeps its name for 90 days. **Read the exemptions as well as the policies** (2026-11-04, found after the fact: the first environment was priced and built as if public access to new services were denied, in a subscription where the owner had waived that policy for the whole subscription; the private endpoints were a choice and were presented as a requirement). List the policy exemptions at every scope that applies, and look at what the policy engine says about a real resource (`Exempt`, `Compliant` or `NonCompliant`), before writing that a policy forces anything. **A policy that changes a resource does not refuse it** (2026-11-04, found after the fact: a storage account and a Cosmos DB account came out of a deploy with Shared Key, local authentication and public access switched off, from a template that said the opposite, and the deploy said Succeeded until a dependent resource was refused). Tenant policies with the effect Modify rewrite a resource while it is made, so after a deploy compare the live properties with the template; read the initiative's list of Modify and DeployIfNotExists policies for the resource types a template makes before it is written; and read each policy's own rule for its opt-out. Using an opt-out (a tag, an exemption) is a deviation from a security control: it is said in the template, the changelog and the proposal, it covers the smallest set of resources, and it is never hidden. **And a design never rests on one** (2026-11-04, the owner: "the tag only works for a limited time"): an opt-out that a policy honours for a limited time, or that anybody can remove, is a time bomb. Build for the state that the policy enforces (rule 23).

22. **Price the cheapest sufficient way, not the default build** (2026-11-04, the owner, about that call-recording part: "You are all about cost... This just sounds WAY too expensive. You need to do better."). When an answer or a plan prices a capability, it first asks whether the capability is needed at all and what the platform already gives for nothing: the gateway's own logs and metrics, free tiers, serverless plans, a network security perimeter instead of a private endpoint. The cheapest sufficient way is named next to the default build, each with a real price (from the Retail Prices API, not from memory) and with what it gives up. A component's default price is never presented as the price of the capability, and what something costs or does is checked against the real environment or the vendor's own documents before it is said. When the owner has named a price and ordered the build anyway (2026-11-04, "build the whole thing, with the 265 storage"), his order stands, and the settings of each part that do not change what he sees still take the cheapest sufficient value (serverless instead of 2,800 provisioned request units); the real price is said before the run, and where the number he named was wrong it is corrected at once.

23. **No keys, ever** (2026-11-04, the owner, after the usage recording had been built with a Logic App that needed a storage account key and a Cosmos DB connection string, held up by a time-limited policy opt-out tag: "THE LOGIC APP MUST GO IF IT DEPENDS ON KEYS ... NO KEYS! NEVER! EVER! ONLY WORKLOAD FEDERATED IDENTITIES, MANAGED IDENTITIES ... CAF AND WAF"). Nothing in this project authenticates with a key, a connection string, a shared access signature, an account key or a password: every caller, in Azure and in GitHub, uses an identity (a managed identity, or a workload identity federated with OpenID Connect). Every service that has a switch for keys has it off in the template (storage `allowSharedKeyAccess: false`; Cosmos DB, Event Hubs, Application Insights and Log Analytics `disableLocalAuth: true`), the Azure Policy `Modify` policies of the tenant then have nothing to change, and a service or an engine that cannot run without a key is not used (the Logic App Standard, whose content share is mounted with the account key, is the one that was built and removed: its work is done by an Azure Functions app on the Flex Consumption plan with its own system-assigned identity). Where a platform leaves no other way, that is said in the template, the changelog and the final report, with the way out, and the owner decides: today that is the connection string in the metadata of the Foundry project's tracing connection (2026-11-06: Microsoft's own templates write it, and the component's local authentication is off, so the string names the component and authenticates nothing). **No other exception is left (2026-11-07):** the contract's key, which the cases app and one test of the Hub read, and the instrumentation key of the Application Insights logger that Meternaut had added to the owner's API Management instance went with those objects when the owner ordered the undo (rule 15 (c)). The cases app reads no key, no custom role of the access file reads one (the key reader is retired), no Hub action reads one, and the model calls go through the AI Gateway with its own identity, a Microsoft Entra token and no key (rule 15 (c)). A test fails a template or the workflow that reads or writes a key, and holds the list of known exceptions empty. A design never depends on a policy opt-out that can expire (rule 19). The Cloud Adoption Framework and the Well-Architected Framework (Security: identity is the perimeter) are the reference; a recommendation that needs a key is wrong, whatever its price.

26. **The loop: the console, the approval and the change made by the approver** (2026-11-05, the owner, after the History workbook failed on his network: "I gave you the GO to develop and deploy the ENTIRE Meternaut solution. 27. **A template makes a subnet once, and never undoes what the landing zone added to it** (2026-11-05, found after the fact: the second deploy of the first cases made the integration subnet again; the landing zone's network manager had put its route table on that subnet a minute after the first make, the second make had none and took it away, and the app on the subnet lost its way to the landing zone's DNS and could not start; the console was down for about an hour). A landing zone changes what a template made: a network manager puts route tables on subnets, and the tenant's `Modify` policies rewrite settings (rule 19). A template that makes the whole resource again takes such a change away, and a deploy that says Succeeded does not say so. So a template makes a subnet only while it is not there (the workflow reads that from Azure and passes it, as `webSubnetExists` does) and names it by its id afterwards; a deploy is followed by a check that the app answers (a wait that holds no credential) and by a statement of what the landing zone has added (the route table of the subnet may come minutes after the subnet is made, so it is said and not required). Both templates that make a network resource follow this: the baseline makes the virtual network, and the cases template the Basic plan's subnet, only while they are not there.

28. **Test what a person does, in a browser, through the platform's sign-in** (2026-11-05, found by the owner, not by a check: the approve button answered an empty 403, "when I press agree, it fails"). The unit tests drive the handler from a Python harness and the Hub's front-door check sends GETs with no sign-in, so neither can see what a real browser sends or what the platform's sign-in does with it. Under `Referrer-Policy: no-referrer` a browser sends `Origin: null` on a form POST, and the App Service sign-in answers an authenticated POST that carries it with an empty 403 before the app is reached (no request in the telemetry); an unauthenticated POST gets the sign-in's redirect whatever `Origin` it carries, so no workflow check can see this. The policy is `same-origin` now and a test pins it, with the rule that no form or page sets a policy of its own. **After every deploy that changes the console, the agent runs the browser check** in the signed-in browser panel: it opens a page, posts a form with the same fields to a plan id that does not exist (that can change nothing), and requires the console's own "I cannot find this request" page and a POST row in the telemetry (`requests`, `name == 'console'`), and not an empty 403. It never presses a button that decides, and it says in the report that this is all that was checked of the approval until the owner has pressed it. A page that was open before the deploy keeps the old headers, and so does a page loaded in the first minute after a publish (the platform's own warm-up request, `/robots933456.txt`, shows in the telemetry when the new container takes over): the check loads its page again after that, and the owner reloads his before he presses a button.

29. **Meternaut holds no right to change Azure: a change runs as the person who approves it** (2026-11-05, the owner, after the first real approvals, when the Activity Log showed that the runner's identity had deleted the two disks: "Once a user OK's a delete, the managed identity of Meternaut executes the action ... NOT A SINGLE CUSTOMER WILL DO THAT ... You should execute the action on-behalf-of ... IS THIS ACCORDING TO WAF AND CAF AS REQUIRED?"). The runner held one narrow custom role in the project's own group, and that is still a standing right to write that a tool holds for ever and that no customer will give it for their estate: the Well-Architected Framework (Security, SE:05, conditional access: just in time, just enough, limited in time and in privilege) and the Microsoft cloud security benchmark (PA-2, avoid standing access) say the same. So no identity of Meternaut, in the project's group or anywhere, holds a role that writes in Azure: the app's identities read (rule 24: every subscription that the cases app's identity can read, and nothing more than reads), keep the app's own records, send letters through Microsoft Graph (rule 25), create and run the agents in the app's own Foundry project (rule 30: a data-plane right inside Meternaut's own group, over Meternaut's own agents and conversations, that changes nothing in any estate) and call the models through the AI Gateway (rule 15 (c): the role AI Gateway Models User on the gateway, inside Meternaut's own group, which lets an identity list and invoke the gateway's models and nothing else). When a person approves a plan, the console sends that person to Microsoft Entra to sign in to Azure Resource Manager (authorization code flow with PKCE, the delegated scope `https://management.azure.com/user_impersonation`, no refresh token; the app registration redeems the code with the federated credential of a managed identity and holds no secret, rule 23) and makes the one approved change in that request with that person's own access token. The token lives in memory for that request and is never stored, logged or shown. Azure decides what the person may do, refuses the change when the person's rights do not allow it, and records the person as the caller in its Activity Log. When Azure answers the delete with 401 and a claims challenge (the person's token lacks a check that a policy asks for, such as multifactor), nothing was deleted: the action goes back to the queue, the plan stays approved, and the console sends the person to Entra once more, in a state of its own, with that claims request; the return makes the delete once more with every check made again. A second challenge, a cancel, an Entra error or a check that is not completed within ten minutes of the recorded approval close the plan as failed, and Meternaut asks for the check once. The challenge header is read by the runner alone, strictly (what is not a well-formed `insufficient_claims` challenge is an ordinary refusal), and it is on no log, event, page or stored record. The timer never changes anything: it expires plans, checks what was done and sends letters. **Reading more does not widen what may be changed:** however many subscriptions the Watch reads, a change is planned and made only in the one resource group of `CHANGE_RESOURCE_GROUP` in `CHANGE_SUBSCRIPTION_ID`, where Meternaut planted waste of its own, and with the approver's token. The design and its limits are in [run as the approver](docs/proposals/05-run-as-the-approver.md). Tests pin that only the sign-in's code starts a change (`runner.execute` is imported by `delegated.py` alone), that the loop's list of calls holds reads only, that no setting names a writer, and that the whole loop deletes with the approver's token and with no other.
