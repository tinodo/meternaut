# Rules for agents working in this repository

Short, durable and binding for every session and every sub-agent. Each rule comes from the project owner; the date is when it was given. Pass them on to any sub-agent you start.

1. **The repository stays PRIVATE until the project owner says to switch it** (2026-10-31: "Keep the repo private until I say to switch it."). Never change its visibility, and never publish any of its content elsewhere — no public fork, GitHub Pages site, release, gist, package, or text posted to another repository. Anything that says "publish" waits for that word. Going public is a one-way door and is the project owner's click.
2. **Ideation first; assume, don't ask** (2026-10-31: "Dont frustrate the ideation processes with questions that have no purpose here"). Take the sensible option and say so; do not stop to ask the project owner questions that have no purpose in ideation. **In the ideation documents (docs 01–12) do not create decision registers, assumption lists, risk registers, kill criteria or gates** — the project owner rejected them as bloat and as technical worry that does not belong in ideation. The questions that matter are *design* questions about the idea itself. (The design phase, rule 11, is different: there decisions, security, governance and tests are wanted.) **Assuming is for your own working; it never goes into a document as a fact about the project owner or his environment.**
3. **Licence: MIT** (2026-10-31) — [`LICENSE`](LICENSE).
4. **Keep history.** Never edit `docs/_archive/` (the frozen earlier versions), and keep the raw reports in `docs/reviews/` verbatim apart from their headers and the appended spot-checks. A substantive change is a new version — a git tag and a [CHANGELOG](CHANGELOG.md) entry — never an overwrite.
5. **Before every commit** run `python tools/check-docs.py --strict` (standard library only; install nothing). It checks links, anchors, diagrams and orphans, and enforces rules 2, 6, 7 and 10 — and, for the design documents, rule 11 (a)–(d) and (g): vocabulary guards plus the size budget — with pattern guards (a guard is a safety net, not a substitute for judgement; rule 8 and rule 11 (e), (f), (h), (i) are not mechanically enforced).
6. **This is a learning system — not a rulebook, and not a product built around two examples** (2026-10-31: "Do NOT live from stuff that I fed; build an app that learns how to do the cost optimization, resulting in the findings and tips I provided."). The design must serve *study · survey · test · act · grow*: how the AI learns about new Azure services, gathers knowledge, investigates cost implications, experiments, and recommends. The project owner's two original findings may appear **only** as exam questions — in [`docs/07-getting-smarter.md`](docs/07-getting-smarter.md) (the founding exam) and in [`docs/research/exam-bank-cost-traps.md`](docs/research/exam-bank-cost-traps.md) — never as the foundation, a "seed", or a release plan, and **never in the design documents**. The lint enforces this.
7. **Pictures show loops, hubs, parallel work and state changes** — never a single linear pipeline (2026-10-31: the project owner rejected "a linear process"). Prefer state diagrams with back-edges, hub-and-spoke maps and feedback loops.
8. **Ideation ≠ technology or feasibility.** In the ideation documents (01–12), do not let feasibility, governance or platform detail shape the north star; guardrails come later ([`docs/09-guardrails-later.md`](docs/09-guardrails-later.md)) and the technology is chosen in the design phase (rule 11). Constraints that do apply throughout: Microsoft technology only; Cloud Adoption Framework and Well-Architected alignment; open source (MIT); fully AI-infused; human-in-the-loop; not a chatbot.
9. **Replies:** concise, with full absolute file paths; deliverables are never overwritten — a substantive change is a new version.
10. **One wording for purchases** (the brief: "click OK and the machine will be resized. Or purchasing reserved instances"; the wording below is the design's answer, agreed in review). A commitment purchase is **prepared by the AI, approved by two named humans with different hats, and then executed by the AI** on their say-so — never on its own judgement. Nothing irreversible runs without a human's OK or a rule a human wrote. The lint guards against the older "executed by humans" wording.
11. **The design phase** (2026-10-31: "I want you to start designing … use Foundry and potentially Microsoft Agent Framework … the latest and greatest new features in the Microsoft AI ecosystem … the AI parts should all be deployed using the CITADEL framework in my landing zone … all possible latest and greatest safeguards and drift controls … security and compliance and test and governance … rubber duck all decisions on technology … twice with different models … as cost efficient as possible"). The ideation (tag `ideation-v4`) stays the north star; the design lives in [`docs/design/`](docs/design/README.md) and may name technologies and contain security, governance, test and decision content. The first design was withdrawn on 2026-11-01 (the project owner: "Do not just fix what I said … try again"); [why](docs/_archive/design-v1/README.md). These rules are what it taught:
    - **(a) Write for the community.** The documents will be public. No "the operator", no personal context, and no statement about the project owner's landing zone, tenant, location, licences or preferences. Say "the adopting organisation". Where the brief says "my landing zone", the design says: *the solution onboards to the Citadel governance hub of the adopting organisation's Azure landing zone*.
    - **(b) Never harden a hedge, never invent.** "I don't think you will use X" is not "no X": decide on merit and give the reason. Do not invent constraints, assumptions, licence positions or sources. A design has no "Assumptions" section and no "constraints" table with a "source" column; sizing numbers are labelled *scenario parameters*.
    - **(c) No lab.** The system never deploys resources in order to experiment — it costs real money and needs its own governance. It learns from documentation, price lists, the bills it reads, replays of history and small reversible trials that an owner approves.
    - **(d) Proportion and plain words.** A design is short enough to be read. The lint enforces a size budget (README ≤ 1,800 words, every other document ≤ 6,000, the whole design ≤ 42,000) and no wall of text (no paragraph over 1,100 characters, no table row over 800). Define each term once, in the README's glossary; do not coin jargon (no "exam", "spine", "leaf", "authority chain"). Pictures follow rule 7.
    - **(e) Decisions are rubber-ducked twice, by different model families.** Each technology decision records the alternatives, cost, security impact and reversibility. Every statement about a Microsoft product is verified on the vendor's page **today** (preview or generally available, regions, price) — nothing from memory.
    - **(f) Cost is a design constraint.** Every component has an idle cost and a scale-to-zero story, and a line in the cost model; numbers in the cost document come from `tools/cost-model.py` (`--update-doc`, then `--check`), never typed by hand.
    - **(g) Review history stays out of the design.** Round numbers, finding ids and dispositions live in [`docs/reviews/`](docs/reviews/README.md); the design says what the system is, not how it was argued.
    - **(h) Feedback names symptoms.** When the project owner lists defects, audit the whole work for the same class of mistake and fix the cause; patching only the named items repeats the failure.
    - **(i) Be honest about what is unproven.** Say what a safeguard does *not* stop. A preview feature is used only behind a switch with a generally available fallback, and the document says which is which.
