# Rules for agents working in this repository

Short, durable and binding for every session and every sub-agent. Each rule comes from the operator; the date is when it was given. Pass them on to any sub-agent you start.

1. **The repository stays PRIVATE until the operator says to switch it** (2026-10-31: "Keep the repo private until I say to switch it."). Never change its visibility, and never publish any of its content elsewhere — no public fork, GitHub Pages site, release, gist, package, or text posted to another repository. Anything that says "publish" waits for that word. Going public is a one-way door and is the operator's click.
2. **Ideation first; assume, don't ask** (2026-10-31: "Dont frustrate the ideation processes with questions that have no purpose here"). Take the sensible option and say so; do not stop to ask the operator questions that have no purpose in ideation. **In the ideation documents (docs 01–12) do not create decision registers, assumption lists, risk registers, kill criteria or gates** — the operator rejected them as bloat and as technical worry that does not belong in ideation. The questions that matter are *design* questions about the idea itself. (The design phase, rule 11, is different: there the operator asked for decisions, security, governance and tests.)
3. **Licence: MIT** (2026-10-31) — [`LICENSE`](LICENSE).
4. **Keep history.** Never edit `docs/_archive/` (the frozen earlier versions), and keep the raw reports in `docs/reviews/` verbatim apart from their headers and the appended spot-checks. A substantive change is a new version — a git tag and a [CHANGELOG](CHANGELOG.md) entry — never an overwrite.
5. **Before every commit** run `python tools/check-docs.py --strict` (standard library only; install nothing). It checks links, anchors, diagrams and orphans, and enforces rules 2, 6, 7 and 10 with pattern guards (a guard is a safety net, not a substitute for judgement; rule 8 is not mechanically enforced).
6. **This is a learning system — not a rulebook, and not a product built around two examples** (2026-10-31: "Do NOT live from stuff that I fed; build an app that learns how to do the cost optimization, resulting in the findings and tips I provided."). The design must serve *study · survey · test · act · grow*: how the AI learns about new Azure services, gathers knowledge, investigates cost implications, experiments, and recommends. The operator's two original findings may appear **only** as exam questions — in [`docs/07-getting-smarter.md`](docs/07-getting-smarter.md) (the founding exam) and in [`docs/research/exam-bank-cost-traps.md`](docs/research/exam-bank-cost-traps.md) — never as the foundation, a "seed", or a release plan. The lint enforces this.
7. **Pictures show loops, hubs, parallel work and state changes** — never a single linear pipeline (2026-10-31: the operator rejected "a linear process"). Prefer state diagrams with back-edges, hub-and-spoke maps and feedback loops.
8. **Ideation ≠ technology or feasibility.** In the ideation documents (01–12), do not let feasibility, governance or platform detail shape the north star; guardrails come later ([`docs/09-guardrails-later.md`](docs/09-guardrails-later.md)) and the technology is chosen in the design phase (rule 11). Constraints that do apply throughout: Microsoft technology only; Cloud Adoption Framework and Well-Architected alignment; open source (MIT); fully AI-infused; human-in-the-loop; not a chatbot.
9. **Replies:** concise, with full absolute file paths; deliverables are never overwritten — a substantive change is a new version.
10. **One wording for purchases** (the brief: "click OK and the machine will be resized. Or purchasing reserved instances"; the wording below is the design's answer, agreed in review). A commitment purchase is **prepared by the AI, approved by two named humans with different hats, and then executed by the AI** on their say-so — never on its own judgement. Nothing irreversible runs without a human's OK or a rule a human wrote. The lint guards against the older "executed by humans" wording.
11. **The design phase** (2026-10-31: "I want you to start designing … I want to make sure you use the latest and greatest new features in the Microsoft AI ecosystem … the AI parts should all be deployed using the CITADEL framework in my landing zone … all the security and compliance and test and governance … rubber duck all decisions on technology … twice with different models … as cost efficient as possible"). The ideation (tag `ideation-v4`) stays the north star; the design lives in [`docs/design/`](docs/design/README.md) and **may** name technologies and contain security, governance, test and decision content, because the operator asked for it. Still binding in the design: rules 1, 3–7, 9, 10; the operator's two findings stay exam questions, never the foundation; no questions to the operator without a purpose — assume and state the assumption. Rules for the design work: (a) every technology decision is recorded with its alternatives, cost and security impact, reversibility and the verdicts of **two rubber-duck rounds on different model families**; (b) every statement about a Microsoft product is verified on the vendor's page **today** (preview versus GA, regions, price) — nothing from memory; (c) cost is a design constraint: every component has an idle cost, a scale-to-zero story and a line in the cost model; (d) research evidence is kept in `docs/design/research/` with the URLs that were fetched. The lint has a design scope for this (see the docstring of `tools/check-docs.py`).
